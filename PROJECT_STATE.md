**TASK-005 — сессии и токены.** Первый успешный ввод кода создаёт учётную запись (одна на номер при любых гонках) и в той же транзакции — сессию мобильного приложения; ответ `POST /auth/login-code/verify` аддитивно получил `accountId` и `session` (access-токен на 15 минут, refresh-токен, сроки). Защищённые маршруты: `GET /auth/me`, `GET /auth/sessions`, `DELETE /auth/sessions/{sessionId}`, `POST /auth/sessions/end-others`, `POST /auth/sessions/end-all`, `POST /auth/logout`; коды ошибок различают «обновите токен» (`ACCESS_TOKEN_EXPIRED`), «войдите» (`AUTH_REQUIRED`) и «сессия завершена, войдите заново» (`SESSION_ENDED`). `POST /auth/session/refresh` ротирует пару и сдвигает скользящий срок (мобильное 90 дней, кабинет 180 дней, админка 12 часов от входа без продления); повтор того же обмена в пределах 60 с возвращает ту же пару (гонки, потерянный ответ), более позднее предъявление заменённого токена завершает сессию (D-044). Refresh-токен в базе не хранится ни в каком виде — только случайное зерно и номер поколения, токен выводится с секретом сервера. Список сессий — только свои, текущая отмечена, IP сокращён до `/24`; чужая сессия неотличима от несуществующей. Мгновенный отзыв: каждый защищённый запрос проверяет строку сессии в PostgreSQL (чёрного списка в Redis нет); при недоступном Redis отозванные сессии отклоняются, действующие работают, не работает только обмен токена (503, повтор); при недоступной PostgreSQL защищённые маршруты отвечают 503. Механика cookie-сессий кабинета и админки готова (HttpOnly, Secure, SameSite=Strict, cookie уходит только на обмен и только с `Origin` своего веб-клиента), выдача закрыта до TASK-006: 403 `SESSION_KIND_UNAVAILABLE` до проверки кода, код не расходуется. Вид сессии выбирает `X-Client`; без заголовка — мобильная, наименее привилегированная. CORS — только домены кабинета и админки из конфигурации (`SUPPLIER_WEB_ORIGINS`, `ADMIN_WEB_ORIGINS`), чужой `Origin` получает 403 `ORIGIN_NOT_ALLOWED`; запросы без `Origin` работают; долг T-1 закрыт. Лимиты обмена: 30 в час на сессию, 600 в час на IP. Сроки и пороги — `SESSION_*` через `SessionSettingsSource` (замена — TASK-007). Токены не попадают в журнал и ответы (тест перехвата всего вывода процесса); ошибки запросов к базе пишутся без значений параметров. Правило коммитов D-024 внесено в CLAUDE.md. **TASK-004 — одноразовые коды входа.** `POST /auth/login-code` и `POST /auth/login-code/verify`. Номер приводится к единому виду (`8 701…`, `+7 (701)…`, `7011234567` — один номер); принимаются только мобильные номера Казахстана (вторая цифра национального номера 0, 4, 5, 6, 7), городские (71x, 72x), российские, иностранные номера и мусор — `VALIDATION_ERROR` без отправки. Ответ одинаков, есть аккаунт с этим номером или нет. Код 6 цифр, живёт 5 минут от фактической отправки, хранится только HMAC-хэшем с секретом, одноразовый; действует только последний доставленный код; одновременный ввод верного кода даёт ровно один успех. Каналы — сначала WhatsApp, при ошибке доставки SMS; явный выбор SMS («не пришло») — сразу SMS; повторный код любым каналом не раньше 60 с; если не доставил ни один канал — `LOGIN_CODE_DELIVERY_FAILED`, можно сразу повторить (попытка SMS остаётся в дневном счётчике). Каналы пока тестовые, реальные — TASK-026. Лимиты (решение D-023) — в Redis; превышение — 429 `RATE_LIMITED` с `Retry-After`; при недоступном Redis код не выдаётся и не проверяется (503), процесс не падает, восстановление без перезапуска. Пороги — переменные `LOGIN_CODE_*`, читаются через `LoginCodeSettingsSource` (замена на настройки — TASK-007). Проверка возвращает подтверждённый номер ровно один раз; отдельного токена подтверждения нет, сессию выдаст TASK-005 в том же запросе (ARCHITECTURE I34). Канал последнего подтверждения хранится по номеру (`phone_verification`) — основа отметки «нет WhatsApp» (PRODUCT 15). Номер в журнале только маской `+7***1234`, кода нет — проверено тестом, перехватывающим весь вывод процесса за интеграционный прогон.
