**TASK-004 — одноразовые коды входа.** `POST /auth/login-code` и `POST /auth/login-code/verify`. Номер приводится к единому виду (`8 701…`, `+7 (701)…`, `7011234567` — один номер); принимаются только мобильные номера Казахстана (вторая цифра национального номера 0, 4, 5, 6, 7), городские (71x, 72x), российские, иностранные номера и мусор — `VALIDATION_ERROR` без отправки. Ответ одинаков, есть аккаунт с этим номером или нет. Код 6 цифр, живёт 5 минут от фактической отправки, хранится только HMAC-хэшем с секретом, одноразовый; действует только последний доставленный код; одновременный ввод верного кода даёт ровно один успех. Каналы — сначала WhatsApp, при ошибке доставки SMS; явный выбор SMS («не пришло») — сразу SMS; повторный код любым каналом не раньше 60 с; если не доставил ни один канал — `LOGIN_CODE_DELIVERY_FAILED`, можно сразу повторить (попытка SMS остаётся в дневном счётчике). Каналы пока тестовые, реальные — TASK-026. Лимиты (решение D-023) — в Redis; превышение — 429 `RATE_LIMITED` с `Retry-After`; при недоступном Redis код не выдаётся и не проверяется (503), процесс не падает, восстановление без перезапуска. Пороги — переменные `LOGIN_CODE_*`, читаются через `LoginCodeSettingsSource` (замена на настройки — TASK-007). Проверка возвращает подтверждённый номер ровно один раз; отдельного токена подтверждения нет, сессию выдаст TASK-005 в том же запросе (ARCHITECTURE I34). Канал последнего подтверждения хранится по номеру (`phone_verification`) — основа отметки «нет WhatsApp» (PRODUCT 15). Номер в журнале только маской `+7***1234`, кода нет — проверено тестом, перехватывающим весь вывод процесса за интеграционный прогон. В dev отправленные коды видны на `http://localhost:3000/dev/login-codes` (после `pnpm --filter api migrate`); сбой WhatsApp имитирует `LOGIN_CODE_TEST_FAILING_CHANNELS=whatsapp`. Production не стартует с тестовыми каналами или dev-страницей (долг T-7). Долг T-5 закрыт: интеграционный тест в CI сверяет описание таблиц Drizzle с базой после миграций; новая таблица регистрируется в `apps/api/src/orm-tables.ts`. CI: зелёный run 35184331403 на `main` (финальный коммит с отчётом — run 35184818724); расхождение схемы воспроизведено: run 35184368428 (красный) → run 35184535655 (зелёный). Интеграционные тесты 53/53. Ручная проверка UI не требовалась (экранов нет); сценарии «Обычный вход», «Не пришло», «Перебор», «Накрутка», «Redis упал» агент прошёл запросами к API на dev.

**TASK-003 — контракт клиент–сервер.** Реестр маршрутов в `packages/contracts` — единый источник для сервера, OpenAPI 3.1 и клиента. `apps/api/openapi.json` хранится в git; в dev доступны `/openapi.json` и `/docs`; CI проверяет, что документ актуален и совпадает с фактически обслуживаемыми маршрутами. Общий типизированный клиент `@adclub/api-client` используется `admin-web`, `supplier-web` и `mobile`, ручных запросов к API в клиентах нет; клиент передаёт платформу и версию (заголовок `X-Client`) и отдаёт типизированную ошибку с `code` и `retryable`. `GET /meta/client-policy` — минимальные версии по платформам и текст обновления на kk/ru/en; клиент ниже минимума получает на любой маршрут, кроме `/health` и политики, HTTP 426 с кодом `CLIENT_UPDATE_REQUIRED`; запросы без версии или с мусором обслуживаются и логируются. Значения политики — в переменных окружения `CLIENT_MIN_VERSION_*`, `CLIENT_UPDATE_MESSAGE_*` (меняются перезапуском API), точка замены на настройки — `ClientPolicySource` (TASK-007). Веб-клиенты показывают сообщение об обновлении; мобильное приложение использует `contracts`, `domain`, `i18n`, `api-client`, при старте запрашивает политику, экран «Нужно обновление» — только по явному ответу сервера, без сети не блокирует. CI: проверка обратной совместимости контракта с базой (oasdiff; для PR — целевая ветка, для push в `main` — предыдущее состояние `main`), осознанное ломающее изменение — трейлер коммита `Contract-Breaking-Change: <причина>`; экспорт JS-бандла мобильного для iOS и Android. Зелёные прогоны: run 35145160711, run 35146081004; ломающее изменение воспроизведено: run 35145444253 (красный) → run 35145690259 (зелёный). Product Owner проверил на телефоне через Expo Go и в браузере: связь с сервером, экран обновления по платформе, отсутствие экрана при минимуме другой платформы и без сервера, повышение минимума при открытом приложении, «старый клиент» в админке, статус связи в кабинете — все сценарии OK.
