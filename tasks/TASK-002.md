# TASK-002 — Каркас сервера: база данных, миграции, конфигурация, модули

## Цель
Сервер, готовый принимать бизнес-модули: подключение к PostgreSQL, Redis и S3 с проверкой готовности, обратимые миграции, валидированная конфигурация, единый формат ошибок и структура доменных модулей по архитектуре. Механизм миграций доказан первой реальной таблицей.

## Контекст
После TASK-001 сервер отвечает только на health. Все последующие задачи этапа A (коды входа, сессии, настройки, фоновые задачи) добавляют таблицы и модули, поэтому основа для данных и модульных границ должна появиться до них. ARCHITECTURE.md 3.4 задаёт состав сервера и список доменных модулей, 5 — модель данных, 7 — формат контракта и ошибок, 15.5 — правило «миграции обратимы, запускаются до деплоя».

## Текущее состояние

- Таблиц, миграций, ORM и подключения к БД нет.
- ORM в ARCHITECTURE 3.4 отмечен как предположение (Drizzle или равнозначная альтернатива) — выбор за тобой, зафиксировать в ARCHITECTURE.md.
- Технический долг T-1 (CORS для любого origin) закрывается в TASK-005, здесь не трогать.

## Требования
1. **Конфигурация.** Все параметры окружения (БД, Redis, S3, порты, окружение dev/staging/prod) читаются из переменных окружения, валидируются при старте; при ошибке процесс не стартует с понятным сообщением. `.env.example` актуален. Секреты в логи не попадают.
2. **Подключения.** PostgreSQL, Redis, S3-совместимое хранилище: подключение при старте, корректное закрытие при завершении. Проверка готовности (readiness) отдельно от liveness: сервер сообщает, какие зависимости доступны. Worker-процесс использует те же подключения.
3. **Миграции.** Механизм обратимых миграций с командами «применить», «откатить», «статус» из CLAUDE.md. Миграции — отдельный шаг, не выполняются автоматически при старте приложения. Первая реальная миграция создаёт одну или несколько фундаментальных таблиц из ARCHITECTURE 5, которые понадобятся EPIC-02 (учётная запись по телефону как минимум); состав — на твоё усмотрение, но без реализации логики этих таблиц. CI проверяет применение и откат миграций на чистой базе.
4. **Модули.** Каркас доменных модулей по списку ARCHITECTURE 3.4 с границами: модуль экспортирует публичный интерфейс, внутренности других модулей недоступны (линт-правило или структура). Заполнены только `identity` (таблица из п. 3, без логики) и служебные модули; остальные — пустые заготовки, если это не создаёт мёртвого кода; допустимо создать только те, что нужны сейчас, при условии, что структура и правило добавления описаны в ARCHITECTURE.md.
5. **Контракт и ошибки.** Входящие запросы валидируются схемами из пакета `contracts`; ошибки валидации, отсутствия ресурса, конфликта и внутренние ошибки возвращаются в едином формате с машиночитаемым кодом (ARCHITECTURE 7). Внутренние детали и стек в ответ не попадают. Формат ошибки описан в `contracts` и используется клиентом хотя бы в одном месте.
6. **Логирование.** Структурированные логи с идентификатором запроса; уровень настраивается; в логи не попадают тела запросов с персональными данными. Полное маскирование — TASK-009, здесь достаточно не логировать тела и секреты.
7. **Тесты.** Интеграционный тест против реальной PostgreSQL (в CI — сервис контейнера): миграции применяются, запрос к таблице проходит, readiness отражает недоступность зависимости. Юнит-тесты для валидации конфигурации и формата ошибок.
8. Значимые решения (ORM, инструмент миграций, структура модулей, формат ошибок) внести в ARCHITECTURE.md.

## Бизнес-правила
Не применимы. Логики предметной области в задаче нет.

## Edge cases
- Недоступна одна из зависимостей при старте: сервер стартует, liveness отвечает, readiness сообщает о проблеме; после восстановления зависимости readiness восстанавливается без перезапуска.
- Откат миграции на базе с данными: миграция первой таблицы обратима; политика для необратимых миграций в будущем описана в ARCHITECTURE.md.
- Одновременный запуск миграций двумя процессами не приводит к повреждению (блокировка или идемпотентность).

## Acceptance Criteria
1. Старт с невалидной конфигурацией завершается с понятной ошибкой без утечки значений; с валидной — сервер и worker стартуют.
2. Liveness и readiness — отдельные эндпоинты; readiness показывает состояние PostgreSQL, Redis, S3; при остановленном Redis readiness сообщает о недоступности, liveness работает.
3. Команды миграций из CLAUDE.md: применить → статус показывает применённую миграцию → откатить → таблицы нет → применить снова. Пройдено локально и в CI на чистой базе.
4. Первая миграция создаёт таблицу(ы) из ARCHITECTURE 5 для EPIC-02; в коде нет бизнес-логики по ним.
5. Запрос с невалидным телом возвращает единый формат ошибки с кодом; несуществующий маршрут и внутренняя ошибка — тот же формат; стек в ответе отсутствует. Формат описан в `contracts`.
6. Импорт внутренностей одного модуля из другого падает на линте (или невозможен структурно) — воспроизведено.
7. Интеграционный тест против реальной PostgreSQL проходит локально и в CI.
8. Логи структурированы, содержат идентификатор запроса, не содержат секретов и тел запросов.
9. ARCHITECTURE.md дополнен решениями по ORM, миграциям, модулям, ошибкам.

## Что должно реально работать
- «Чистая машина»: клон → окружение → миграции → сервер → readiness зелёный по всем трём зависимостям.
- «Падение зависимости»: остановить Redis → readiness красный по Redis, liveness зелёный → поднять Redis → readiness зелёный без перезапуска сервера.
- «Плохой запрос»: отправить невалидное тело на любой валидируемый эндпоинт → ответ в едином формате с кодом ошибки; тот же формат при 404.
- «Миграции туда-обратно»: применить, откатить, применить — состояние базы и вывод команды статуса соответствуют на каждом шаге.
