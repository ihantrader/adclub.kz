# TASK-003 — Контракт клиент–сервер и подключение мобильного приложения к общим пакетам

## Цель
Контракт API становится единым источником правды для сервера и всех трёх клиентов: из схем `packages/contracts` генерируется OpenAPI и типизированный клиент; клиенты сообщают свою версию; сервер умеет потребовать обновления старого мобильного приложения; CI ловит несовместимые изменения контракта. Мобильное приложение перестаёт быть изолированным и использует общие пакеты.

## Контекст
ARCHITECTURE 7 задаёт стиль контракта: REST/JSON, схемы в `contracts`, генерация OpenAPI 3.1 и типизированного клиента, только аддитивные изменения, принудительное обновление по минимальной версии. Причина продуктовая: мобильное приложение обновляется через сторы, старые версии живут неделями, и сервер не должен их ломать (PRODUCT 5, ARCHITECTURE 7.4).

Отдельно: единый TypeScript-стек выбран ради общих контрактов и доменных правил между сервером и клиентами. Сейчас `apps/mobile` их не использует (долг T-4), и если это не решить до экранов этапа B, мобильное разойдётся с сервером.

## Текущее состояние
- `packages/contracts`: демонстрационная схема health, схема готовности, единый формат ошибки (`code`, `message`, `details`, `retryable`) — используется сервером.
- `apps/api` (NestJS): `/health`, `/ready`, глобальный фильтр ошибок, валидация тел запросов схемами из `contracts`, модуль `identity` с таблицей `account` без логики. Боевых эндпоинтов с телом нет.
- `apps/admin-web`, `apps/supplier-web`: используют `contracts` для ответа health.
- `apps/mobile` (Expo SDK 57, TypeScript 6.0.3 по требованию Expo): автономен, общие пакеты не использует; система модулей пакетов — CommonJS (ARCHITECTURE 4.1 I3). Запуск на эмуляторе у агента невозможен (нет Android SDK и macOS).
- Важно для любого кода в `apps/api`: конструкторная инъекция только с явным `@Inject(Класс)` (ARCHITECTURE 4.2 I19).
- CI: обязательная проверка фактическим прогоном на GitHub Actions; NOT RUN для CI недопустим.

## Требования
1. **Генерация OpenAPI.** Документ OpenAPI 3.1 формируется из схем `contracts` и фактических маршрутов сервера. Он доступен в dev-окружении для просмотра и сохраняется артефактом в репозитории или сборке так, чтобы изменения контракта были видны в diff.
2. **Типизированный клиент.** Общий типизированный клиент API, которым пользуются `admin-web`, `supplier-web` и `mobile`. Клиент подставляет общие заголовки (см. п. 3), разбирает единый формат ошибки и отдаёт вызывающему коду типизированную ошибку с `code` и `retryable`. Существующие вызовы health в веб-приложениях переведены на него.
3. **Версия клиента.** Каждый запрос клиента несёт платформу (ios / android / supplier-web / admin-web) и версию приложения. Сервер принимает запросы без этих данных (старые клиенты, внешние вызовы), но логирует их отсутствие.
4. **Политика клиента.** Публичный эндпоинт политики клиента: минимальная поддерживаемая версия по платформе и текст сообщения об обновлении (ARCHITECTURE 7.4). Пока таблицы настроек нет (TASK-007), значения берутся из конфигурации сервера с понятной точкой замены. Если версия клиента ниже минимальной, сервер на любой запрос, кроме политики и health, отвечает единым форматом ошибки с отдельным кодом «требуется обновление».
5. **Обратная совместимость в CI.** CI сравнивает контракт текущей ветки с контрактом в `main` и падает на несовместимом изменении (удаление поля или маршрута, изменение типа, новое обязательное поле во входящих данных). Аддитивные изменения проходят. Способ обойти проверку для осознанного breaking change описан в ARCHITECTURE.md и требует явного действия.
6. **Мобильное приложение и общие пакеты (T-4).** `apps/mobile` использует `contracts` и типизированный клиент (как минимум для политики клиента), `domain` и `i18n` подключаются и работают в Metro. При старте приложение запрашивает политику клиента и, если версия ниже минимальной, показывает экран «нужно обновление» с текстом с сервера; при недоступности сервера — не блокирует пользователя этим экраном. Если совместное использование пакетов с Expo требует изменений системы модулей, TypeScript или сборки пакетов — сделай их так, чтобы остальной репозиторий продолжил работать, и зафиксируй в ARCHITECTURE.md.
7. **Проверка мобильного без эмулятора.** Раз эмулятора у тебя нет, обеспечь проверку, которая доказывает, что мобильный бандл с общими пакетами собирается (например, экспорт JS-бандла для обеих платформ в CI), и тесты логики экрана политики. Запуск на телефоне выполнит Product Owner через Expo Go — подготовь для этого окружение (см. «Что должно реально работать»).
8. Значимые решения внести в ARCHITECTURE.md; блок «0. Проект» CLAUDE.md обновить, если изменились команды.

## Бизнес-правила
- Старое мобильное приложение, версия которого не ниже минимальной, продолжает работать после любых аддитивных изменений сервера.
- Экран «нужно обновление» показывается только по явному ответу сервера; отсутствие связи не должно приводить к блокировке.
- Текст сообщения об обновлении приходит с сервера и меняется без выпуска приложения.

## Edge cases
- Клиент не прислал версию или прислал мусор — запрос обрабатывается как от неизвестной версии, не падает с 500.
- Минимальная версия повышена, пока приложение открыто — следующий запрос получает код «требуется обновление», клиент показывает экран.
- Сервер недоступен при старте мобильного приложения — приложение открывается, экран обновления не показывается.
- Разные минимальные версии для iOS и Android.

## Не входит в задачу
- Бизнес-эндпоинты (коды входа, сессии, каталог).
- Таблица настроек и админка для минимальной версии (TASK-007, EPIC-12).
- OTA-обновления, EAS Build, публикация в сторы.
- Экраны мобильного приложения, кроме экрана «нужно обновление».
- Изменение CORS (T-1, TASK-005).
- Сверка Drizzle-схемы с миграциями (T-5, TASK-004).

## Acceptance Criteria
1. OpenAPI 3.1 генерируется из схем и маршрутов; содержит health, ready и политику клиента с форматом ошибки; изменение схемы отражается в сгенерированном документе.
2. `admin-web`, `supplier-web` и `mobile` вызывают API через общий типизированный клиент; ручных fetch к API в клиентах не осталось.
3. Запросы клиентов несут платформу и версию; сервер принимает запросы и без них.
4. Эндпоинт политики клиента отдаёт минимальные версии по платформам и текст; запрос от версии ниже минимальной на обычный маршрут получает единый формат ошибки с кодом «требуется обновление»; health и политика доступны всегда.
5. CI падает на несовместимом изменении контракта и проходит на аддитивном — оба случая воспроизведены (изменение → прогон → откат).
6. `apps/mobile` импортирует `contracts`, `domain`, `i18n` и типизированный клиент; JS-бандл собирается для iOS и Android в CI.
7. Логика мобильного экрана политики покрыта тестами: версия ниже минимальной → экран; версия в порядке → нет экрана; сервер недоступен → нет экрана.
8. Фактический прогон CI на GitHub Actions зелёный; ссылка и статус получены через API/CLI.
9. ARCHITECTURE.md дополнен; CLAUDE.md, блок «0. Проект», актуален.

## Что должно реально работать
- «Старый клиент»: выставить минимальную версию выше текущей версии веб-админки → обычный запрос из админки получает ошибку «требуется обновление», админка показывает понятное сообщение; вернуть значение → всё работает.
- «Ломающее изменение»: удалить поле из схемы ответа → CI красный на проверке совместимости; вернуть → зелёный.
- «Мобильное на телефоне» (выполнит Product Owner через Expo Go): приложение открывается и показывает, что связь с сервером есть; минимальная версия для платформы телефона повышена → после перезапуска виден экран «нужно обновление» с текстом с сервера; сервер остановлен → приложение открывается без экрана обновления. Для этого окружение должно позволять телефону в той же Wi-Fi сети обращаться к API на машине разработки — опиши в отчёте, как это настроено.
