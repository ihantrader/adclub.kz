# TASK-004 — Одноразовые коды входа: выдача, проверка, каналы

Модель: Opus 5, High

## Цель
Сервер умеет подтвердить владение номером телефона одноразовым кодом: выдать код, доставить его через канал с резервом, проверить его и устоять перед перебором и накруткой отправок. Заодно CI начинает ловить расхождение между описанием схемы в ORM и фактической базой после миграций (долг T-5).

## Контекст
Паролей в продукте нет: пользователь, сотрудник поставщика и администратор входят по одноразовому коду (PRODUCT 6.1, 12.6, 16). Основной канал — WhatsApp, резервный — SMS; SMS для уведомлений не используется (PRODUCT 15). Технический поток и защита описаны в ARCHITECTURE 8.1; значения по умолчанию и ключи настроек — ARCHITECTURE 14.

Это первая задача EPIC-02. На её результат опираются TASK-005 (выдача сессий после успешной проверки кода), TASK-006 (учётная запись, роли, выбор компании), TASK-026 (реальные WhatsApp и SMS-провайдер вместо тестовых каналов).

Коды входа — самое дорогое место для злоупотреблений: каждая отправка стоит денег (особенно SMS), а перебор кода даёт доступ к чужому аккаунту.

## Требования
1. **Запрос кода.** Публичный эндпоинт принимает номер телефона (и, при необходимости, желаемый канал) и отправляет одноразовый код. Номер приводится к единому виду; разные записи одного номера (`+7 701 …`, `8 701 …`, с пробелами и скобками) считаются одним номером.
2. **Проверка кода.** Публичный эндпоинт принимает номер и код и отвечает, подтверждён ли номер. Успешная проверка погашает код. Сессий и токенов в этой задаче нет: ответ об успехе сейчас не выдаёт доступ, выдача сессии добавится аддитивно в TASK-005. Результат успешной проверки должен быть однократно пригоден для TASK-005 — как именно, решаешь ты; зафиксируй в ARCHITECTURE.md.
3. **Каналы.** Отправка идёт через абстракцию канала. В этой задаче — тестовые реализации двух каналов (основной «WhatsApp» и резервный «SMS»), которые можно заставить вернуть ошибку доставки для проверки резерва. Реальные провайдеры — TASK-026, их подключение не должно требовать изменений в логике кодов.
4. **Резерв.** Код уходит по SMS, если: основной канал вернул ошибку доставки; пользователь запросил код повторно с выбором SMS («не пришло»), но не раньше разрешённого интервала; пользователь сразу явно выбрал SMS.
5. **Код в dev.** В dev и тестах разработчик и Product Owner могут увидеть отправленный код для ручной проверки — способ выбираешь ты. В production-конфигурации это невозможно: сервер не должен стартовать с тестовыми каналами или с механизмом показа кода.
6. **Защита от перебора.** Ограничено число попыток ввода на один код; после исчерпания код недействителен и нужен новый. После неудачных попыток — нарастающая задержка или эквивалентная защита. Перебор не должен обходиться запросом новых кодов подряд: число проверок и выдач на номер за период тоже ограничено.
7. **Защита от накрутки отправок.** Ограничения частоты выдачи кода по номеру и по IP; отдельный, более строгий дневной лимит отправок SMS на номер и на IP (защита от SMS-накрутки за наш счёт). Превышение — ошибка единого формата с отдельным кодом, `retryable: true` и временем, через которое можно повторить.
8. **Пороги.** Длина кода, срок жизни, число попыток, интервал повторной отправки, лимиты частоты — из конфигурации сервера с понятной точкой замены на таблицу настроек (TASK-007), как у политики клиента. Значения по умолчанию — ARCHITECTURE 8.1 и 14.
9. **Журнал.** В журнале видно: запрос кода, канал и результат доставки, переход на резерв, успешная и неуспешная проверка, срабатывание лимита. Код в логах не появляется никогда; номер телефона в логах — только в маскированном виде.
10. **Канал подтверждения.** Для успешно подтверждённого номера сохраняется канал, через который пришёл последний действующий код. Это нужно для отметки «нет WhatsApp» в профиле (PRODUCT 15) в следующих задачах.
11. **Контракт.** Эндпоинты и новые коды ошибок — в реестре `contracts`, OpenAPI обновлён, проверка совместимости проходит (изменение аддитивное).
12. **Долг T-5.** CI падает, если описание схемы в ORM расходится с базой, полученной применением миграций (отсутствующая или лишняя таблица, колонка, тип, обязательность). Новые таблицы этой задачи проходят эту проверку.
13. Значимые решения — в ARCHITECTURE.md; блок «0. Проект» CLAUDE.md — если изменились команды или способ увидеть код в dev.

## Бизнес-правила
- Ответ на запрос кода одинаков независимо от того, существует ли аккаунт с этим номером.
- Код никогда не возвращается в ответе API в production и никогда не пишется в логи.
- В каждый момент у номера не больше одного действующего кода: новый код делает предыдущий недействительным. Пользователь, получивший код и по WhatsApp, и по SMS, должен ввести последний.
- Код одноразовый: после успешной проверки повторно не принимается.
- Истёкший код и код после исчерпания попыток не принимаются, даже если введены верно.
- Лимиты не должны мешать обычному человеку: один запрос, одна повторная отправка через интервал, пара ошибок ввода — проходят без блокировки.
- В MVP принимаются только мобильные номера Казахстана (+7 7xx…). Номер в другом формате или другой страны — понятная ошибка валидации, код не отправляется.

## Edge cases
- Два одновременных запроса кода для одного номера — действующим остаётся ровно один код, лимиты учитывают оба запроса.
- Два одновременных ввода верного кода — успех ровно один.
- Верный код, введённый для другого номера, не принимается.
- Оба канала вернули ошибку доставки — ответ единого формата с `retryable: true`; лимиты при этом не расходуются так, чтобы человек оказался заблокирован без полученного кода.
- Redis недоступен — выдача кода не становится безлимитной: запрос отклоняется с `retryable: true`, сервер не падает. `/ready` уже показывает деградацию Redis.
- Мусор вместо номера или кода (буквы, пустая строка, очень длинная строка) — ошибка валидации, не 500.
- Устаревший клиент (ниже минимальной версии) получает 426, как на любой обычный маршрут.
- Повторная отправка раньше разрешённого интервала — ошибка с временем ожидания, новый код не создаётся.

## Acceptance Criteria
1. Запрос кода и проверка кода работают через публичные эндпоинты; разные записи одного казахстанского номера считаются одним номером; некорректный или неказахстанский номер — ошибка валидации.
2. Успешная проверка погашает код; повторный ввод того же кода, истёкший код и код после исчерпания попыток — отклоняются. Покрыто тестами, в том числе одновременный ввод верного кода.
3. Новый код делает предыдущий недействительным; одновременные запросы оставляют ровно один действующий код.
4. Ошибка доставки основного канала приводит к отправке по SMS; повторный запрос с выбором SMS раньше интервала отклоняется, после интервала — проходит; явный выбор SMS отправляет сразу по SMS.
5. Превышение лимитов по номеру, по IP и дневного лимита SMS возвращает ошибку единого формата с отдельным кодом, `retryable: true` и временем ожидания. Обычный сценарий человека лимитами не блокируется.
6. При недоступном Redis выдача кода отклоняется с `retryable: true`, сервер не падает.
7. Ответ на запрос кода не раскрывает, существует ли аккаунт; код отсутствует в ответе (вне dev) и в логах; номер в логах маскирован — подтверждено тестом, перехватывающим логи.
8. Сервер не стартует в production-конфигурации с тестовыми каналами или механизмом показа кода.
9. Сохраняется канал доставки подтверждённого кода.
10. Пороги берутся из конфигурации с точкой замены на настройки; значения по умолчанию соответствуют ARCHITECTURE 8.1 и 14.
11. OpenAPI содержит новые эндпоинты и коды ошибок; проверка совместимости контракта в CI проходит.
12. Сверка ORM-схемы с базой после миграций падает при расхождении и проходит без него — оба случая воспроизведены в CI (изменение → прогон → откат).
13. Фактический прогон CI на GitHub Actions зелёный; ссылка и статус получены через API/CLI.
14. ARCHITECTURE.md дополнен; CLAUDE.md, блок «0. Проект», актуален.

## Что должно реально работать
- «Обычный вход»: на поднятом dev-окружении запросить код для номера в формате `8 701 …` → увидеть код способом для dev → ввести его для того же номера в формате `+7701…` → успех; ввести тот же код ещё раз → отказ.
- «Не пришло»: тестовый основной канал настроен на ошибку доставки → код уходит по SMS, в журнале виден переход на резерв с маскированным номером и без кода.
- «Перебор»: вводить неверный код до исчерпания попыток → верный код после этого не принимается; запрос нового кода работает в пределах лимитов.
- «Накрутка»: запрашивать коды для одного номера и с одного IP сверх лимита → ошибка с временем ожидания; после истечения окна запрос снова проходит.
- «Redis упал»: остановить Redis → запрос кода отклоняется понятной ошибкой, `/health` отвечает, после запуска Redis запрос проходит без перезапуска сервера.
- «Расхождение схемы»: изменить описание таблицы в ORM без миграции → CI красный на сверке схемы; откатить → зелёный.
