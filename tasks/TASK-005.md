# TASK-005 — Сессии и токены

Модель: Opus 5, High

## Цель
После успешной проверки кода входа человек получает сессию, которой можно пользоваться долго, видеть свои устройства и завершать их. Отозванная сессия перестаёт работать сразу. Механика сессий кабинета поставщика и админки готова, но выдавать их нельзя, пока в TASK-006 нет проверок членства и администратора. CORS сужен до доменов веб-клиентов (долг T-1).

## Контекст
Это вторая задача EPIC-02 «Идентификация и сессии». От неё зависят все функции, требующие входа: гараж и заявки пользователя, кабинет поставщика, админка.

Продуктовые требования:
- PRODUCT 6.1: идентификатор — номер телефона, паролей нет.
- PRODUCT 5: кабинет поставщика держит длительную сессию, повторная авторизация не чаще раза в несколько месяцев, выход только по явному действию.
- PRODUCT 6.7: при выходе из аккаунта данные активных заявок на устройстве удаляются. Это клиентская часть, она будет в TASK-029, но сервер должен позволять выйти.
- PRODUCT 12.6: удалённый сотрудник теряет доступ сразу. Удаление сотрудников появится позже, но мгновенный отзыв закладывается здесь.

Архитектурная основа — ARCHITECTURE 8.2 (вариант A: короткий access-токен и отзываемые refresh-сессии, чёрный список для мгновенного отзыва), 8.3 и 5.1 (`session`, `account`). Сроки: мобильное приложение — 90 дней скользящих, кабинет поставщика — 180 дней скользящих, админка — 12 часов.

Решения Product Owner, которые учитываются в этой задаче:
- **D-025.** Учётная запись создаётся при первом успешном подтверждении номера. Сессия мобильного приложения выдаётся сразу. Сессии кабинета и админки выдаются только после проверок TASK-006. Cookie-сессия кабинета защищена от подделки межсайтовых запросов.
- **D-024.** Правило коммитов вносится в CLAUDE.md (см. требование 9).
- **D-022.** Контракт меняется только аддитивно.
- **D-003.** Сроки и пороги — это настройки, а не константы в коде.

## Требования

1. **Учётная запись по номеру.** При успешной проверке кода учётная запись находится по подтверждённому номеру. Если записи нет, она создаётся. Один номер — одна учётная запись при любых гонках: два одновременных первых входа с одного номера не создают двух записей. Профиль (имя, город, язык, согласия) в задачу не входит.

2. **Выдача сессии мобильного приложения.** Успешный `POST /auth/login-code/verify` для клиента мобильного приложения создаёт сессию и возвращает в том же ответе короткоживущий access-токен, refresh-токен и сроки их действия. Поля добавляются аддитивно, существующие поля ответа не меняются. Ошибочная, повторная или просроченная проверка сессию не создаёт.

3. **Доступ по access-токену.** Защищённые маршруты принимают только действующий access-токен неотозванной сессии. Нужен хотя бы один защищённый маршрут, чтобы поведение было проверяемым: минимум — текущая учётная запись и текущая сессия. Незащищённые маршруты (`/health`, `/ready`, политика клиента, запрос и проверка кода) продолжают работать без токена.

4. **Обновление и ротация.** Refresh-токен обменивается на новую пару токенов. Старый refresh-токен после обмена не работает. Скользящий срок продлевается при обновлении, но админская сессия не живёт дольше 12 часов от входа. Предъявление уже использованного refresh-токена — признак кражи: вся сессия отзывается. При этом обычный клиент не должен терять сессию из-за гонки, когда два его запроса обновления уходят почти одновременно (приложение вернулось из фона, открыто несколько вкладок кабинета). Как отличить гонку от кражи, реши сам и опиши в ARCHITECTURE.md.

5. **Устройства и завершение сессий.** Владелец видит список своих действующих сессий: название устройства или клиента, платформа, версия клиента, когда создана, когда последний раз использовалась. Текущая сессия отмечена. Владелец может:
   - выйти (завершить текущую сессию);
   - завершить одну выбранную свою сессию;
   - завершить все свои сессии, кроме текущей;
   - завершить все свои сессии.

   Чужие сессии недоступны ни для просмотра, ни для завершения: попытка отвечает так же, как для несуществующей сессии. Полный IP в списке не показывается.

6. **Мгновенный отзыв.** После завершения или отзыва сессии её access-токен перестаёт приниматься сразу, а не по истечении срока. Это должно выполняться для всех видов сессий. Если хранилище, через которое реализован мгновенный отзыв, недоступно, отозванная сессия всё равно не должна приниматься. Выбери поведение, которое не пропускает отозванную сессию и не выкидывает все сессии при кратком сбое, и опиши его в ARCHITECTURE.md.

7. **Сессии кабинета поставщика и админки — механика без выдачи.**
   - Сессия кабинета: 180 дней скользящих, refresh хранится в HttpOnly-cookie, недоступной скрипту страницы. Выход только явный.
   - Сессия админки: 12 часов.
   - У сессии кабинета есть место для контекста компании и сотрудника (заполнит TASK-006).
   - **Выдача этих сессий через API в этой задаче закрыта.** Запрос сессии кабинета или админки при проверке кода получает понятную ошибку и не создаёт сессию, при этом код не расходуется впустую. Механика проверяется тестами без открытого пути выдачи.
   - Для cookie-сессии кабинета реализована защита от подделки межсайтовых запросов: запрос с чужого сайта не может выполнить действие от имени сотрудника.

8. **CORS (долг T-1).** Браузерные запросы принимаются только с доменов кабинета поставщика и админки из конфигурации для каждого окружения. Заголовки `X-Client`, `Accept-Language` и `Authorization` разрешены, иначе веб-клиенты сломаются на preflight. Для кабинета разрешена передача cookie. Мобильное приложение и запросы без `Origin` не ломаются. Существующие веб-клиенты в dev продолжают связываться с API.

9. **Правило коммитов (D-024).** Внести в CLAUDE.md:
   - в коммит попадают только явно перечисленные файлы, без `git commit -a` и `git add -A` / `git add .`;
   - перед каждым коммитом проверяется состав изменений;
   - правки Product Owner в документах проекта (PRODUCT.md, PROJECT_PLAN.md, PROJECT_STATE.md, `tasks/` и другие) агент коммитит отдельным коммитом с понятным сообщением в `main` и перечисляет в отчёте;
   - эти правки не смешиваются с коммитами задачи и никогда не попадают во временные или экспериментальные ветки.

   Этой задачи правило касается сразу.

10. **Настройки.** Сроки access-токена и всех видов сессий, а также пороги обновления читаются через источник настроек с точкой замены на таблицу настроек (TASK-007), как у кодов входа. Ключи добавить в ARCHITECTURE 14.

11. **Лимиты.** Обмен refresh-токена защищён от перебора и накрутки лимитом. Значения выбери сам, это настройки. Обычное использование не упирается в лимит.

12. **Журнал.** Фиксируются: создание сессии, обновление, выход, отзыв (одной и всех), обнаружение повторного использования refresh-токена, отказ по отозванной сессии. Номер — только маской. В журнале, ответах об ошибках и OpenAPI-примерах нет access- и refresh-токенов и их частей, пригодных для использования. Секреты хранятся только в виде, непригодном для входа при утечке базы.

13. **Контракт.** Новые маршруты и поля — в `contracts`, OpenAPI и `@adclub/api-client`. Изменение аддитивное, проверка совместимости в CI проходит без трейлера.

14. **Документация.** ARCHITECTURE.md: решения реализации (новый подраздел 4.x), уточнения 5.1, 8.2, 14. CLAUDE.md, блок 0: как получить сессию и вызвать защищённый маршрут в dev.

## Бизнес-правила
- Идентификатор человека — номер телефона. Одна учётная запись на номер.
- Сроки: мобильное приложение — 90 дней скользящих; кабинет поставщика — 180 дней скользящих, выход только явный; админка — 12 часов от входа без продления сверх этого.
- Отозванная, завершённая или истёкшая сессия не даёт доступа ни в одном случае.
- Человек видит и завершает только свои сессии.
- Сессию кабинета или админки нельзя получить, пока нет проверки членства или записи администратора (D-025).
- Повторное использование старого refresh-токена завершает сессию целиком.

## Edge cases
- Два почти одновременных обновления одной сессии от легитимного клиента.
- Украденный refresh-токен предъявлен после того, как владелец уже обновился, и наоборот.
- Два одновременных первых входа одного номера.
- Завершение текущей сессии и последующий запрос с её access-токеном.
- Завершение всех сессий: запросы со всех устройств отклоняются сразу.
- Недоступен Redis или другое хранилище мгновенного отзыва.
- Истёкший access при действующей сессии: клиент получает ошибку, по которой понятно, что нужно обновить токен, а не входить заново.
- Истёкшая сессия: ошибка, по которой понятно, что нужен новый вход.
- Админская сессия, которую обновляют дольше 12 часов.
- Запрос с `Origin` чужого сайта, preflight с `X-Client` и `Accept-Language`, запрос без `Origin`.
- Подделанный или обрезанный токен, токен другого окружения, токен с изменённым содержимым.
- Старая версия клиента ниже минимума по-прежнему получает 426 до проверки токена, где это установлено TASK-003.

## Не входит в задачу
- Роли, контексты, выбор компании сотрудником, `admin_user`, TOTP, единый предикат прав — TASK-006.
- Открытие выдачи сессий кабинета и админки — TASK-006.
- Профиль, согласие на передачу номера, перенос гостевого гаража — TASK-029.
- Экраны входа, списка устройств и выхода во всех клиентах. Существующие клиенты меняются только в той мере, в какой этого требует CORS.
- Таблица настроек — TASK-007. Очистка истёкших сессий фоновой задачей — TASK-008. Общий санитайзер и мониторинг — TASK-009.
- Смена номера телефона, блокировка учётной записи, удаление аккаунта.
- Реальные каналы кодов и запуск production (T-7) — TASK-026.

## Acceptance Criteria
- **AC-1.** Первый успешный вход по номеру создаёт ровно одну учётную запись, в том числе при двух одновременных входах. Повторный вход находит ту же запись.
- **AC-2.** Успешная проверка кода для мобильного клиента возвращает access, refresh и сроки. Неуспешная, повторная или просроченная проверка сессию не создаёт. Существующие поля ответа не изменились.
- **AC-3.** Защищённый маршрут принимает только действующий access неотозванной сессии. Подделанный, изменённый, истёкший токен и токен отозванной сессии отклоняются единым форматом ошибки, по коду различимы «обновите токен» и «войдите заново». Незащищённые маршруты работают без токена.
- **AC-4.** Refresh обменивается на новую пару, старый refresh после этого не работает. Повторное использование старого refresh отзывает сессию. Одновременные обновления легитимного клиента сессию не отзывают. Скользящий срок продлевается, админская сессия не переживает 12 часов от входа.
- **AC-5.** Список сессий показывает только свои сессии с отметкой текущей, без полного IP. Выход, завершение одной, всех кроме текущей и всех работают. Чужая сессия недоступна и не отличима от несуществующей.
- **AC-6.** После любого завершения или отзыва access-токен этой сессии отклоняется сразу. При недоступном хранилище мгновенного отзыва отозванная сессия не принимается, процесс не падает, после восстановления работа идёт без перезапуска.
- **AC-7.** Выдача сессий кабинета поставщика и админки через API закрыта: понятная ошибка, сессия не создана. Механика cookie-сессии кабинета (HttpOnly, 180 дней скользящих, явный выход) и 12-часовой сессии админки подтверждена тестами. Защита от подделки межсайтовых запросов для cookie-сессии подтверждена тестом с запросом «с чужого сайта».
- **AC-8.** CORS: разрешены только настроенные домены кабинета и админки. Preflight с `X-Client`, `Accept-Language`, `Authorization` проходит. Чужой origin отклоняется. Мобильный клиент и запросы без `Origin` работают. Веб-клиенты в dev связываются с API.
- **AC-9.** Refresh защищён лимитом с ответом `RATE_LIMITED`. Обычный сценарий в лимит не упирается.
- **AC-10.** Токены и их пригодные к использованию части не встречаются в журнале за весь интеграционный прогон и в ответах об ошибках. Секреты сессий в базе хранятся в виде, непригодном для входа. События из требования 12 пишутся, номер маскирован.
- **AC-11.** Сроки и пороги читаются через источник настроек с точкой замены на TASK-007. Ключи есть в ARCHITECTURE 14 и `.env.example`.
- **AC-12.** Контракт, OpenAPI и `@adclub/api-client` обновлены. Проверка совместимости проходит без трейлера. Сверка ORM-схемы с базой проходит, новые таблицы зарегистрированы.
- **AC-13.** CLAUDE.md содержит правило коммитов D-024. Коммиты этой задачи ему соответствуют: в отчёте состав каждого коммита.
- **AC-14.** CI на `main` зелёный — фактический прогон, номер и статус через `gh` (D-018).
- **AC-15.** ARCHITECTURE.md обновлён (новый подраздел решений, 5.1, 8.2, 14, версия и история). CLAUDE.md, блок 0: как получить сессию и вызвать защищённый маршрут в dev.

## Что должно реально работать
- **Первый вход.** Запросить код для нового номера → взять код на `/dev/login-codes` → проверить → получить токены → вызвать защищённый маршрут и увидеть свою учётную запись и сессию.
- **Второе устройство.** Войти тем же номером ещё раз → в списке две сессии, текущая отмечена → учётная запись та же.
- **Выход с другого устройства.** С первой сессии завершить вторую → следующий запрос второй сессии отклонён сразу, её refresh не работает.
- **Обновление.** Обменять refresh → новый access работает, старый refresh отклонён → повторить старый refresh → сессия отозвана целиком.
- **Гонка обновлений.** Два одновременных обмена одного refresh легитимным клиентом → сессия продолжает работать.
- **Выйти везде.** Завершить все сессии → ни одна не принимается.
- **Redis упал.** Отозвать сессию → остановить Redis → отозванная сессия по-прежнему отклоняется, действующие ведут себя так, как описано в ARCHITECTURE.md → Redis поднят → работа без перезапуска.
- **Кабинет и админка закрыты.** Попытка получить сессию кабинета или админки при проверке кода → ошибка, сессии нет.
- **CORS.** Веб-клиенты в dev работают. Запрос с чужого origin отклонён.
