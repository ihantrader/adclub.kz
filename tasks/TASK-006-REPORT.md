# TASK REPORT — TASK-006

## Status

COMPLETED — 14/14 AC.

## Result

Один номер телефона работает в трёх ролях. Права решает одно серверное правило. Оно учитывает вид сессии и актуальное состояние членства или записи администратора.

- **Контекст маршрута.** Каждый защищённый маршрут объявляет контекст: `user`, `supplier` или `admin`. Без объявленного контекста сервер маршрут не привяжет.
- **Вход в кабинет поставщика открыт.**
  - Номер без членства получает отказ после расходования кода. Учётная запись и сессия не создаются.
  - Одна компания или запомненная — сессия выдаётся сразу.
  - Несколько компаний — выбор без нового кода: шаг одноразовый и живёт 10 минут.
  - Компанию можно сменить в действующей сессии.
  - Чужая компания неотличима от несуществующей.
- **Вход в админку открыт.**
  - Не-администратор получает отказ после расходования кода.
  - Сессия админки создаётся только после TOTP. При первом входе настройка TOTP обязательна, после неё выдаются 10 одноразовых резервных кодов.
  - Работают повторные входы по коду приложения или по резервному коду.
  - Есть защита от повторного использования кода, допуск расхождения часов и лимиты попыток. Если Redis недоступен — отказ.
  - Администратор может получить новый набор резервных кодов.
  - Администратор может сбросить TOTP другому администратору, но не себе.
- **Серверная команда оператора.** Назначает и снимает администратора, сбрасывает TOTP. В dev и тестах она же заводит компании и сотрудников. Через API назначить администратора нельзя.
- **Мгновенная потеря прав.**
  - Удалили членство — сессия этой компании на следующем же запросе или обмене получает `SUPPLIER_ACCESS_CLOSED`.
  - Сняли администратора или сбросили TOTP — его сессии админки завершаются сразу.
  - Остальные сессии человека продолжают работать.

## Technical Decisions

Все решения внесены в ARCHITECTURE.md, раздел 4.8 (I67–I79). Там же уточнены разделы 5.1, 8.1, 8.3, 14, заголовок и история.

- **Выбор компании и TOTP при существующем ответе `verify`** (вопрос из задачи).
  - Поле `session` в ответе 200 обязательное. Сделать его необязательным — ломающее изменение.
  - Поэтому требование следующего шага возвращается как ошибка 403 с `details.signInStep { token, expiresAt }`: коды `SUPPLIER_SELECTION_REQUIRED`, `TOTP_SETUP_REQUIRED`, `TOTP_REQUIRED`.
  - Шаг хранится в `sign_in_step`. В базе лежит только HMAC токена, ключ выводится из `SESSION_TOKEN_SECRET`. Шаг одноразовый: блокировка строки `FOR UPDATE`.
  - Сессия админки до второго фактора не существует (I69).
- **Порядок отказа (D-046).** Продолжение в транзакции кода возвращает итог. Отказ выбрасывается после фиксации, поэтому код расходуется при любом исходе. Для кабинета и админки учётная запись только ищется, но не создаётся.
- **Предикат.** `decideAccess` в `@adclub/domain`. Состояние членства и администратора читается одним SQL-запросом вместе со строкой `session`.
  - Потеря контекста завершает сессию с причиной `access_closed` / `admin_removed` / `totp_reset`. Восстановленное членство старую сессию не возвращает (I67, I76).
  - Закрыт долг из TASK-005.A: `ApiRoute` теперь требует конкретный guard доступа (с меткой), а не любой.
- **Смена компании** меняет контекст той же сессии, новая сессия не создаётся. Черновик 8.3 (`/auth/switch-context`) предполагал новую сессию; уточнено в 8.3 и I70.
- **TOTP.**
  - Собственная реализация RFC 6238 на `node:crypto`.
  - Секрет шифруется AES-256-GCM; в дополнительные данные входит id строки.
  - Повтор кода запрещён через `totp_last_used_step`.
  - Новый набор резервных кодов требует текущий код приложения (I71, I72).
- **`IdentityModule` стал `global`.** Nest 12 различает динамические модули по ссылке: повторный `forRoot` в другом модуле создал бы второй экземпляр (I67).
- **Серверная команда** — отдельная точка входа `src/operator.ts`: контекст Nest без HTTP и без Redis (I75).
- **Общий перехват вывода интеграционных тестов** закрывает долг из TASK-005.A: раньше проверка на утечку токенов охватывала только файл тестов сессий (I77).

## Deviations

- **QR-изображение сервер не рисует.** Он отдаёт содержимое QR (`otpauthUri`) и секрет для ручного ввода; картинку строит экран A-AUTH (TASK-031).
  - Задача говорит «сервер выдаёт данные… QR и секрет». Данные те же, но изображение не генерируется: генератор QR на сервере — лишняя зависимость (у `qrcode` в зависимостях есть CLI-пакеты).
  - Если нужен именно PNG/SVG с сервера — это небольшая доработка (ARCHITECTURE 4.8 I71).
- **Секрет TOTP и резервные коды всё же возвращаются в ответах.** Требование 7 запрещает секреты «в ответах в открытом виде», но требование 4 обязывает показать их при настройке. Поэтому они возвращаются только в ответе шага настройки и при выпуске нового набора — и больше нигде: ни в ошибках, ни в `/auth/me`, ни в примерах OpenAPI.
- **Требования следующего шага оформлены кодами ошибок 403 с `details`**, а не отдельным успешным ответом. Так обязательное поле `session` в ответе `verify` сохраняется без ломающего изменения (I69).
- **Смена компании меняет контекст той же сессии.** Черновик ARCHITECTURE 8.3 предлагал новую сессию; уточнено в 8.3.
- **Заголовок ARCHITECTURE.md.** По задаче основание — SCREENS.md 1.0. Пока шла работа, параллельная сессия PO обновила SCREENS.md до 1.1 (коммит `98bbd5f`). Сверку ARCHITECTURE с SCREENS 1.1 я не делал.
- **Новые таблицы `supplier` и `supplier_member` пока в модуле `identity`.** `supplier` переедет в модуль поставщиков в TASK-016 без изменения схемы.

## Known Issues / Risks

- **Смена `ADMIN_TOTP_ENCRYPTION_KEY`** делает недействительными все секреты TOTP и резервные коды. Нужен сброс серверной командой `admin:reset-totp` для каждого администратора. Ротации ключа нет.
- **Строки `sign_in_step`** копятся до фоновой очистки (TASK-008; индекс по `expires_at` есть).
- **Токен шага предъявительский.** Кто его перехватил в течение 10 минут, тот завершит выбор компании; для админки всё равно нужен TOTP.
- **Удаление сотрудника в TASK-017** должно завершать сессии членства в той же транзакции (индекс `session_supplier_member_active_idx` есть). Сейчас сессия завершается на ближайшем запросе. Если членство удалили и восстановили до этого запроса, сессия продолжит работать.
- **Лимиты второго фактора по IP** (20 за 15 минут) могут задеть нескольких администраторов за одним NAT — это настройка.
- **Серверная команда в production не проверялась:** production-конфигурация пока не стартует из-за тестовых каналов, TASK-026.
- **Секреты в выводе проверяются только на уровне тестов.** Общий санитайзер журнала — TASK-009, журнал действий `audit_log` — тоже TASK-009; события пока пишутся в журнал приложения.
- **dev-база содержит тестовые данные прогона UAT:** компании «UAT Альфа», «UAT Бета», номера +7707…, администраторы. Удалять их не стал.
