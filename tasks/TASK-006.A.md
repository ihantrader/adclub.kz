# TASK-006.A — Исправления по приёмке TASK-006

Модель: Opus 5, High

## Цель

Закрыть два существенных дефекта безопасности и мелкие замечания, найденные при приёмке TASK-006. Корректно реализованное в TASK-006 не переделывается, продуктовое поведение не меняется.

## Контекст

TASK-006 реализована (ARCHITECTURE.md 0.11, раздел 4.8, I67–I79), CI зелёный. Проверка кода при приёмке нашла:

1. Токен незавершённого шага входа (выбор компании, TOTP) работает для любого, кто его держит. Токен приходит в теле ответа 403 и живёт 10 минут. Если он утечёт (например, через клиентский мониторинг ошибок, который сохраняет тела ответов), с другого устройства можно получить сессию кабинета на 180 дней без кода. Edge case TASK-006 «шаг предъявлен с другого устройства» не обработан и не покрыт тестом.
2. Удаление сотрудника не завершает его сессии: они отклоняются только при следующем запросе, потому что предикат смотрит на текущий статус членства. Повторное добавление сотрудника восстанавливает ту же запись членства с тем же идентификатором. Сессия, которая не обращалась к серверу между удалением и восстановлением (забытый или украденный ноутбук), снова начинает работать. Это нарушает правило «потеря членства прекращает доступ сразу»; восстановление сотрудников появится в TASK-017.

## Текущее состояние

- Шаги входа: `apps/api/src/modules/identity/session/sign-in-steps.service.ts`, `sign-in-step.store.ts`, `sign-in-step.controller.ts`; токен шага приходит в `details` ошибки 403; шаг одноразовый, срок — настройка.
- Членство: `apps/api/src/modules/identity/supplier/supplier-membership.store.ts` — `removeMember` меняет только статус, `addMember` восстанавливает запись через `onConflictDoUpdate`. Серверная команда — `operator.service.ts`. Индекс `session_supplier_member_active_idx` есть.
- Снятие администратора и сброс TOTP уже завершают сессии админки в той же транзакции (`admin-access-revoker.ts`) — это образец.
- Смена компании (`supplier-context.service.ts`, `switchTo`) читает целевое членство без блокировки.
- Шифрование секрета TOTP — `admin-crypto.ts` (AES-256-GCM), расшифровка без явной длины тега.
- `SIGN_IN_*_TTL_SECONDS` не имеют верхней границы.
- Перехват вывода интеграционных тестов подключён ко всем файлам, но коды входа из `session.integration.test.ts` не регистрируются для поиска.
- В отчёте TASK-006 экран входа в админку отнесён к TASK-031; на самом деле это TASK-034 (TASK-031 — кабинет поставщика).

## Требования

1. **Привязка шага входа к устройству.** Незавершённый шаг (выбор компании, настройка и ввод TOTP) можно завершить только с того же клиента, который прошёл проверку кода. Токен из ответа сам по себе недостаточен. Способ — на усмотрение агента (например, HttpOnly-cookie с отдельным случайным значением, хэш которого хранится вместе с шагом). Для мобильного клиента (без cookie) — равноценная защита либо обоснование в отчёте, почему она не нужна (сейчас шаги есть только у веб-клиентов). Предъявление с другого устройства — отказ тем же кодом, что у недействительного шага; шаг при этом не расходуется законным владельцем.
2. **Удаление сотрудника завершает сессии.** Удаление членства в той же транзакции завершает все сессии кабинета этого членства. Восстановление членства старые сессии не возвращает — нужен новый вход.
3. **Смена компании без гонки.** Смена компании на членство, удаляемое в тот же момент, не приводит к переключению сессии на удалённое членство.
4. **Шифрование TOTP.** При расшифровке требуется тег полной длины.
5. **Верхние границы сроков шагов входа** в проверке конфигурации (разумный предел — на усмотрение агента, описать в ARCHITECTURE).
6. **Перехват вывода.** Коды входа из всех интеграционных тестов участвуют в поиске утечек.
7. **Документация.** ARCHITECTURE.md (версия, история, решения), исправление ссылки TASK-031 → TASK-034 в отчёте TASK-006.

## Бизнес-правила

- Сессию кабинета или админки получает только тот, кто сам прошёл проверку кода.
- Удалённый сотрудник теряет доступ сразу и навсегда для существующих сессий; восстановленный сотрудник входит заново.

## Edge cases

- Токен шага предъявлен с другого браузера (без cookie шага), затем законным владельцем — владелец завершает вход.
- Два шага входа одного номера в двух вкладках одного браузера.
- Удаление сотрудника, у которого сессии в двух браузерах, и его мобильная сессия — мобильная и сессии в других компаниях продолжают работать.
- Удаление → восстановление → старая сессия (не обращавшаяся между ними) отклонена.
- Смена компании одновременно с удалением целевого членства.
- Тег шифрования укорочен — расшифровка отклоняется.

## Не входит в задачу

- Экраны входа — TASK-031, TASK-034.
- Удаление и восстановление сотрудников через интерфейс — TASK-017.
- Генерация QR-картинки на сервере — не нужна, картинку строит экран TASK-034.
- Остальные косметические замечания (KDF для ключа, запрет dev-значений секретов в production) — отдельно, если потребуется.

## Acceptance Criteria

- **AC-1.** Тест: токен шага выбора компании и шага TOTP, предъявленный с другого клиента, отклоняется; законный владелец после этого завершает вход.
- **AC-2.** Тест: удаление членства сразу завершает сессии этого членства (строки сессий завершены, а не только отклоняются на запросе); после восстановления членства старая сессия, не обращавшаяся к серверу, отклонена; другие сессии человека работают.
- **AC-3.** Тест на одновременные смену компании и удаление целевого членства: сессия не остаётся в контексте удалённого членства.
- **AC-4.** Тест: укороченный тег отклоняется.
- **AC-5.** Срок шага больше предела — процесс не стартует; есть тест.
- **AC-6.** Коды входа всех интеграционных тестов участвуют в поиске утечек.
- **AC-7.** Контракт — только аддитивно, проверка совместимости без трейлера; миграции (если нужны) обратимы, таблицы зарегистрированы.
- **AC-8.** Существующие тесты проходят без ослабления; CI на `main` зелёный, включая коммит с отчётом (номер и статус через `gh`); коммиты по D-024.
- **AC-9.** ARCHITECTURE.md обновлён; в отчёте TASK-006 исправлена ссылка на TASK-034.

## Что должно реально работать

Запросами к API в dev:

- Войти в кабинет номером сотрудника двух компаний → получить шаг выбора → предъявить токен шага без cookie (другой клиент) → отказ → завершить выбор с исходного клиента → сессия выдана.
- Войти сотрудником → удалить членство серверной командой → сессия завершена → восстановить членство → старая сессия отклонена → новый вход работает.
- Администратор: код → шаг TOTP → предъявить токен с другого клиента → отказ → завершить с исходного → сессия админки.
