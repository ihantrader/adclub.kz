# TASK-006 — Роли, контексты и предикат прав

Модель: Opus 5, High

## Цель

Один номер телефона работает в трёх ролях: пользователь приложения, сотрудник поставщика, администратор. Права определяются одним серверным правилом, которое учитывает вид сессии и актуальное состояние членства или записи администратора. Открыта выдача сессий кабинета поставщика (с выбором и сменой компании) и админки (с обязательным вторым фактором TOTP). Потеря членства или прав администратора сразу прекращает доступ.

## Контекст

Это третья и последняя задача EPIC-02 «Идентификация и сессии». От неё зависят кабинет поставщика (EPIC-06, EPIC-11), админка (EPIC-12) и все функции, где важно, от чьего имени выполняется действие.

Продуктовые требования:

- PRODUCT 2, 5: три роли и три интерфейса. Пользователь работает в мобильном приложении, поставщик в веб-кабинете, администратор в веб-панели.
- PRODUCT 12.6: у компании несколько сотрудников, каждый входит по коду на свой номер. Все сотрудники равноправны. Удалённый сотрудник теряет доступ сразу. Сотрудник может одновременно быть пользователем приложения.
- PRODUCT 5: длительная сессия кабинета, выход только явный.
- SCREENS.md:
  - S-AUTH-01/02: вход в кабинет. Если номер не привязан к кабинету, сообщение показывается только после проверки кода.
  - S-AUTH-03: выбор компании. Выбор запоминается, сменить компанию можно в «Мои настройки».
  - Раздел 6.0: пауза и блокировка поставщика вход не закрывают. Удалённому сотруднику показывается «Доступ к кабинету закрыт».
  - A-AUTH: телефон → код → TOTP. При первом входе обязательна настройка TOTP.
- ARCHITECTURE 8.1 (вход сотрудника и администратора, TOTP), 8.3 (роли, сотрудники, мгновенный отзыв), 5.1 (`supplier_member`, `admin_user`).

Решения Product Owner, которые учитываются в этой задаче:

- **D-025.** Сессии кабинета и админки выдаются только после проверки активного членства или записи администратора. Cookie-сессия защищена от подделки межсайтовых запросов (механика есть с TASK-005).
- **D-045.** Администраторы назначаются и снимаются только серверной командой оператора, с записью в журнал. Через API и админку назначить администратора нельзя. В MVP все администраторы равны.
- **D-046.** Номер без активного членства входит в кабинет или номер без записи администратора входит в админку. Код проверяется и расходуется, затем возвращается отказ. Учётная запись и сессия не создаются.
- **D-047.**
  - Настройка TOTP при первом входе обязательна.
  - При настройке выдаются одноразовые резервные коды.
  - TOTP сбрасывает любой другой активный администратор, но не сам себе. Сброс пишется в журнал и завершает все сессии админки этого администратора.
  - Единственному администратору TOTP сбрасывает серверная команда.
- **D-003.** Пороги и лимиты — это настройки, а не константы.
- **D-022.** Контракт меняется только аддитивно.
- **D-024.** Правило коммитов из CLAUDE.md.

- **Настройки.** Читаются через источники с точкой замены на таблицу настроек (TASK-007): `LoginCodeSettingsSource`, `SessionSettingsSource`.

Таблицы настроек нет, она появится в TASK-007.

## Требования

### 1. Контексты и единый предикат прав

- **Три контекста:**
  - пользователь — мобильная сессия;
  - сотрудник поставщика — сессия кабинета с активным членством в компании этой сессии;
  - администратор — сессия админки у активного администратора, прошедшего TOTP.
- **Контекст задаёт маршрут.** Каждый защищённый маршрут объявляет, в каком контексте он доступен. Проверка выполняется одним общим правилом (предикатом прав) на сервере. В обработчиках своих проверок ролей нет.
- **Права не переносятся между видами сессий.** Сессия одного вида никогда не даёт прав другого контекста, даже если у учётной записи есть другие роли. Мобильная сессия администратора не открывает админские маршруты. Сессия кабинета не открывает маршруты другой компании.
- **Заголовки прав не дают.** Права не зависят от заголовков запроса (`X-Client` и т. п.), только от сессии и данных на сервере.
- **Состояние проверяется на каждом запросе.** Членство и запись администратора проверяются по актуальным данным. Если членство удалено или администратор снят, следующий запрос этой сессии отклоняется.
- **Защищённый маршрут без объявленного контекста обслужить нельзя.** Это правило работает так же, как в TASK-005 для `auth: "session"`.
- **Проверяемые маршруты.** Для каждого из трёх контекстов есть хотя бы один защищённый маршрут. Минимум: `GET /auth/me` дополнен контекстом (компания и сотрудник, признак администратора), есть маршрут текущей компании для кабинета и служебный маршрут для админки.
- **Задел под роли.** Предикат оставляет место для будущих ролей и прав сотрудников (BACKLOG), но в MVP все сотрудники компании равны и все администраторы равны.

### 2. Минимальные данные компании и членства

- **Компания и членство.** Есть компания (название, город; статус, если нужен для будущих задач) и членство сотрудника (учётная запись, компания, отображаемое имя, статус «активно / удалено»). Один номер может быть сотрудником нескольких компаний.
- **Полная модель — позже.** Воронка подключения, реквизиты, адреса, пауза и блокировка — это TASK-016. Добавление, удаление и восстановление сотрудников — TASK-017. Модель данных должна позволить им развиться без переделки.
- **Способ завести данные.** Нужен способ создать компанию и сотрудника без админки и кабинета, иначе вход в кабинет нельзя проверить. Он доступен в development и тестах. В production его нет или он выполняется только серверной командой оператора.
- **Номер сотрудника без учётной записи.** Если при заведении сотрудника у номера ещё нет учётной записи, она создаётся (D-046).

### 3. Вход в кабинет поставщика

- **Порядок входа.** Запрос с клиента кабинета: проверка кода → поиск активных членств по номеру.
  - **Членств нет.** Код израсходован. Возвращается ошибка с отдельным кодом, по которой клиент покажет текст S-AUTH-01/02 («Этот номер не привязан к кабинету поставщика…»). Учётная запись не создаётся, сессия не выдаётся.
  - **Одно членство.** Выдаётся сессия кабинета с контекстом этой компании и сотрудника.
  - **Несколько членств.** Человек выбирает компанию без повторного ввода кода, после чего сессия создаётся в контексте выбранной.
- **Выбор компании.** Выбрать можно только компанию с активным членством. Незавершённый выбор живёт недолго (настройка) и пригоден только один раз. Способ реализации — на усмотрение агента.
- **Смена компании.** Сотрудник может сменить компанию в действующей сессии кабинета без повторного входа, только на компанию с активным членством. После смены права на прежнюю компанию этой сессией не действуют.
- **Запоминание выбора.** Кабинет по SCREENS запоминает выбор. Серверу достаточно, чтобы клиент мог передать предпочтительную компанию при следующем входе. Если членства в ней нет, работает обычный выбор.
- **Статус поставщика.** Пауза и блокировка вход не закрывают (SCREENS 6.0). Если статусы поставщика ещё не заведены, это правило учитывается в модели.
- **Список сессий.** Сессия кабинета в списке своих сессий показывает компанию.

### 4. Вход в админку и TOTP

- **Проверка администратора.** Запрос с клиента админки: проверка кода → проверка активной записи администратора. Если записи нет — код израсходован, возвращается ошибка с отдельным кодом, учётная запись и сессия не создаются (D-046).
- **До прохождения TOTP.** Администратор с активной записью ещё не получает админских прав. Пока второй фактор не пройден, ни один админский маршрут не доступен. Незавершённый шаг живёт недолго (настройка) и не превращается в сессию админки без TOTP.
- **Первый вход — настройка TOTP.**
  - Сервер выдаёт данные для приложения-аутентификатора: QR и секрет для ручного ввода.
  - Администратор подтверждает настройку текущим кодом из приложения.
  - После подтверждения выдаётся набор одноразовых резервных кодов. Он показывается один раз, количество — настройка.
  - Только после этого создаётся сессия админки.
- **Следующие входы.** Код из приложения или один из неиспользованных резервных кодов.
  - Использованный резервный код больше не принимается.
  - Один и тот же TOTP-код повторно в пределах своего окна не принимается.
  - Допускается небольшое расхождение часов устройства (настройка).
- **Защита от перебора.** Проверка второго фактора ограничена лимитом попыток. При недоступности хранилища лимитов — отказ, как у кодов входа.
- **Новый набор резервных кодов.** Администратор в своей сессии может получить новый набор, прежний перестаёт действовать.
- **Хранение.** Секрет TOTP хранится зашифрованным ключом из конфигурации окружения. Резервные коды хранятся в виде, непригодном для входа при утечке базы.
- **Срок сессии.** 12 часов от входа, без продления сверх этого (как в TASK-005).

### 5. Управление администраторами и сброс TOTP

- **Серверная команда оператора (D-045):**
  - назначить номер администратором (если учётной записи нет, она создаётся);
  - снять администратора — все его сессии админки завершаются сразу;
  - сбросить TOTP — нужно, если администратор единственный.

  Каждое действие пишется в журнал приложения. Через API назначить или снять администратора нельзя.
- **Сброс TOTP другому администратору (D-047).** Активный администратор в своей сессии админки сбрасывает TOTP другому администратору через API. Сбросить TOTP себе нельзя. После сброса:
  - секрет и резервные коды этого администратора недействительны;
  - все его сессии админки завершены;
  - при следующем входе обязательна повторная настройка.
- **Экраны не нужны.** Экран сброса появится в TASK-034, здесь нужен только серверный маршрут.

### 6. Мгновенная потеря прав

- **Членство удалено.** Сессии кабинета в контексте этого членства сразу перестают приниматься: и доступ, и обмен refresh-токена. По коду ошибки клиент покажет «Доступ к кабинету закрыт» (SCREENS 6.0). Сессии того же человека в других компаниях и его мобильная сессия продолжают работать.
- **Администратор снят.** Все его сессии админки сразу перестают приниматься. Мобильная сессия и сессии кабинета продолжают работать.
- **Проверка без интерфейса.** Удаление сотрудника появится в TASK-017. Здесь достаточно, чтобы потеря прав срабатывала при изменении данных и была подтверждена тестами.

### 7. Журнал

Фиксируются:

- вход в кабинет с выбором компании и отказ по отсутствию членства;
- смена компании;
- вход в админку, отказ по отсутствию записи администратора;
- настройка TOTP, успешная и неуспешная проверка второго фактора, использование резервного кода, выдача нового набора;
- сброс TOTP (кто и кому);
- назначение и снятие администратора;
- отказ доступа по контексту;
- отказ после потери членства или прав.

Номер пишется только маской. В журнале, ответах, OpenAPI-примерах и базе в открытом виде нет секретов TOTP, TOTP-кодов, резервных кодов и токенов. До появления журнала действий (TASK-009) эти события пишутся в журнал приложения.

- номер не привязан к кабинету;

## Бизнес-правила

- Одна учётная запись на номер, в любых ролях.
- Права определяются видом сессии и актуальным членством или записью администратора. Другие роли той же учётной записи прав не добавляют.
- Сессию кабинета можно получить только при активном членстве, сессию админки — только у активного администратора после TOTP.
- Отказ во входе в кабинет или админку расходует код и не создаёт учётную запись (D-046). Отказ показывается только после проверки кода: посторонний не узнаёт, привязан ли номер к кабинету.
- Сотрудник действует в контексте одной выбранной компании. Данных других компаний эта сессия не видит.
- Пауза и блокировка поставщика вход сотрудника не закрывают.
- Все сотрудники компании равны. Все администраторы равны.
- Назначение и снятие администраторов — только серверной командой (D-045).
- TOTP обязателен для каждого входа в админку. Сбросить TOTP себе нельзя (D-047).
- Потеря членства или прав администратора прекращает доступ сразу.

## Edge cases

- Номер — сотрудник двух компаний. Во время выбора компании членство в одной из них удалили.
- Незавершённый выбор компании или шаг TOTP предъявлен повторно, после истечения или с другого устройства.
- Один человек в одном браузере держит сессии кабинета и админки одновременно. Он же пользуется мобильным приложением.
- Мобильная сессия администратора или сотрудника вызывает админский или кабинетный маршрут.
- Сессия кабинета компании A обращается к данным компании B. Ответ такой же, как для несуществующего объекта.
- Смена компании на ту, где членство удалено или его никогда не было.
- Администратора снимают, пока он на шаге TOTP или в активной сессии.
- Два одновременных подтверждения настройки TOTP из двух вкладок.
- Повтор того же TOTP-кода. Резервный код введён дважды, в том числе одновременно.
- Часы устройства администратора отстают или спешат на один шаг.
- Администратор пытается сбросить TOTP себе.
- Сброс TOTP, когда администратор единственный.
- Redis недоступен при проверке второго фактора.
- Запрос входа в кабинет или админку без `X-Client`: получает только мобильную сессию и не получает прав кабинета или админки.
- Номер, который есть в членстве, но ещё ни разу не входил: учётная запись создана при заведении сотрудника.
- Обмен refresh-токена сессии кабинета после удаления членства.

## Acceptance Criteria

- **AC-1.** Каждый защищённый маршрут объявляет контекст, а проверка выполняется единым предикатом. Маршрут без объявленного контекста обслужить нельзя. Тестовая матрица «вид сессии × контекст маршрута» подтверждает, что другие роли учётной записи прав не добавляют, а заголовки на права не влияют.
- **AC-2.** Вход в кабинет:
  - номер без членства — код израсходован, отдельный код ошибки, учётная запись и сессия не созданы;
  - одно членство — сессия с контекстом;
  - несколько — выбор без повторного кода, только из активных членств, одноразовый и ограниченный по времени.
- **AC-3.** Смена компании в действующей сессии работает только на компанию с активным членством. После смены права на прежнюю компанию этой сессией не действуют. Обращение к данным чужой компании неотличимо от несуществующего объекта.
- **AC-4.** Вход в админку: не-администратор получает отказ без создания учётной записи. Администратор без пройденного TOTP не получает доступа ни к одному админскому маршруту. Незавершённый шаг TOTP одноразовый и ограничен по времени.
- **AC-5.** Первая настройка TOTP: данные для аутентификатора, подтверждение кодом, резервные коды показаны один раз, затем сессия. Следующие входы принимают TOTP или неиспользованный резервный код. Повтор TOTP-кода в окне и повтор резервного кода, в том числе одновременный, отклоняются. Допуск расхождения часов работает. Новый набор резервных кодов отменяет прежний.
- **AC-6.** Проверка второго фактора ограничена лимитом с `RATE_LIMITED`. При недоступном Redis — отказ, процесс не падает, восстановление без перезапуска.
- **AC-7.** Сброс TOTP другим администратором завершает все сессии админки этого администратора и требует повторной настройки. Сбросить себе нельзя. Серверные команды назначения, снятия и сброса работают и пишут журнал. Через API назначить администратора нельзя.
- **AC-8.** Удаление членства сразу отклоняет доступ и обмен refresh-токена сессий кабинета этого членства, с кодом «доступ к кабинету закрыт». Другие сессии человека продолжают работать. Снятие администратора сразу отклоняет его сессии админки.
- **AC-9.** Секреты TOTP хранятся зашифрованными, резервные коды — в виде, непригодном для входа. Тест перехвата всего вывода процесса за интеграционный прогон не находит секретов TOTP, TOTP-кодов, резервных кодов и токенов. Номер в журнале маскирован. События из требования 7 пишутся.
- **AC-10.** Пороги читаются через источник настроек с точкой замены на TASK-007. Ключи есть в ARCHITECTURE 14 и `.env.example`. Без ключа шифрования TOTP процесс вне development и test не стартует.
- **AC-11.** Контракт, OpenAPI и `@adclub/api-client` обновлены. Совместимость проходит без трейлера. Сверка ORM-схемы с базой проходит, новые таблицы зарегистрированы. Миграции обратимы.
- **AC-12.** Мобильный вход, сессии и все сценарии TASK-005 не сломаны: существующие тесты проходят без ослабления.
- **AC-13.** Коммиты соответствуют D-024, в отчёте указан состав каждого коммита. CI на `main` зелёный: фактический прогон, номер и статус через `gh` (D-018), включая последний коммит с отчётом.
- **AC-14.** ARCHITECTURE.md обновлён: основание PRODUCT 1.3, SCREENS 1.0 и DESIGN 0.1, новый подраздел решений, 5.1, 8.1, 8.3, 14, версия и история. CLAUDE.md, блок 0: вход в кабинет и админку в dev.

## Что должно реально работать

Все сценарии проходятся запросами к API в dev.

- **Сотрудник одной компании.** Завести компанию и сотрудника → войти с клиента кабинета → сессия с контекстом компании → маршрут текущей компании отвечает.
- **Сотрудник двух компаний.** Войти → получить выбор → выбрать компанию A → работать → сменить на B → данные A этой сессией недоступны.
- **Посторонний номер в кабинете.** Войти с клиента кабинета номером без членства → отказ после проверки кода → учётная запись не создана.
- **Удалённый сотрудник.** Удалить членство в данных → следующий запрос и обмен refresh-токена отклонены с «доступ закрыт» → мобильная сессия того же номера работает.
- **Первый вход администратора.** Назначить номер серверной командой → войти с клиента админки → настроить TOTP → получить резервные коды → админский маршрут отвечает.
- **Обычный вход администратора.** Войти → TOTP → доступ. Войти ещё раз → резервный код → доступ. Тот же резервный код ещё раз → отказ.
- **Без второго фактора.** После кода, но до TOTP, вызвать админский маршрут → отказ.
- **Сброс TOTP.** Администратор A сбрасывает TOTP администратору B → сессии B завершены → вход B требует настройки. A пытается сбросить себе → отказ.
- **Снятие администратора.** Снять серверной командой → его сессия админки отклонена сразу.
- **Смешение ролей.** Мобильная сессия администратора вызывает админский маршрут → отказ.
- **Redis упал.** Проверка TOTP → отказ без падения → после восстановления работает.
