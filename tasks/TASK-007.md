# TASK-007 — Настройки в данных

Модель: Opus 5, High

## Цель

Продуктовые пороги, лимиты, сроки и тексты хранятся в данных, а не в коде и не в переменных окружения. Администратор видит и меняет их через API без релиза и перезапуска, каждое изменение записывается в историю. Политика клиента (минимальные версии, текст обновления) управляется так же, и её изменение не может отрезать администратору доступ к исправлению.

## Контекст

Первая задача EPIC-03 «Ядро платформы». От неё зависят все задачи с порогами: заявки, уведомления, рейтинг, биллинг, ИИ, гостевой режим.

- **D-003.** Все продуктовые пороги, тарифы, шаблоны и лимиты — данные, не код (PRODUCT 19: пороги будут меняться без релиза).
- **ARCHITECTURE 14** — группы и ключи настроек со значениями по умолчанию; изменения валидируются по типу и диапазону, пишутся в журнал, кэшируются на 30 секунд; тесты задают значения через тот же механизм.
- **SCREENS.md 1.1:**
  - A-SET-01 «Пороги и лимиты»: у значения — диапазон, единица, описание, кто и когда менял; правка показывает «было → стало» и требует причину.
  - A-SET-02 «Политика клиента»: минимальная версия по платформам, тексты обновления kk/ru/en; «Нельзя установить минимальную версию админки выше текущей версии».
- **D-045.** Опасные действия с правами — только серверной командой оператора. По аналогии — D-053 ниже.

**D-053 (предлагается Product Owner'у вместе с задачей).** Настройки безопасности входа — коды входа, сессии, шаги входа, второй фактор (`login_code_*`, `session_*`, `sign_in_*`, `admin_totp_*`, `admin_backup_code_count`) — хранятся в той же таблице, администратор видит их, но меняет только серверная команда оператора. Остальные настройки меняет администратор через API. Причина: ошибочная правка этих значений может открыть перебор кодов или отрезать всех от входа, а в интерфейсе админки их нет (SCREENS A-SET-01).

## Текущее состояние

- **Где сейчас значения.** Пороги кодов входа, сессий, шагов входа и второго фактора — переменные окружения `LOGIN_CODE_*`, `SESSION_*`, `SIGN_IN_*`, `ADMIN_TOTP_*`, `ADMIN_BACKUP_CODE_COUNT`. Читаются через источники с точкой замены: `LoginCodeSettingsSource`, `SessionSettingsSource`, `SignInSettingsSource`. Жёсткие пределы проверяются при старте: админская сессия ≤ 12 часов, шаг входа ≤ 30 минут (ARCHITECTURE 4.7 I63, 4.9 I84).
- **Политика клиента.** `ClientPolicySource` (`apps/api/src/client-policy`), значения — `CLIENT_MIN_VERSION_*`, `CLIENT_UPDATE_MESSAGE_*`, меняются перезапуском API; маршрут `GET /meta/client-policy` и ответ 426 `CLIENT_UPDATE_REQUIRED` работают (TASK-003).
- **Права.** Единый предикат прав: маршрут объявляет контекст `admin`, сессия админки выдаётся только после TOTP (TASK-006). Серверная команда оператора `pnpm --filter api operator …` есть.
- **Нет:** таблицы настроек, журнала действий `audit_log` (TASK-009), очереди и worker-задач с порогами (TASK-008), экранов админки (TASK-034).
- **Тесты.** Два теста TASK-005 в `session.integration.test.ts`, зависящие от времени (токен с TTL 1 с, округление `exp` до секунды), изредка падают на медленной машине.
- Production-окружения нет, переносить значения из существующих установок не нужно.

## Требования

### 1. Реестр настроек

- **Описание каждой настройки** — ключ, группа, тип, единица, допустимый диапазон или набор значений, значение по умолчанию, описание (ru), кто может менять (администратор или только серверная команда — D-053).
- **Типы:** целое, число, да/нет, строка, текст на трёх языках (kk/ru/en), составное значение со своей схемой (например, `guest_limits`), длительность.
- **Состав.** Все ключи ARCHITECTURE 14 и группы SCREENS A-SET-01 заведены со значениями по умолчанию. Ключи, которых нет в ARCHITECTURE 14, но которые называет SCREENS A-SET-01 (например, порог резкого изменения цены, порог ожидания проверки отзывов), — добавить; значение по умолчанию брать из PRODUCT.md, а если его там нет — назвать в отчёте как предположение. Шаблоны уведомлений (`notification_template`) и тарифы (`plan`) — не в этой задаче.
- **Жёсткие пределы безопасности** остаются в силе при любых значениях: админская сессия ≤ 12 часов, шаг входа ≤ 30 минут и другие пределы, уже проверяемые конфигурацией.

### 2. Хранение и чтение

- **Сохраняются только изменённые значения**, для остальных действует значение по умолчанию из реестра; сброс к умолчанию — отдельное действие.
- **Значение в базе, не прошедшее проверку** (ручная правка, изменился реестр) не применяется: действует значение по умолчанию, событие пишется в журнал приложения.
- **Кэш.** Изменение начинает действовать во всех процессах API и worker не позже чем через 30 секунд, без перезапуска.
- **Отказ базы.** Если свежие значения прочитать нельзя, процесс продолжает работать на последних успешно прочитанных значениях. Молча переходить на значения по умолчанию, если в базе сохранены другие, нельзя. Если значения ни разу не удалось прочитать — поведение как у других запросов, зависящих от базы.
- **Перенос.** Коды входа, сессии, шаги входа, второй фактор и политика клиента читают значения из настроек. Соответствующие переменные окружения больше не используются: убрать их из схемы конфигурации и `.env.example`. В окружении остаются только секреты, адреса инфраструктуры и то, что не является продуктовым порогом (описать в ARCHITECTURE).

### 3. API для администратора

- **Список настроек** по группам: ключ, описание, тип, единица, диапазон, значение по умолчанию, текущее значение, кто и когда менял последним, можно ли менять через API.
- **Изменение одного значения** с обязательной причиной. Проверка типа и диапазона на сервере. Ответ — «было → стало».
- **Одновременная правка.** Изменение указывает, от какой версии значения оно сделано; если значение уже изменил кто-то другой — отказ с отдельным кодом, ничего не перезаписывается.
- **Сброс к значению по умолчанию** — тоже с причиной.
- **История изменений** настройки: кто (администратор или серверная команда), когда, было, стало, причина.
- Доступно только в контексте `admin` (предикат TASK-006). Настройки безопасности входа (D-053) через API не меняются — отказ с отдельным кодом.

### 4. Серверная команда оператора

Показать значение, изменить, сбросить, показать историю — для любых настроек, включая настройки безопасности. Причина обязательна, изменение записывается в историю с отметкой «серверная команда». Это же — способ восстановления, если политика клиента или порог выставлены ошибочно.

### 5. Политика клиента в настройках

- Минимальные версии по платформам (iOS, Android, кабинет, админка) и тексты обновления kk/ru/en — настройки. `GET /meta/client-policy` и ответ 426 работают как прежде, но значения берут из настроек и меняются без перезапуска.
- **Защита от блокировки админки.** Минимальную версию админки нельзя установить выше текущей версии админки, которую отдаёт сервер (SCREENS A-SET-02). Администратор со старой вкладкой админки после любых изменений политики может войти и исправить политику: способ — на усмотрение агента, описать в ARCHITECTURE.
- Неверный формат версии — отказ проверки.

### 6. История и журнал

- История изменений хранится в базе и не редактируется через API.
- До появления журнала действий (TASK-009) каждое изменение дополнительно пишется в журнал приложения. TASK-009 перенесёт события в общий журнал; модель истории не должна этому мешать.

### 7. Тесты

- Тесты задают значения настроек через тот же механизм, а не через переменные окружения или константы.
- Стабилизировать два теста TASK-005, зависящие от времени, без ослабления проверок.

### 8. Контракт и документация

- Новые маршруты, схемы и коды ошибок — в `contracts`, OpenAPI, `@adclub/api-client`; изменение аддитивное, проверка совместимости без трейлера.
- ARCHITECTURE.md: подраздел решений 4.x; раздел 14 (фактический список ключей, что осталось в окружении и почему); версия и история.
- CLAUDE.md, блок 0: как в dev посмотреть и изменить настройку (API и серверная команда); прежние указания про `LOGIN_CODE_*`, `CLIENT_MIN_VERSION_*` и т. п. заменить.

## Бизнес-правила

- Продуктовые пороги — данные; изменение не требует релиза и перезапуска.
- Каждое изменение — с причиной и автором, история не редактируется.
- Настройки безопасности входа меняет только серверная команда (D-053).
- Значение вне диапазона сохранить нельзя; жёсткие пределы безопасности не обходятся настройкой.
- Изменение политики клиента не может отрезать администратора от её исправления.

## Edge cases

- Два администратора меняют одно значение одновременно.
- Значение в базе испорчено или ключ удалён из реестра.
- База недоступна в момент обновления кэша; база недоступна при старте процесса.
- Минимальная версия админки выше текущей; мусор вместо версии.
- Администратор со старой вкладкой админки после повышения минимума.
- Попытка изменить настройку безопасности через API.
- Мобильная сессия или сессия кабинета вызывает маршруты настроек.
- Текст на трёх языках с пустым языком; составное значение с лишним или отсутствующим полем.
- Изменение лимита кодов входа серверной командой вступает в силу без перезапуска.

## Не входит в задачу

- Экраны настроек в админке — TASK-034.
- Журнал действий `audit_log` и маскирование — TASK-009.
- Шаблоны уведомлений — EPIC-09; тарифы — EPIC-14.
- Фоновые задачи и очистка — TASK-008.
- Логика функций, для которых заводятся ключи (заявки, рейтинг, биллинг, ИИ и т. д.) — их задачи.

## Acceptance Criteria

- **AC-1.** Реестр содержит все ключи ARCHITECTURE 14 и групп SCREENS A-SET-01 с типом, единицей, диапазоном, умолчанием, описанием и правом изменения; ключи вне ARCHITECTURE 14 и предположения по умолчаниям перечислены в отчёте.
- **AC-2.** Администратор получает список, меняет значение с причиной, получает «было → стало», сбрасывает к умолчанию, видит историю; неверный тип и выход за диапазон отклоняются; одновременная правка даёт отказ, а не перезапись.
- **AC-3.** Изменение вступает в силу в API и worker не позже чем через 30 секунд без перезапуска; тест подтверждает это на реальном пороге (например, лимит кодов входа).
- **AC-4.** Настройки безопасности входа через API не меняются; серверная команда меняет любые настройки с записью в историю.
- **AC-5.** Коды входа, сессии, шаги входа, второй фактор и политика клиента читают значения из настроек; соответствующих переменных нет в схеме конфигурации и `.env.example`; жёсткие пределы безопасности действуют.
- **AC-6.** Политика клиента меняется без перезапуска; минимум админки выше текущей версии отклоняется; сценарий «старая вкладка админки после повышения минимумов» проходит — администратор может исправить политику.
- **AC-7.** Испорченное значение в базе не применяется и видно в журнале; при недоступной базе процесс работает на последних прочитанных значениях и не переходит молча на умолчания.
- **AC-8.** Маршруты настроек недоступны мобильной сессии и сессии кабинета (матрица предиката).
- **AC-9.** Тесты задают настройки через тот же механизм; два нестабильных теста TASK-005 стабилизированы без ослабления; `pnpm test` и `pnpm test:integration` проходят.
- **AC-10.** Контракт, OpenAPI и клиент обновлены; совместимость без трейлера; миграции обратимы; новые таблицы зарегистрированы в сверке схемы.
- **AC-11.** Коммиты по D-024 с составом в отчёте; CI на `main` зелёный, включая коммит с отчётом (номер и статус через `gh`).
- **AC-12.** ARCHITECTURE.md (4.x, 14, версия, история) и CLAUDE.md (блок 0) обновлены.

## Что должно реально работать

Запросами к API и серверной командой в dev:

- **Порог меняется на лету.** Администратор снижает дневной лимит помощника → список показывает новое значение, кто и когда → история показывает «было → стало» и причину → сброс возвращает умолчание.
- **Неверное значение.** Значение вне диапазона → отказ с понятной ошибкой, в истории ничего.
- **Одновременная правка.** Два изменения от одной версии → одно проходит, второе получает отказ.
- **Безопасность.** Изменить лимит кодов входа через API → отказ; изменить серверной командой → через ≤ 30 с новый лимит действует на `POST /auth/login-code` без перезапуска.
- **Политика клиента.** Поднять минимальную версию Android → запрос мобильного клиента старой версии получает 426 без перезапуска API → вернуть обратно. Поднять минимум админки выше текущей → отказ.
- **Чужой контекст.** Мобильная сессия и сессия кабинета → маршруты настроек отказывают.
