# TASK-008 — Фоновые задачи и дедлайны

Модель: Opus 5, High

## Цель

В worker-процессе работает надёжный механизм фоновых задач: постановка задачи в той же транзакции, что и бизнес-изменение; свиперы дедлайнов; периодические задачи по времени Алматы; повторы и мёртвая очередь; видимость состояния для оператора. Механизм сразу используется реальными задачами очистки устаревших данных входа.

## Контекст

Вторая задача EPIC-03 «Ядро платформы». На этом механизме будут построены все продуктовые таймеры: автоотмена заявки без ответа поставщика, истечение резерва, позднее закрытие, повторы списаний, напоминания, сводки модерации, сверка подписок сторов (ARCHITECTURE 13.2).

- **ARCHITECTURE 13.1 (принято):** pg-boss — очередь и cron на PostgreSQL. Правило: любой продуктовый таймер — это поле дедлайна на сущности плюс свипер раз в минуту (singleton), который выбирает просроченные строки пакетами и применяет переход. Отложенные задачи — только ускорители, не единственный источник истины.
- **ARCHITECTURE 13.3:** хранение времени — UTC; задачи с «человеческим» временем (например, 10:00) — в `Asia/Almaty`.
- **ARCHITECTURE 13.4:** пороги читаются из настроек при каждом запуске периодической задачи и при входе в состояние.
- **ARCHITECTURE 15.3:** в метриках будут глубина очереди и ошибки (сами метрики и мониторинг — TASK-009).
- **PRODUCT 10.4:** при сбое канала таймеры автоматически не продлеваются.
- **D-003:** пороги и сроки — настройки, а не константы.

## Текущее состояние

- **Worker** (`apps/api/src/worker.ts`, `worker.module.ts`) запускается отдельной командой, подключается к PostgreSQL, Redis и S3, корректно завершается по сигналу с ограничением по времени (TASK-005.A). Фоновых задач нет — на их месте заглушка ожидания (ARCHITECTURE I5).
- **Настройки** (TASK-007): реестр в `apps/api/src/modules/settings`, значения из базы с кэшем 30 с (кэш ленивый — перечитывается при обращении), история изменений, серверная команда `operator settings:*`. Администратор меняет продуктовые настройки через API, настройки безопасности входа — только серверная команда (D-053).
- **Данные, которые копятся без очистки:** `otp_challenge` (коды входа — замечание приёмки TASK-004), завершённые и истёкшие строки `session`, использованные и истёкшие шаги входа (`sign_in_step`).
- **Нет:** pg-boss в зависимостях; заявок и других сущностей с продуктовыми дедлайнами; журнала действий `audit_log` и метрик (TASK-009); экранов админки.
- Production-окружения нет.

## Требования

### 1. Очередь и worker

- **Очередь на PostgreSQL** (pg-boss, ARCHITECTURE 13.1) подключена в worker. API-процесс задачи не выполняет, но может их ставить.
- **Транзакционная постановка.** Модуль может поставить задачу в той же транзакции, что и своё изменение данных: если транзакция откатилась — задачи нет; если зафиксирована — задача обязательно выполнится.
- **Схема очереди** создаётся и обновляется управляемо, согласованно с миграциями проекта (ARCHITECTURE 4.2): не должно быть «таблицы появились сами при первом запуске» без следа в процессе миграций. Способ — на усмотрение агента, описать в ARCHITECTURE.
- **Несколько экземпляров worker** работают одновременно без двойного выполнения singleton-задач и периодических задач.
- **Остановка worker.** Выполняющиеся задачи либо завершаются в пределах ограничения по времени остановки, либо безопасно возвращаются в очередь и будут выполнены повторно. Задача не теряется и не выполняется «наполовину без следа».
- **Недоступность базы.** Worker не падает, после восстановления продолжает без перезапуска (как API в TASK-002).

### 2. Каркас задач

- **Объявление задачи** модулем: имя, обработчик, повторы (число и паузы), срок выполнения, singleton или нет. Обработчики — идемпотентные: повторное выполнение той же задачи не портит данные (правило для всех будущих задач — в ARCHITECTURE).
- **Повторы и мёртвая очередь.** Упавшая задача повторяется по правилам; исчерпавшая повторы попадает в мёртвую очередь и остаётся видимой, пока оператор не разберётся.
- **Свипер дедлайнов** — общий способ, которым будущие модули описывают «выбрать просроченные строки пакетом и применить переход»: запуск раз в минуту, singleton, пакеты ограниченного размера, строки, захваченные одним запуском, не обрабатываются параллельно другим, падение на одной строке не останавливает остальные. В этой задаче свипер проверяется на задачах очистки (требование 4) и в тестах.
- **Периодические задачи** задаются расписанием во времени `Asia/Almaty`; время из настройки (например, «час отправки») читается при каждом запуске, изменение настройки действует без перезапуска.
- **Журнал.** Старт, успех, повтор, окончательная ошибка задачи пишутся в журнал приложения с именем задачи и идентификатором; полезная нагрузка задачи в журнал не пишется (там могут быть персональные данные).

### 3. Видимость для оператора

Серверная команда оператора показывает состояние очереди (по задачам: ожидают, выполняются, упали, в мёртвой очереди, последний успешный запуск периодических задач), содержимое мёртвой очереди (без персональных данных полезной нагрузки) и позволяет повторить или удалить задачу из мёртвой очереди. Экраны админки и метрики — не в этой задаче.

### 4. Очистка устаревших данных входа

Первые реальные задачи на механизме — периодическая очистка:

- использованные, заменённые и истёкшие коды входа (`otp_challenge`);
- использованные и истёкшие шаги входа;
- завершённые и истёкшие сессии.

Сроки хранения — настройки (TASK-007, группа «Очистка», меняет администратор), по умолчанию (D-054, подтверждено Product Owner): коды входа — 7 дней после окончания действия, шаги входа — 1 день, сессии — 30 дней после завершения или истечения.

Правила:

- действующие коды, шаги и сессии не удаляются никогда;
- `phone_verification` (канал последнего подтверждения номера — основа отметки «нет WhatsApp») не удаляется;
- удаление идёт пакетами и не блокирует вход пользователей;
- удаление не нарушает лимиты входа и защиту от повторного использования refresh-токенов в пределах их сроков;
- число удалённых записей пишется в журнал (без номеров телефонов).

### 5. Тесты и документация

- Интеграционные тесты на реальной PostgreSQL: транзакционная постановка (откат и фиксация), повторы и мёртвая очередь, singleton при двух worker'ах, свипер (пакеты, падение одной строки, параллельный запуск), периодическая задача со временем из настройки и `Asia/Almaty`, остановка worker во время выполнения задачи, недоступность базы, задачи очистки (включая «действующее не удаляется»).
- Проверка корректной остановки worker в CI продолжает проходить.
- ARCHITECTURE.md: подраздел решений 4.x (схема очереди и миграции, объявление задач, свипер, идемпотентность, остановка, наблюдаемость), уточнение 13.1–13.2, ключи очистки в 14, версия и история.
- CLAUDE.md, блок 0: как в dev запустить worker, посмотреть очередь и мёртвую очередь, запустить очистку вручную или дождаться её.

## Бизнес-правила

- Продуктовый таймер — это дедлайн в данных; очередь его ускоряет, но не заменяет.
- Задача, поставленная вместе с изменением данных, выполняется тогда и только тогда, когда изменение зафиксировано.
- Время для людей — по Алматы; хранение — UTC.
- Сроки хранения — настройки; действующие данные входа не удаляются.
- Таймеры автоматически не продлеваются при сбоях (PRODUCT 10.4).

## Edge cases

- Транзакция с постановкой задачи откатилась; зафиксировалась, а worker в этот момент остановлен.
- Два worker'а одновременно; один останавливается посреди пакета свипера.
- Задача падает всегда — доходит до мёртвой очереди; оператор повторяет её после исправления.
- Периодическая задача пропустила запуск (worker был выключен) — поведение после старта описано и проверено (догоняет один раз, а не столько, сколько пропущено).
- Время запуска в настройке изменено между запусками.
- PostgreSQL недоступен во время работы worker'а и при старте.
- Очистка при сессии, у которой refresh-токен ещё в окне повторного использования.
- Очень много устаревших строк — очистка идёт пакетами, вход в это время работает.

## Не входит в задачу

- Продуктовые таймеры заявок, биллинга, напоминаний и т. д. — их задачи (здесь только механизм).
- Метрики, дашборды, алерты, `audit_log` — TASK-009.
- Экран очереди в админке.
- Очистка фото документов, диалогов, входящих вебхуков — с их задачами.
- Действие «пересчитать дедлайны незакрытых заявок» — с задачами заявок.

## Acceptance Criteria

- **AC-1.** Очередь работает в worker; схема очереди создаётся управляемо и описана в ARCHITECTURE; API может ставить задачи.
- **AC-2.** Тест: задача, поставленная в откатившейся транзакции, не выполняется; в зафиксированной — выполняется, в том числе если worker запущен после фиксации.
- **AC-3.** Тесты: повторы по правилам; исчерпавшая повторы задача в мёртвой очереди; оператор видит её и повторяет или удаляет.
- **AC-4.** Тест: при двух worker'ах singleton-задачи и периодические задачи не выполняются дважды.
- **AC-5.** Свипер: пакеты ограниченного размера, падение одной строки не останавливает остальные, параллельные запуски не обрабатывают одну строку дважды — подтверждено тестами.
- **AC-6.** Периодическая задача запускается по времени `Asia/Almaty`, время из настройки меняется без перезапуска; поведение после пропущенных запусков описано и проверено.
- **AC-7.** Остановка worker во время задачи: задача завершается или возвращается и выполняется повторно; worker завершается в пределах ограничения; проверка остановки в CI проходит.
- **AC-8.** Недоступность PostgreSQL: worker не падает и продолжает после восстановления без перезапуска.
- **AC-9.** Очистка: устаревшие коды, шаги и сессии удаляются по срокам из настроек; действующие и `phone_verification` не затрагиваются; работает пакетами; число удалённых — в журнале без номеров.
- **AC-10.** В журнале нет полезной нагрузки задач, номеров телефонов, кодов и токенов (проверка перехвата вывода покрывает новые тесты).
- **AC-11.** Новые ключи в реестре настроек; миграции обратимы; новые таблицы зарегистрированы в сверке схемы (или обосновано, почему таблицы очереди в неё не входят); контракт API — только аддитивно, если менялся.
- **AC-12.** Существующие тесты проходят без ослабления; коммиты по D-024 с составом в отчёте; CI на `main` зелёный, включая коммит с отчётом (номер и статус через `gh`).
- **AC-13.** ARCHITECTURE.md (4.x, 13, 14, версия, история) и CLAUDE.md (блок 0) обновлены.

## Что должно реально работать

В dev (API, worker, серверная команда):

- **Очистка.** Завести устаревшие коды входа и завершённые сессии (обычным входом и выходом, при необходимости — уменьшив срок хранения настройкой) → дождаться или запустить очистку → устаревшее удалено, действующая сессия продолжает работать, вход по коду работает.
- **Мёртвая очередь.** Поставить тестовую задачу, которая всегда падает (способ — на усмотрение агента, только в dev и тестах) → после повторов она в мёртвой очереди → оператор видит её без персональных данных → повторяет или удаляет.
- **Два worker'а.** Запустить два worker'а → периодическая очистка выполняется один раз за запуск.
- **Остановка.** Остановить worker во время выполнения задачи → после запуска задача выполнена один раз.
- **База упала.** Остановить PostgreSQL при работающем worker'е → worker жив → запустить базу → задачи снова выполняются.
