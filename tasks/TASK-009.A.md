# TASK-009.A — Исправления по приёмке TASK-009

Модель: Opus 5, High

## Цель

Закрыть утечки персональных данных и дефекты, найденные при приёмке TASK-009. Корректно реализованное в TASK-009 не переделывается, продуктовое поведение не меняется.

## Контекст

TASK-009 реализована (ARCHITECTURE.md 0.16, раздел 4.13, I120–I130), CI зелёный. Проверка кода при приёмке нашла, что санитайзер в реальных случаях пропускает персональные данные во внешний мониторинг и журнал. Это нарушает PRODUCT 17 и решение D-011: персональные данные не покидают РК.

Найдено и подтверждено:

1. **Значения SQL-запроса уходят в мониторинг.** Drizzle формирует текст ошибки как `params: a,b,c` без скобок (`drizzle-orm/errors.js`), а правило `QUERY_PARAMS` (`apps/api/src/observability/sanitizer.ts`) ждёт `params: [ … ]`; правило пар «ключ=значение» убирает только первое значение. HTTP-фильтр предварительно чистит ошибку (`withoutQueryParameters`), но отправка из упавшей задачи (`jobs/job-runner.service.ts`, `captureException(error, …)`) и из необработанной ошибки (`common/shutdown/unhandled-failures.ts`) передаёт исходную ошибку. Пример: задача падает на запросе с параметрами `(uuid, "Айгерим Касымова", "позвонить +77011234567.")` — имя и номер доходят до приёмника. Unit-тест проверяет формат со скобками, которого Drizzle не выдаёт.
2. **Номер, за которым идёт точка или дефис, не маскируется.** В правиле `PHONE` после номера запрещены `.` и `-`: «Позвонить +77011234567.» уходит как есть. Правило «номер в журналах — только маской» нарушено.
3. **Постраничный вывод журнала действий теряет записи.** Курсор хранит время с точностью до миллисекунд, а в базе — микросекунды; запись между `X.123` и `X.123456` не попадает ни на одну страницу. Особенно вероятно для нескольких записей одной транзакции.
4. **`/metrics` открыт по умолчанию и в production.** `METRICS_ENABLED` по умолчанию включён, `METRICS_TOKEN` необязателен; каждый анонимный запрос выполняет запросы к базе. Токен сравнивается не за постоянное время.
5. **Коды прочих 4xx не исправлены.** TASK-009 требовала: 405, 413, 415 и подобные получают код по смыслу, а не `VALIDATION_ERROR`. Для 413 и 415 оставлен `VALIDATION_ERROR`, прочие 4xx (406, 408, 410, 414…) попадают в него же; отчёт утверждает обратное.
6. **Строка «Action recorded» пишется в журнал приложения до фиксации транзакции** — после отката остаётся запись о несуществующем действии (то же замечание TASK-005, в новом месте).

Мелкие находки:

- ошибки PostgreSQL с деталями вида `Key (display_name)=(Иван Петров)` — значения в деталях не очищаются;
- сжатый IPv6 (`2a02:2168:8a1f::1`) не маскируется; ключи `set-cookie`, `x-api-key`, `proxy-authorization` не убираются;
- дата со временем (`2026-09-18 03:14:33`) принимается за телефон и IPv6;
- логгер: объект первым аргументом становится `[object Object]`; `String(message)` вне защиты — бросающий `toString` роняет вызов;
- при сбое старта `main.ts` и `worker.ts` выводят ошибку через `console.error` мимо санитайзера;
- после `uncaughtException` процесс продолжает работу в неопределённом состоянии;
- комментарий реестра метрик обещает проверку меток, которой нет; при сбое сбора остаются старые значения; `_total` у метрик типа gauge.

## Текущее состояние

- Санитайзер — `apps/api/src/observability/sanitizer.ts`; мониторинг — `error-reporter.service.ts`; метрики — `metrics.controller.ts`, `metrics.service.ts`, `metrics-registry.ts`; журнал действий — `audit-log.service.ts`, `audit-log.store.ts`, `GET /admin/audit-log`; журнал приложения — `common/logging/json-logger.service.ts`; коды ошибок — `common/errors/http-exception.filter.ts`.
- Интеграционный тест «перехват отправки» (`observability.integration.test.ts`) проверяет весь принятый поток, но только для HTTP 500.
- Перехват вывода всех интеграционных тестов (`testing/output-capture.ts`) работает.

## Требования

1. **Ничего из SQL-запроса наружу.** Ни один путь отправки в мониторинг и в журнал не передаёт значения параметров и детали ошибок базы. Очистка не должна зависеть от того, вспомнил ли вызывающий код предварительно почистить ошибку; способ — на усмотрение агента. Фикстуры тестов — в реальном формате Drizzle и PostgreSQL (включая детали нарушения ограничений).
2. **Номер в любом месте текста** маскируется, в том числе перед точкой, запятой, дефисом, скобкой, в конце строки и склеенный с буквами (например, `user_77011234567`). Идентификаторы (UUID, числовые id) при этом не портятся; даты и время не принимаются за номер или IP.
3. **Остальные пропуски санитайзера:** сжатый IPv6; ключи `set-cookie`, `x-api-key`, `proxy-authorization` и подобные.
4. **Постраничный вывод журнала действий** не теряет и не повторяет записи, включая записи одной транзакции с одинаковым временем.
5. **Метрики.** Вне development и test `/metrics` не открывается без токена: либо метрики выключены по умолчанию, либо без токена процесс не стартует — выбор описать в ARCHITECTURE. Токен сравнивается за постоянное время. Комментарии реестра соответствуют коду; при сбое сбора не отдаются устаревшие значения как свежие; имена метрик соответствуют их типу.
6. **Коды 4xx по смыслу.** 405, 406, 408, 410, 413, 414, 415 и прочие 4xx, не относящиеся к валидации, получают собственные коды ошибок; `VALIDATION_ERROR` — только для ошибок валидации. Изменение контракта — аддитивное.
7. **Журнал приложения после фиксации.** Строка о записи в журнал действий пишется только после фиксации транзакции.
8. **Логгер.** Объект первым аргументом сериализуется; сбой преобразования сообщения не роняет вызов. Ошибки старта API и worker выводятся через санитайзер.
9. **Необработанное исключение.** После `uncaughtException` процесс отправляет очищенное событие, пишет в журнал и завершается с ненулевым кодом в пределах ограничения остановки (перезапуск — забота окружения); поведение для `unhandledRejection` — описать в ARCHITECTURE.
10. **Тесты,** которых не хватало: отправка в мониторинг из упавшей задачи и из необработанной ошибки проверяется перехватом всего принятого потока; сбой записи в журнал действий откатывает само действие; страницы журнала действий вместе дают все записи без пропусков и повторов.
11. **Документация.** ARCHITECTURE.md (версия, история, решения); исправление утверждений отчёта TASK-009 о кодах 4xx.

## Бизнес-правила

- Персональные данные не покидают РК: во внешний мониторинг уходит только очищенное (PRODUCT 17, D-011).
- Номер в журналах — только маской.
- Администратор видит в журнале действий все записи.
- Служебные данные системы не доступны анонимно.

## Edge cases

- Задача падает на запросе с именем, телефоном и адресом в параметрах; то же при необработанном отказе.
- Нарушение уникальности с деталями `Key (phone)=(…)` и `Key (display_name)=(…)`.
- Номер в конце предложения, в скобках, через дефис, склеенный с буквами; UUID и длинные числовые id рядом с номером.
- Десять записей журнала действий в одной транзакции при размере страницы 3.
- `/metrics` в production без токена; с неверным токеном.
- Запрос с методом, который маршрут не поддерживает; слишком большое тело; неподдерживаемый тип содержимого.
- `uncaughtException` во время обработки запроса.

## Не входит в задачу

- Экран журнала действий — TASK-034.
- Реальный мониторинг, дашборды, алерты — TASK-055.
- Маскирование на клиентах.

## Acceptance Criteria

- **AC-1.** Тесты с фикстурами в реальном формате Drizzle и PostgreSQL: значения параметров и детали ошибок базы не попадают ни в журнал, ни в поток мониторинга — для HTTP, упавшей задачи и необработанной ошибки.
- **AC-2.** Тесты: номер маскируется во всех позициях из edge cases; UUID, id, даты и время не искажаются.
- **AC-3.** Тесты: сжатый IPv6 и заголовки с секретами убираются.
- **AC-4.** Тест: страницы журнала действий (включая записи одной транзакции) вместе дают все записи ровно один раз.
- **AC-5.** Вне development и test `/metrics` без токена недоступен (или процесс не стартует — по выбранному способу); неверный токен — отказ; сравнение за постоянное время — тесты.
- **AC-6.** Тесты: 405, 413, 415 и прочие 4xx получают собственные коды; контракт совместим без трейлера.
- **AC-7.** Тест: после отката транзакции в журнале приложения нет строки о записи действия.
- **AC-8.** Тесты логгера (объект первым аргументом, бросающий `toString`); ошибки старта проходят через санитайзер.
- **AC-9.** Тест: `uncaughtException` — очищенное событие, запись в журнал, завершение процесса.
- **AC-10.** Тест: сбой записи в журнал действий откатывает действие.
- **AC-11.** Перехват вывода всех интеграционных тестов не находит номеров, кодов и токенов; существующие тесты проходят без ослабления.
- **AC-12.** Коммиты по D-024 с составом в отчёте; CI на `main` зелёный, включая коммит с отчётом (номер и статус через `gh`).
- **AC-13.** ARCHITECTURE.md обновлён; в отчёте TASK-009 исправлено утверждение о кодах 4xx.

## Что должно реально работать

В dev:

- Вызвать падение фоновой задачи на запросе с телефоном и именем в параметрах → в тестовом приёмнике мониторинга и в журнале нет ни имени, ни номера.
- Записать в журнал строку с номером в конце предложения → номер маской.
- Создать много записей журнала действий одной операцией → пролистать журнал постранично → все записи на месте, без повторов.
- Запустить API с настройками production без токена метрик → `/metrics` недоступен (или процесс не стартует).
- Отправить `DELETE` на маршрут, который его не поддерживает, и слишком большое тело → коды ошибок по смыслу.
