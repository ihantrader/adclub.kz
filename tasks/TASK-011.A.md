# TASK-011.A — Доводка по приёмке TASK-011 и гонка расписания фоновых задач

Модель: Opus 5, High

## Цель

Закрыть замечания приёмки TASK-011 и реальную гонку в синхронизации расписаний фоновых задач (TASK-008), из-за которой краснеет CI. Корректно реализованное не переделывается, продуктовое поведение, кроме описанного ниже, не меняется.

## Контекст

TASK-011 принята (PASS WITH NOTES). При приёмке найдено:

1. **Дубль «задним числом» блокирует несвязанные правки.** Проверка «такой товар уже есть» (`assertNoSameProduct`, `catalog-items.service.ts`) выполняется при любой записи значений позиции и для каждой позиции в дозаполнении. Если после архивирования характеристики или снятия признака «участвует в полноте» два товара стали одинаковыми (структура дубли не проверяет, ARCHITECTURE I160), то запись любого значения такой позиции (даже не определяющего идентичность) получает 409 `CATALOG_ITEM_DUPLICATE`, а любой запрос дозаполнения, в котором есть такая позиция, отклоняется целиком. Администратор при этом не узнаёт, что такие пары появились.
2. **Тестовый файл с сырым байтом NUL.** `apps/api/src/modules/catalog/catalog-values.test.ts` содержит литеральный NUL вместо escape-последовательности — git считает файл бинарным, его изменения не видны на ревью.
3. **500 вместо 409 в редком случае.** При нарушении уникальности написания бренда или артикула, если конкурирующая транзакция откатилась, клиент получает необработанную ошибку.

Из прогона CI TASK-011 (первая попытка run 35433317491 упала):

4. **Гонка синхронизации расписаний.** Каждый worker раз в 15 секунд пересобирает общее расписание периодических задач по своему кэшу настроек (кэш может отставать до 30 секунд, TASK-007). После изменения времени запуска (например, `billing_notify_hour`) разные worker'ы записывают в общее расписание то новое, то старое время, пока их кэши не обновятся. Если это совпадёт с минутой запуска, задача может быть пропущена или выполнена в старое время. Тест TASK-008 «reads the Almaty time from the setting at every sync, without a restart» прямо проверяет «nothing flips back» и изредка ловит это — это реальный дефект, а не нестабильность теста.

## Текущее состояние

- Позиции справочника — `apps/api/src/modules/catalog` (TASK-011, ARCHITECTURE 4.17, I157–I168): идентичность товара по характеристикам — совпадение всех заполненных характеристик «участвует в полноте» в той же категории и бренде, блокировка `productIdentityLock`; полнота пересчитывается сервисом; дозаполнение всё-или-ничего; ответ создания характеристики несёт `itemsWithoutValue`.
- Фоновые задачи — `apps/api/src/jobs` (TASK-008, ARCHITECTURE 4.12): `JobRunner.syncSchedules` раз в 15 с, расписание pg-boss общее для всех worker'ов; настройки читаются через `AppSettings` с кэшем до 30 с.
- CI на `main` зелёный после перезапуска (run 35433317491, attempt 2).

## Требования

1. **Проверка дубля только при изменении идентичности.** Отказ «такой товар уже есть» возникает, только если изменение затрагивает то, что определяет идентичность товара (бренд, категория, значения характеристик «участвует в полноте»), и в результате позиция совпала бы с другой. Правка остального (другие характеристики, название, состояние) проходит, даже если позиция уже совпадает с другой. То же для дозаполнения: ячейка, не затрагивающая идентичность, не отклоняется из-за существующего совпадения.
2. **Администратор узнаёт о появившихся совпадениях.** Изменение структуры, после которого товары стали одинаковыми (архивирование или восстановление характеристики, снятие или установка признака «участвует в полноте», архивирование варианта списка, если оно влияет), не отклоняется, но ответ сообщает число таких совпадений; в списке позиций есть отбор «совпадает с другой позицией». Правило «совпадение не считается дублем, пока не изменена идентичность» описать в ARCHITECTURE.
3. **Тестовый файл** хранится как текст: NUL — escape-последовательностью.
4. **Нарушение уникальности** написания бренда и артикула всегда отвечает 409 с понятным кодом, в том числе при откате конкурирующей транзакции.
5. **Расписание без переключений.** После изменения настройки времени запуска все worker'ы записывают в общее расписание одно и то же значение; расписание не возвращается к прежнему времени ни на одном шаге синхронизации. Способ — на усмотрение агента (например, синхронизация по свежему значению из базы, а не из кэша, или одна точка синхронизации); описать в ARCHITECTURE. Тест TASK-008 «reads the Almaty time…» проходит надёжно без ослабления проверки «nothing flips back»; добавить тест, который воспроизводит гонку (два worker'а, у одного кэш устарел) и падает на прежнем коде.
6. **Документация:** ARCHITECTURE.md (версия, история, решения).

## Бизнес-правила

- Появившееся совпадение товаров не мешает работать с позицией; администратор видит такие пары и решает сам.
- Изменение времени запуска фоновой задачи применяется ко всем worker'ам одинаково.

## Edge cases

- Два масла стали одинаковыми после архивирования «Допуска» → правка «Примечания» одного из них проходит; попытка изменить вязкость одного так, что он совпадёт с третьим, — отказ.
- Дозаполнение категории, в которой есть совпадающая пара, ячейкой, не затрагивающей идентичность.
- Восстановление «Допуска» — совпадение исчезает, счётчик и отбор это отражают.
- Два worker'а: один прочитал новую настройку, у другого кэш устарел — расписание не переключается обратно.
- Одновременная регистрация одного написания бренда двумя запросами, один из которых откатывается.

## Не входит в задачу

- Слияние дублей позиций (перенос предложений, ссылок) — позже, если понадобится.
- Индексы для поиска по подстроке артикула и названия — при росте справочника (EPIC-15).
- Повторная проверка сохранённых значений при сужении границ числа.

## Acceptance Criteria

- **AC-1.** Тесты: правка не определяющего идентичность значения позиции, совпадающей с другой, проходит; изменение идентичности в совпадение — отказ; дозаполнение по правилу требования 1.
- **AC-2.** Тесты: изменение структуры, создавшее совпадения, возвращает их число; отбор «совпадает с другой позицией» показывает эти позиции и перестаёт показывать после устранения.
- **AC-3.** `catalog-values.test.ts` — текстовый файл (git diff показывает содержимое).
- **AC-4.** Тест: нарушение уникальности при откате конкурирующей транзакции — 409.
- **AC-5.** Тест, воспроизводящий гонку расписания, падает на прежнем коде и проходит на новом; тест TASK-008 «reads the Almaty time…» без ослабления — 10/10 прогонов.
- **AC-6.** Контракт — аддитивно, совместимость без трейлера; существующие тесты не ослаблены; коммиты по D-024 с составом в отчёте; CI на `main` зелёный с первой попытки, включая коммит с отчётом (номер и статус через `gh`).
- **AC-7.** ARCHITECTURE.md обновлён.

## Что должно реально работать

В dev:

- Архивировать «Допуск» у «Моторных масел» → ответ сообщает число совпадений → отбор «совпадает с другой позицией» показывает масла → изменить «Объём» одного из них не получится, если он совпадёт с третьим, но правка названия проходит → восстановить «Допуск» → отбор пуст.
- Запустить два worker'а → изменить время ежедневной задачи серверной командой → `jobs:status` показывает новое время и не возвращается к старому.
