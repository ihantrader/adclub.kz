# TASK-020.A — Доводка каталога по приёмке TASK-020

Модель: Opus 5, High

## Цель

Закрыть обход правила «название поставщика скрыто без клубного доступа» через свободный текст гарантии, устранить расхождение между правилом витрины и фактической выдачей каталога, сделать страницы сортировки «Рекомендуемые» устойчивыми и ограничить выкачивание каталога. Продуктовое поведение, кроме перечисленного, не меняется.

## Контекст

TASK-020 принята. Проверка кода при приёмке нашла:

1. **Обход политики видимости через текст гарантии.** `warrantyText` — свободный текст поставщика, он отдаётся гостю как есть (`showcase.service.ts`, контракт `contracts/showcase.ts`). Поставщик пишет в него «Автомаркет, ул. Райымбека 200, +7 705 555 01 01» — и любой гость видит, кто поставщик и где он. Правило D-005 держится только на добросовестности поставщика.
2. **Правило витрины и фактическая выдача расходятся.** Каталог отбрасывает предложение, если дата получения не рассчиталась (`showcase-offers.ts`), а `receiptDate` возвращает «нет рабочего дня» не только при пустых часах, но и когда нерабочие даты закрывают весь горизонт (60 дней). Правило `offerVisibility` и его SQL-двойник смотрят только на часы. Поставщик, закрывший два месяца на инвентаризацию, пропадает с витрины, а в «Моих предложениях» видит `visible: true` без причины — то есть D-060 «поставщик видит причину» не выполняется.
3. **Страницы сортировки «Рекомендуемые» могут пропускать и повторять позиции.** Оценка считается относительно минимальной цены текущей страницы, поэтому при изменении данных или весов между страницами масштаб меняется и порядок может перевернуться. Для «Дешевле» и «Быстрее» ключ абсолютный — там всё верно.
4. **Каталог не ограничен по частоте** (`/catalog/categories/{id}/items`, `/catalog/items/{id}`): конкурент выкачивает весь каталог с ценами. Ограничение должно быть щедрым — за одним адресом мобильного оператора сидит много настоящих пользователей.

Мелочи оттуда же:

5. Правило «услуги показываются только в выбранном городе» применяется в списке и карточке, но не к аналогам — правило перестало быть в одном месте.
6. При замене выдачи клубного доступа прежняя запись закрывается с причиной **новой** выдачи — в истории причина по смыслу неверна.

## Требования

### 1. Гарантия не раскрывает поставщика

- **Без клубного доступа** зритель видит гарантию только в виде срока (месяцев); свободный текст гарантии таким зрителям не отдаётся вовсе (поле отсутствует, как остальные скрытые поля).
- **С клубным доступом** текст гарантии виден.
- При сохранении предложения текст гарантии проверяется на очевидные признаки самоназвания: телефоны, адреса сайтов и ссылки, e-mail. Найдено — понятная ошибка поставщику с объяснением правила («название и контакты компании в гарантии указывать нельзя, пользователь увидит их после принятия заявки»). Проверка — на сервере, в одном месте, с тестами; существующие значения, не проходящие проверку, при следующем сохранении отклоняются (поведение уже сохранённых описать).
- Это правило и его причина записываются в ARCHITECTURE рядом с политикой видимости.

### 2. Одно правило витрины

- Причина «нет рабочего дня в обозримом будущем» (включая случай, когда всё закрыто нерабочими датами) должна одинаково учитываться и в правиле видимости, и в SQL-двойнике, и в выдаче каталога: предложение либо везде видно, либо везде скрыто **с причиной, которую видит поставщик**.
- Тест сверяет три места на одних и тех же данных, включая случай «нерабочие даты закрывают весь горизонт».

### 3. Устойчивые страницы «Рекомендуемых»

- Постраничный вывод сортировки «Рекомендуемые» не пропускает и не повторяет позиции, если между страницами данные изменились (появилось или исчезло предложение, изменились веса). Способ — на усмотрение агента (например, абсолютный ключ сортировки), описать в ARCHITECTURE.
- Тест меняет данные между страницами и проверяет, что каждая позиция встретилась ровно один раз.

### 4. Ограничение частоты каталога

- Маршруты списка и карточки каталога ограничены по частоте общим механизмом: пределы — настройки, щедрые по умолчанию (обычный человек не должен их достигать даже при активном пролистывании), с учётом сети IPv6 и доверенного прокси.
- Для запросов с сессией предел считается по учётной записи, а не только по адресу, — иначе пользователи за одним адресом мешают друг другу. Решение описать.
- Недоступность Redis не мешает чтению каталога (как сейчас).

### 5. Мелочи

- Правило «услуги только в выбранном городе» применяется и к аналогам — в одном месте.
- При замене выдачи клубного доступа прежняя запись закрывается с причиной, отражающей замену, а не причиной новой выдачи.

### 6. Документация

- ARCHITECTURE.md: политика гарантии, единое правило витрины с причинами, устойчивость страниц, ограничение частоты каталога; версия и история.
- CLAUDE.md, блок 0 — если меняются команды и проверки в dev.

## Бизнес-правила

- Без клубного доступа зритель не должен узнать, кто поставщик, ни одним полем ответа.
- Предложение либо видно на витрине, либо нет — и поставщик всегда знает причину.
- Каталог доступен гостю, но не предназначен для выгрузки целиком.

## Edge cases

- Текст гарантии с номером в разных написаниях, со ссылкой, с e-mail, с названием компании без контактов (описать, что проверяем и чего не ловим).
- Предложение с уже сохранённым текстом, который новая проверка не пропускает.
- Поставщик закрыл нерабочими датами весь горизонт; открыл часть дней обратно.
- Страницы «Рекомендуемых» при исчезнувшем самом дешёвом предложении и при смене весов.
- Много запросов каталога с одного адреса от разных пользователей с сессиями.

## Не входит в задачу

- Изменение правил видимости поставщика в остальном (TASK-020 принята).
- Модерация текста гарантии человеком и ИИ-проверка — если понадобится, отдельной задачей.
- Заявки — TASK-021.

## Acceptance Criteria

- **AC-1.** Без клубного доступа текст гарантии отсутствует в ответе (тест «поле отсутствует для роли»), с доступом — присутствует; сохранение текста с телефоном, ссылкой или e-mail отклоняется — тесты.
- **AC-2.** Правило видимости, SQL-двойник и выдача каталога совпадают, включая «нерабочие даты закрыли горизонт»; поставщик видит причину — тесты.
- **AC-3.** Страницы «Рекомендуемых» не теряют и не повторяют позиции при изменении данных между страницами — тест.
- **AC-4.** Маршруты каталога ограничены по частоте с настройками; сессия считается по учётной записи; чтение каталога работает при недоступном Redis — тесты.
- **AC-5.** Услуги вне выбранного города не попадают и в аналоги; замена выдачи клубного доступа пишет верную причину — тесты.
- **AC-6.** Контракт совместим (изменение выдачи гарантии — аддитивное или обосновано трейлером); существующие тесты не ослаблены; перехват вывода чист.
- **AC-7.** Коммиты по D-024 с составом в отчёте; CI на `main` зелёный с первой попытки, включая коммит с отчётом (номер и статус через `gh`).
- **AC-8.** ARCHITECTURE.md обновлён.

## Что должно реально работать

В dev:

- Поставщик пытается сохранить гарантию «Автомаркет, +7 705 555 01 01» → отказ с объяснением; сохраняет «12 месяцев по чеку» → сохранилось.
- Гость видит у предложения срок гарантии, но не текст; пользователь с клубным доступом — текст.
- Поставщик закрывает нерабочими датами два месяца → предложение пропадает с витрины, и в «Моих предложениях» видна причина; открывает даты обратно → предложение снова на витрине.
- Пролистать список «Рекомендуемые», между страницами снять самое дешёвое предложение → ни одна позиция не пропала и не повторилась.
- Много запросов каталога подряд с одного адреса → 429 после щедрого предела; обычное пролистывание предела не достигает.
