# TASK REPORT — TASK-021

## Status
COMPLETED

## Result
- **Заявка на товар в наличии создаётся.** `POST /orders`: пользователь с клубным доступом (`ClubAccess`, D-059) оформляет заявку на предложение, видимое на витрине (одно правило витрины TASK-018/020.A): количество (по умолчанию 1, предел — настройка `order_max_quantity`), способ получения из доступных у предложения, необязательный комментарий. Гость — 401 `AUTH_REQUIRED`, без клубного доступа — 403 `SUBSCRIPTION_REQUIRED`; невидимое/несуществующее предложение — одинаковый 409 `ORDER_OFFER_UNAVAILABLE`; «под заказ» — 409 `ORDER_KIND_NOT_SUPPORTED` (EPIC-13); нет такого способа получения — 409; цена не та, что видел пользователь (`expectedPrice`), — 409 `ORDER_PRICE_CHANGED`; вторая активная заявка на то же предложение — 409 `ORDER_DUPLICATE_ACTIVE` (подтверждается `allowAnotherActive`). Заявка хранит **снимок предложения** (`OfferSnapshots.take` TASK-018 в той же транзакции), итог = цена × количество (D-033), человекочитаемый номер (`№ 1001`…), **код подтверждения** (шесть цифр, уникален среди активных заявок) и **содержимое QR** (`ADCLUB-ORDER:<128 бит>`), срок ответа `respondBy`. Частота создания ограничена на пользователя (`order_create_per_account`, 20 в час); повтор той же заявки (`idempotencyKey`) возвращает ту же заявку и лимит не тратит.
- **Автомат состояний.** `created → accepted → ready → completed`; `cancelled_by_user`, `declined_by_supplier`, `response_expired`, `reserve_expired`. Таблица переходов — одна функция `orderTransition` в `@adclub/domain`; каждый переход — **условное обновление** (статус + версия + срок) и запись в журнал заявки в той же транзакции; проигравший гонку решает заново. Два сотрудника одновременно — выигрывает один, второй получает 409 `ORDER_STATE_CONFLICT` с тем, кто и что уже сделал («принял Марат»), и его нажатие пишется как `late_action_ignored`. Отмена пользователем — до выдачи, в том числе после принятия; отказ поставщика — из новой, принятой и готовой, с необязательной причиной (пользователю не видна); при «нет в наличии» ответ предлагает снять предложение (`withdrawOffer`). «Выдана» (`close`) есть в таблице (из «принята» и «готова», D-040), действие — TASK-022. Конечные статусы необратимы. Повтор своего же действия — 200 без новой записи.
- **Сроки.** Срок ответа — `supplier_response_hours` от создания; без ответа — `response_expired` с событием «нет ответа» (`expire_no_response`). Резерв самовывоза — `pickup_reserve_hours` от момента, когда товар можно получить по часам точки (`receiptDate` TASK-018); «готова» начинает резерв заново, не короче; за `reserve_warning_hours` — заметка `reserve_expiring`; по истечении — `reserve_expired`. Применяет один свипер `orders.apply-deadlines` (каркас TASK-008) пакетами, идемпотентно; выключенный на часы worker применяет всё наступившее один раз. Прошедший, но ещё не обработанный срок применяется и перед действием человека. Выставленные сроки изменение настроек не пересчитывает.
- **Что видит каждая сторона** (одно место — `order-views.ts`). Пользователь: свои заявки, условия снимка, поставщик по названию, код и QR (пока заявка активна), после принятия — адрес точки, часы, нерабочие даты и телефон поставщика (D-026), ход заявки без имён и причин. Поставщик: заявки своей компании; телефон покупателя — только в карточке и только после принятия этой заявки; журнал с именами сотрудников; кода и QR нет. Администратор: любые заявки с отборами (статус, поставщик, период, номер, тестовые отдельно), покупатель, журнал с актором; кода и QR нет.
- **Тестовые заявки:** заявка сотрудника у своей компании — `isTest: true`, в списке администратора по умолчанию скрыта (`test=only|include`).

## Technical Decisions
Внесены в ARCHITECTURE.md, раздел 4.31:
- I307 — таблица `customer_order` вместо `order` (ORDER — зарезервированное слово SQL); журнал `order_event` только на добавление.
- I308 — два статуса истечения (`response_expired`, `reserve_expired`) вместо одного `expired` из 6.1: так формулирует TASK-021, у них разные тексты (M-ORD-03), и позднее закрытие TASK-022 допустимо только для истёкшего резерва. Отказ поставщика — и из «готова» (SCREENS S-ORD-02).
- I309 — действия сотрудника требуют `expectedVersion` (иначе «Отказать» на новой заявке сработал бы поверх одновременного принятия коллеги); отмена пользователя версии не требует — одновременные «Отменить» и «Принять» дают однозначный исход (либо принятие, потом отмена, либо отмена и отказ принятию).
- I310 — прошедший срок применяется перед действием человека (срок — его время, не задержка свипера).
- I311 — идемпотентность создания ключом приложения `idempotencyKey` (уникальный ключ в базе) и повторного действия тем же человеком.
- I313 — код из шести цифр (диктуется и набирается на любой клавиатуре; среди цифр нет похожих символов), уникален среди активных заявок, при совпадении разыгрывается заново; хранится как есть (пользователь должен видеть его снова), отдаётся только пользователю.
- I315 — резерв при принятии считается от даты получения по расписанию точки, «готова» начинает его заново, не сокращая; доставке резерв не ставится.
- I317 — имени покупателя поставщик не видит (профиля с именем пока нет); открытый при принятии телефон остаётся в карточке и после отмены.
- I318 — раскрытие телефона пишется и в журнал действий (`order.phone_revealed`), без номера телефона.
- I319 — без Redis заявка создаётся (лимит не считается), без PostgreSQL — 503.
