# TASK-023.A — Надёжное объектное хранилище для dev и CI (долг T-8)

Модель: Sonnet 5, Medium

## Цель

Сделать так, чтобы проверки в CI падали только из-за кода. Сейчас набор фотографий (TASK-013) поднимает S3-совместимый сервер из замороженного репозитория образов и время от времени отвечает 503 на загрузке — два прогона TASK-023 покраснели именно так, ни один из них не был связан с задачей. Это мешает каждой следующей задаче и делает критерий «CI зелёный с первой попытки» нечестным.

## Контекст

- TASK-022 (вне задачи, коммит `e570f7a`): собственные образы MinIO (`quay.io/minio/minio` и `minio/minio`) перестали отдаваться без учётной записи — CI не мог запустить контейнер вовсе. Образ заменён на ту же MinIO в сборке Bitnami из репозитория `bitnamilegacy`, закреплён по версии; решение — ARCHITECTURE I339.
- TASK-023: два прогона на `main` упали на наборе фотографий — `SERVICE_UNAVAILABLE` («The file storage is temporarily unavailable») на загрузке, каждый раз в другом тесте (прогоны 36152424612 и 36153651818). Третий прогон того же кода — зелёный. То есть контейнер стартует, но не всегда готов к моменту первого обращения, либо отказывает под нагрузкой.
- Там же (коммит `7516b25`, вне задачи) выяснилось, что `PhotoStorage.put` глотал причину отказа (`catch {}`); теперь причина пишется в лог — этим и надо воспользоваться, чтобы узнать, что именно отвечает хранилище.
- Долг **T-8** в `PROJECT_STATE.md`: постоянный источник S3-сервера для dev и тестов не выбран.

## Текущее состояние

- `infra/docker/compose.dev.yml` — сервис `minio` (образ `bitnamilegacy/minio:2025.7.23-debian-12-r5`, `user: root`, бакет из `MINIO_DEFAULT_BUCKETS`, данные в `/bitnami/minio/data`).
- `apps/api/src/modules/catalog/catalog-photos.integration.test.ts` — набор из 31 теста на настоящем хранилище через Testcontainers.
- `apps/api/src/modules/catalog/photo-storage.ts` — работа с хранилищем, подписанные ссылки, отказ 503 `SERVICE_UNAVAILABLE` с `retryable: true`.
- CI — один workflow, шаг `Integration test` поднимает все контейнеры набора.

## Требования

### 1. Найти настоящую причину 503

- По логам упавших прогонов и по воспроизведению локально (повторный запуск набора фотографий подряд, желательно несколько раз) определить, что именно отвечает хранилище: контейнер ещё не готов, бакета ещё нет, исчерпаны соединения, нехватка памяти или диска у раннера, что-то ещё.
- Вывод — в отчёт фактом (строка лога, код ответа), а не предположением.

### 2. Убрать причину

Решение выбирает агент; ориентиры в порядке предпочтения:

- дождаться настоящей готовности сервера и **существования бакета** перед первым тестом (проверка готовности контейнера, а не пауза);
- закрепить источник образа, который отдаётся без учётной записи и не заморожен: либо другой S3-совместимый сервер для dev и тестов, либо собственное зеркало образа;
- если отказ приходит под нагрузкой — устранить причину (соединения, ресурсы), а не прятать её повтором в тесте.

**Чего делать нельзя:** ослаблять или пропускать тесты фотографий, оборачивать их в «повторить при падении», подменять хранилище заглушкой — набор ценен именно тем, что работает с настоящим S3.

### 3. Доказать устойчивость

- Набор фотографий проходит **пять запусков подряд** локально без единого падения — вывод в отчёт.
- Полный `pnpm test:integration` в CI зелёный на коммите задачи с первой попытки.

### 4. Долг T-8

- Если выбран постоянный источник — сказать в отчёте, что долг T-8 закрыт и почему источник постоянный (кто его публикует, обновляется ли).
- Если источник остаётся временным — честно сказать, что T-8 остаётся, и что именно сделано, чтобы прогоны не падали.

### 5. Документация

- ARCHITECTURE.md — решение об источнике хранилища для dev и тестов и о проверке готовности (обновить I339, если оно меняется); версия и история.
- CLAUDE.md, блок 0 — если меняются команды запуска dev.
- `.env.example` — если меняются переменные.

## Не входит в задачу

- Production-хранилище (Servercore S3) и его настройка — TASK-055.
- Любые изменения в логике фотографий, подписанных ссылок и фоновых задач TASK-013.
- Прочие нестабильные тесты, если такие найдутся, — назвать в отчёте, не чинить здесь.

## Acceptance Criteria

- **AC-1.** Причина отказов названа фактом (лог, код ответа), а не догадкой.
- **AC-2.** Причина устранена; тесты фотографий не ослаблены и не пропускаются (diff это показывает).
- **AC-3.** Пять запусков набора фотографий подряд локально — без падений; вывод в отчёте.
- **AC-4.** CI на `main` зелёный с первой попытки, включая коммит с отчётом (номера прогонов через `gh`).
- **AC-5.** Состояние долга T-8 названо честно: закрыт или остаётся, с причиной.
- **AC-6.** ARCHITECTURE.md обновлён; коммиты по D-024 с составом в отчёте.

## Что должно реально работать

- `docker compose -f infra/docker/compose.dev.yml up -d` на чистой машине — хранилище готово, бакет есть, загрузка фотографии в dev проходит с первого раза.
- Набор фотографий, запущенный пять раз подряд, зелёный каждый раз.
