# TASK-031 — Кабинет поставщика: каркас PWA, вход, сотрудники, компания

Модель: Opus 5.5, High

## Цель

Сейчас поставщик работает с клубом только через WhatsApp-уведомления и команды, которые за него выполняет Product Owner. Чтобы позвать реальных поставщиков на внутреннюю альфу, нужен **кабинет поставщика** — веб-приложение для телефона, которое ставится на экран как приложение (PWA).

Эта задача — первая из трёх (TASK-031 → TASK-032 предложения → TASK-033 заявки и сканер). Она даёт:
- каркас кабинета с навигацией;
- вход сотрудника по коду с выбором компании и сессией на 180 дней;
- установку на экран;
- экраны «Сотрудники», «Мои настройки» и «Компания».

Сервер для всего этого уже готов (TASK-006, TASK-016, TASK-017). Задача почти целиком клиентская.

  - 6.0 — общие правила и состояния кабинета;

  - тексты T-AUTH-*, T-SUP-*.
- **Макеты DES-5** — `design/mockups/supplier.html`, утверждены. Шрифты и линии с тех пор изменились по D-068 (лёгкий дизайн, DESIGN.md 5, 7.4–7.8), макеты отстали — источник правды по виду `DESIGN.md` и `packages/ui`.
- **Дизайн-система веба** — `packages/ui`: компоненты, темы, Onest 300/400/500, Phosphor Light. Витрина — `/showcase` (TASK-075, TASK-030.B). Кабинет по умолчанию в **светлой** теме (DESIGN 7.3).
- **Сервер (ARCHITECTURE 4.6–4.9, 4.26, 4.27):**
  - вход по коду с `X-Client: supplier-web/…`;
  - шаг выбора компании — cookie `adclub_sign_in_<id>`, 403 `SUPPLIER_SELECTION_REQUIRED`, `POST /auth/sign-in/supplier`;
  - сессия — refresh-токен только в HttpOnly cookie `adclub_supplier_refresh` (Secure, SameSite=Strict), обмен — `POST /auth/session/refresh`;
  - смена компании — `POST /auth/supplier-context`, `GET /auth/suppliers`;
  - номер без членства — 403 `NOT_SUPPLIER_MEMBER` после проверки кода;
  - удалённый сотрудник — 401 `SUPPLIER_ACCESS_CLOSED`;

  - компания — `GET /supplier/company`, `PATCH /supplier/company`, `PUT /supplier/company/schedule`.

  Сессия кабинета живёт `session_supplier_web_ttl_seconds` (180 дней), браузерные origin — `SUPPLIER_WEB_ORIGINS`.
- Как сделан вход в мобильном (TASK-029, ARCHITECTURE 4.41): один обмен на все одновременно истёкшие запросы, выход в гостя только по слову сервера (I438). Для веба механика другая — обмен по cookie, но правила «когда выходить, когда нет» те же.
- `apps/supplier-web` сейчас — заглушка: проверка связи с API, «Нужно обновить», dev-витрина.

## Требования

### 1. Каркас и навигация

- **Телефон:** нижние вкладки «Заявки · Предложения · Сканер (в центре) · Ещё».
- **Компьютер (от 1024):** боковое меню с теми же разделами (DESIGN 7.5).
- В шапке всегда название текущей компании (SCREENS 6.0).
- **«Прайс»** — этап C (EPIC-16), в этой задаче его нет ни во вкладках, ни в меню.
- **«Заявки», «Предложения» и «Сканер»** наполняются в TASK-032 и TASK-033. Здесь у каждого раздела — честный экран «Раздел появится в следующем обновлении кабинета» с заголовком раздела. Не имитация данных.
- **«Ещё»:** «Мои настройки», «Сотрудники», «Компания», «Установить на экран».
- Адреса страниц понятны и переживают перезагрузку: открыл `/team` — после обновления страницы ты снова там. Кнопка «назад» браузера работает ожидаемо.
- **Язык интерфейса** kk/ru/en (все тексты через `@adclub/i18n`, казахский — самый длинный). **Тема** — «Светлая» по умолчанию, «Тёмная», «Как в системе», хранится в браузере.

### 2. Вход (S-AUTH-01…03)

- Номер → код → (несколько компаний) выбор компании → кабинет. Тексты и состояния — как M-AUTH-01/02 в мобильном: неверный код, устарел, попытки исчерпаны, повторная отправка с таймером, WhatsApp недоступен и отправлено SMS. Регистрации нет.
- **Номер без членства:** после проверки кода — текст S-AUTH-01 «Этот номер не привязан к кабинету поставщика…» и ссылка на публичную заявку S-PUB-01. Сам экран S-PUB-01 — не в этой задаче: ссылка ведёт на его адрес, если он уже есть, иначе текст без ссылки.
- **Выбор компании (S-AUTH-03):** список с городами; выбор запоминается (следующий вход в эту компанию — без вопроса), сменить можно в «Мои настройки».
- Все запросы входа, шагов и обмена — с cookie (`credentials: "include"`). Refresh-токен в JavaScript недоступен никогда (HttpOnly), access-токен — только в памяти страницы.

### 3. Длинная сессия

- **Сессия на 180 дней, выход — только явный** (SCREENS 6.1). Закрыл вкладку, перезапустил телефон, открыл через неделю — сразу в кабинете, без входа.
- **Истёкший access-токен** обменивается автоматически: один обмен на все одновременные запросы, повтор каждого. Вкладок кабинета может быть несколько — две вкладки не должны «перебить» друг другу ротацию refresh-токена так, что одна вылетит. Способ — на усмотрение агента, решение — в ARCHITECTURE.
- **Сервер сказал, что сессии нет** (`SESSION_ENDED`, `SUPPLIER_ACCESS_CLOSED`, отказ обмена) — экран входа:
  - удалённый сотрудник — «Доступ к кабинету закрыт. Обратитесь к коллегам или администратору клуба» (SCREENS 6.0);
  - конец сессии — обычный вход с сообщением T-SES-01 в формулировке для кабинета.
- **Обмен просто не удался** (нет сети, 5xx) — не выход: баннер «Нет сети», действия неактивны, следующий запрос пробует снова.
- **«Выйти»** (с подтверждением) — `POST /auth/logout`, экран входа.
- **«Нужно обновить»** — по `CLIENT_UPDATE_REQUIRED`, как сейчас.

### 4. Установка на экран (S-INST-01) и PWA

- Манифест (название, иконки из `design/brand` / `pnpm brand:assets`, цвета темы, `display: standalone`, стартовый адрес), иконки для iOS и Android.
- **Service worker:** кабинет открывается и без сети — оболочка приложения с баннером «Нет сети», а не ошибка браузера. Обновление кабинета не застревает в старой версии: новая версия применяется при следующем открытии или по «Обновить». Кэшировать ответы API в этой задаче не нужно.
- **S-INST-01:** один раз после первого входа, потом — из «Ещё»: «Кабинет откроется одним нажатием, как приложение».
  - **Android/Chrome** — кнопка «Установить» (системный запрос).
  - **iPhone/Safari** — картинка «Поделиться → На экран „Домой“».
  - **Уже установлен** — пункт не показывается.

### 5. Сотрудники (S-TEAM-01)

- **Список:** имя, телефон, «Получает уведомления», язык уведомлений, «Контактное лицо». Пояснение — T-SUP-03 с пределом `{N}`.
- **Добавить:** имя и телефон. Казахстанский мобильный номер проверяется сразу. После добавления — «Приглашение отправлено в WhatsApp».
  - Уже состоящий номер — понятный текст (409 `SUPPLIER_MEMBER_EXISTS`).
  - Ранее удалённый — «Вернуть доступ может только администратор клуба».
  - Лимит в сутки — понятный текст.
- **Переключатель «Получает уведомления»** у каждого сотрудника. Предел достигнут — у выключенных переключатель неактивен, «Достигнут предел — N». Язык уведомлений — kk/ru.
- **Удалить:** подтверждение T-SUP-04.
  - Последнего нельзя — «В компании должен остаться хотя бы один сотрудник».
  - Себя можно, если есть другие; после этого — выход на экран входа.
- Все права одинаковые (SCREENS 6.0): любой сотрудник видит и делает всё это.

### 6. Мои настройки (S-TEAM-02)

Имя и телефон (только чтение), «Получать уведомления», язык уведомлений (kk/ru; по умолчанию как интерфейс, если это kk или ru, иначе ru — SCREENS 6.0), язык интерфейса, «Оформление», «Сменить компанию» (если компаний больше одной), «Установить на экран», «Выйти».

### 7. Компания (S-COMP-01)

- **Только чтение:** название, БИН, город, «Проверенный партнёр», состояние (пауза или блокировка — с баннером, п. 8).
- **Редактируется:**
  - адрес точки выдачи и район, телефон компании;
  - часы работы по дням недели, с перерывом и «круглосуточно»;
  - нерабочие даты с заметкой; прошедшую дату добавить нельзя.

  Сохранение — с `expectedVersion`. Чужая версия — «Данные компании изменились. Обновите страницу» без потери введённого. Подсказка: «Без часов работы предложения не показываются клиентам» (D-060).
- **«Доставка по умолчанию для новых предложений»** (SCREENS) — в TASK-032, вместе с формой предложения. Здесь не делать.

### 8. Состояния компании (SCREENS 6.0)

- **Пауза администратора** — баннер на всех страницах T-SUP-05 (новый текст, SCREENS 8.5 уже обновлён).
- **Блокировка** — баннер «Кабинет заблокирован администратором клуба».
- Пауза из-за подписки (T-SUP-01) и «Карта не привязана» (T-SUP-02) — этап C, здесь не нужны. Модель состояний не должна мешать их добавить.

### 9. Ручная проверка на iPhone и HTTPS

- Cookie сессии и шага — `Secure`, а service worker требует защищённого контекста. По HTTP на адрес машины в Wi-Fi на iPhone кабинет полноценно не работает.
- Агент выбирает способ проверить кабинет на телефоне **по HTTPS в локальной сети** с минимумом ручных шагов для Product Owner (например, локальный сертификат с понятной инструкцией) и описывает его в `CLAUDE.md` блок 0.
- **Ослаблять `Secure` и `SameSite` ради dev нельзя.**
- **Публичный туннель** (доступ к dev-машине из интернета) — только с явного согласия Product Owner. Агент спрашивает, а не делает сам.

## Бизнес-правила

- Код подтверждения заявки кабинет не видит никогда (пока это только принцип — заявок в этой задаче нет).
- Все сотрудники одной компании равны. Права проверяет сервер — кабинет не прячет «чужие» действия, а показывает понятный ответ сервера.
- Сотрудник видит только свою текущую компанию. Смена компании не оставляет на экране данных прежней.
- Номера телефонов коллег показываются целиком: это их же компания, сервер их отдаёт.

## Edge cases

- **Сотрудник удалён коллегой, пока у него открыт кабинет** — следующий запрос: «Доступ к кабинету закрыт», данные компании с экрана убраны.
- **Две вкладки кабинета, обе с истёкшим access-токеном** — обе продолжают работать, ни одна не вылетает в вход.
- **Сотрудник двух компаний** — при входе выбор, затем «Сменить компанию». Выбранная запоминается; если из неё удалили — снова выбор, а не ошибка.
- **Нет сети при открытии установленного кабинета** — оболочка с баннером, без белого экрана.
- **Нет сети при сохранении** — введённое не теряется, кнопка снова доступна, когда связь вернётся.
- **Длинное казахское название компании в шапке** на 360 px — без наложений (многоточие, полное — на «Компания»).
- **Системный размер шрифта 200 %** в браузере телефона — ничего не налезает.
- **Safari на iPhone:** вход в браузере, затем «На экран „Домой“» — установленный кабинет на iOS имеет **свои** cookie и потребует входа ещё раз. Это поведение iOS. Опишите его в отчёте и, если нужно, в S-INST-01 («После установки войдите ещё раз»), но не пытайтесь обойти.
- Кабинет открыт в браузере, где администратор поднял `client_min_version_supplier_web`, — экран «Нужно обновить».

## Не входит

- Заявки, сканер, предложения (TASK-032, TASK-033), прайс (этап C), подписка (этап C), статистика (этап D).
- Публичная форма заявки S-PUB-01 как экран (если её нет — отдельной задачей).
- Админка (TASK-034).
- Изменения сервера сверх необходимого. Если без серверной правки не обойтись (например, чего-то не хватает в ответе) — правка аддитивная, с тестом, в отчёте.

## Acceptance Criteria

1. Вход: номер → код → выбор компании → кабинет; номер без членства — текст S-AUTH-01; неверный и устаревший код, исчерпанные попытки, повторная отправка — по SCREENS. Проход в браузере с dev-кодами.
2. Сессия переживает закрытие вкладки и перезапуск браузера. Истёкший access-токен обменивается сам (проба: короткий `session_access_token_ttl_seconds`), один обмен на одновременные запросы, две вкладки не выбивают друг друга. Покрыто тестом логики обмена.
3. `SESSION_ENDED`, `SUPPLIER_ACCESS_CLOSED` и отказ обмена ведут на вход с правильным текстом; сбой сети — не выход.
4. Каркас: вкладки на телефоне и боковое меню на компьютере, шапка с названием компании, адреса переживают перезагрузку; «Прайса» нет; разделы TASK-032/033 — честные экраны «появится».
5. PWA: манифест и иконки, установка на Android (системный запрос) и инструкция для iPhone; без сети — оболочка с баннером; новая версия не застревает.
6. Сотрудники: добавление с приглашением, отказы по SCREENS, переключатели уведомлений с пределом, язык уведомлений, удаление с T-SUP-04, правила последнего и себя.
7. Мои настройки и Компания — по SCREENS; сохранение компании с версией и конфликтом без потери введённого; подсказка D-060.
8. Баннеры паузы и блокировки на всех страницах.
9. kk/ru/en, светлая (по умолчанию) и тёмная темы, 360 px и 1280 px, системный шрифт 200 % — без наложений; казахский — без обрезаний.
10. Способ проверки на iPhone по HTTPS описан в `CLAUDE.md`, `Secure`/`SameSite` не ослаблены.
11. `ARCHITECTURE.md` — раздел с решениями (маршрутизация, хранение access-токена, обмен по cookie и несколько вкладок, service worker и обновление, HTTPS в dev).
12. `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` — PASS; CI на main — success.
13. Отчёт `tasks/TASK-031-REPORT.md` со списком проверок для Product Owner на iPhone и Android.

## Что должно реально работать

Product Owner открывает кабинет на iPhone по ссылке из инструкции и входит номером сотрудника «Автомаркета» `+77055550101` (код — на dev-странице). Ставит кабинет на экран «Домой», открывает его оттуда, входит. Добавляет коллегу, включает ему уведомления, меняет часы работы точки. Закрывает кабинет и открывает через день — он по-прежнему внутри.

Коллегу удаляют с другого устройства — у того кабинет показывает «Доступ к кабинету закрыт».
