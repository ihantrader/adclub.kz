# TASK-036.B — Админка: заявки, пользователи, раскрытие номеров, общий поиск, понятный журнал

Модель: Opus 5.5, High

## Цель

Последняя часть админки перед внутренней альфой. Администратор должен сам, без запросов к API и команд оператора:
- найти и разобрать любую заявку, продлить срок, отменить или закрыть её без кода — с причиной;
- массово продлить сроки после сбоя канала;
- найти пользователя, выдать или отозвать клубный доступ, посмотреть его гараж, заявки, неявки и завершить его сессии;
- увидеть полный номер человека только по нажатию, с записью в журнал;
- найти что угодно одной строкой в шапке.

И журнал должен читаться человеком: имена вместо идентификаторов, слова вместо кодов полей и статусов.

## Контекст

- **SCREENS.md 7.0** — общие правила: причина обязательна для ручных действий с заявкой и продления сроков; «было → стало»; конфликт версий; телефоны частично скрыты («+7 777 *** ** 12»), полный — по нажатию с записью в аудит; выгрузки списков с персональными данными нет; код заявки не показывается нигде.
- **SCREENS.md 7.5** — A-ORD-01 список, A-ORD-02 карточка, A-ORD-03 массовое продление. **7.6** — A-USR-01 список, A-USR-02 карточка, A-USR-03 неявки. **7.0** — A-SEARCH.
- **Сервер уже умеет** (ARCHITECTURE 4.31–4.36; примеры — `CLAUDE.md` блок 0: «Заявки в dev», «Выдача заявки, позднее закрытие и дисциплина в dev», «Уведомления по заявкам в dev», «Каталог для пользователя в dev» — клубный доступ):
  - заявки: `GET /admin/orders` с отборами, `GET /admin/orders/{id}`, закрытие без кода `POST …/close`, продление `POST …/extend-deadline`, кандидаты сбоя `GET /admin/order-extension-candidates`, массовое `POST /admin/order-extensions`;
  - дисциплина: `GET /admin/discipline`, `GET /admin/discipline/users`, снятие `POST /admin/discipline/{markId}/revoke`;
  - клубный доступ: выдача, отзыв, список выдач (`/admin/club-access/…`).
- **Сервера ещё нет** для: списка и карточки пользователя, отмены заявки администратором, раскрытия номера с аудитом, общего поиска. Сейчас админские ответы отдают номера целиком, а экран их только маскирует (TASK-036, ARCHITECTURE 4.56 I584).
- **Админка** (TASK-034…036; ARCHITECTURE 4.52–4.56): каркас, `@adclub/ui`, `SearchSelect`, `useSaver`, `ReasonDialog`, общий компонент истории `JournalHistory`, D-068, D-069. Пункты меню «Заявки» и «Пользователи» сейчас — «появится». Вкладка «Заявки» карточки поставщика показывает номера без перехода.
- **Замечание Product Owner к журналу (проверка TASK-036, 09.10.2026).** Журнал и вкладки «История» показывают объект идентификатором («Компания: 4ee901c4-…», «Сотрудник поставщика: fd714065-…»), поля — кодами (`removedAt`, `accountId`, `cityId`, `noteId`, `restored`, `again`, `state`), значения — кодами и сырыми датами (`new → contacted`, `blocked → active`, `2026-10-09T14:52:21.581Z`, `cityId: — → 65753706-…`). Администратору это не читается.
- **Клубный доступ сейчас выдаётся только командой оператора** — после этой задачи его выдаёт администратор из карточки пользователя.

## Требования

### 1. Заявки (A-ORD-01, A-ORD-02, A-ORD-03)

- **Список:** поиск по номеру («1028», «№ 1028») и по телефону клиента; отборы — статус, поставщик (`SearchSelect`), город, период, «Закрыта поздно», «Закрыта администратором»; «Показывать тестовые» (по умолчанию выключено); «Всего N», «Показать ещё». Отбор «Есть жалоба» — этап C, не показывать.
- **Карточка:** позиция, количество, сумма по заявке; клиент (имя, номер скрыт); поставщик со ссылкой на карточку; способ получения; сроки (ответ, резерв, позднее закрытие); журнал заявки с актором — сотрудник, администратор, система, «через WhatsApp» — и временем. Код и QR — нигде.
- **Ручные действия — все с причиной и подтверждением «было → стало»:**
  - «Продлить срок ответа» / «Продлить резерв» — новый срок (существующий `extend-deadline`);
  - «Закрыть без кода» — текст подтверждения из SCREENS 7.5 (существующий `close`);
  - «Снять дисциплинарную отметку» — если у заявки есть отметка (существующий `revoke`);
  - **«Отменить заявку» — новое действие сервера.** Только через единственную таблицу переходов `orderTransition` и `OrderTransitions` (новое действие администратора, как `admin_close`), с причиной в журнале действий. Из каких статусов можно отменить — решение агента по смыслу автомата, записать в ARCHITECTURE. Новых шаблонов WhatsApp не заводить (они требуют одобрения Meta): поставщик видит отмену в кабинете, пользователь — в приложении. Если по существующим правилам уведомление W-04 подходит по смыслу — решение агента, записать.
- **Массовое продление (A-ORD-03):** из сигнала «Сбой канала» на главной («Продлить сроки») и из «Сигналов» — список заявок сбоя с отметкой «уведомление не дошло», выбор, «Продлить на N минут» с причиной; итог — продлено и пропущено с причинами.
- **Связи:** вкладка «Заявки» карточки поставщика и заявки пользователя ведут в карточку заявки; журнал — тоже.

### 2. Пользователи (A-USR-01, A-USR-02, A-USR-03)

- **Новый сервер** — список и карточка пользователя (учётной записи мобильного приложения).
- **Список:** поиск по телефону (любое написание, часть номера) и имени; отборы — клубный доступ (есть / нет / истекает в ближайшие N дней), есть неявки; «Всего N», «Показать ещё». Подписок пока нет (TASK-040) — вместо «статуса подписки» показывать клубный доступ. Отбор «нет WhatsApp» — только если сервер уже знает это о номере пользователя; если не знает, не показывать и написать в отчёте.
- **Карточка:**
  - профиль: имя, телефон (скрыт), e-mail, город, язык, дата регистрации; согласия с версиями и датами;
  - **клубный доступ:** текущее состояние и до какого числа, история выдач и отзывов с причинами; «Выдать доступ…» (до даты, с причиной) и «Отозвать…» (с причиной) — существующие маршруты;
  - гараж — только просмотр;
  - заявки пользователя — со ссылкой на карточку заявки;
  - дисциплина — неявки, в том числе снятые, с «Снять…» и причиной;
  - сессии — устройство, время, «Завершить» одну и «Завершить все сессии» с подтверждением;
  - история — журнал по пользователю.
- **Неявки (A-USR-03):** пользователь, неявок за период, последняя неявка; сортировка; период — отбором (существующий `discipline/users`).
- **Обезличенных удалённых аккаунтов** пока нет (удаления аккаунта ещё нет) — ничего не делать, кроме того, чтобы список не ломался на учётной записи без имени.
- Сотрудник поставщика, который тоже пользуется приложением, — в карточке пользователя пометка «Сотрудник поставщика: {компания}» со ссылкой. Обратную ссылку — по усмотрению агента.

### 3. Номера — скрыты на сервере, полный — по нажатию с аудитом

- Все админские ответы с номерами людей — пользователей, сотрудников поставщика, контактов заявок на подключение, клиентов заявок — отдают номер **частично скрытым**. Полный номер в эти ответы не попадает.
- **«Показать номер»** рядом со скрытым номером → отдельный запрос сервера → полный номер на экране и запись в журнал действий: кто, чей номер, по какому объекту. Сам номер в журнал не пишется.
- Экраны TASK-036 (воронка, заведение, сотрудники) переводятся на это же правило. Заведение из заявки по-прежнему берёт номер из заявки на сервере, не через экран.
- Контракт — только аддитивно: новые поля и маршруты рядом со старыми. Если поле с полным номером нельзя убрать без ломающего изменения — решение агента (например, оставить поле пустым для админки или описать breaking change трейлером по I28); записать в ARCHITECTURE.
- Поиск по номеру (список заявок, пользователей, общий поиск) работает по полному номеру на сервере, а в ответе номер всё равно скрыт.

### 4. Общий поиск в шапке (A-SEARCH)

- Одна строка в шапке на всех страницах. Сервер разбирает запрос:
  - телефон → пользователь и/или сотрудник поставщика (номер в ответе скрыт);
  - «№ 4821» или число, похожее на номер заявки → заявка;
  - 12 цифр → поставщик по БИН (и заявка на подключение того же БИН);
  - артикул в любом написании → позиция справочника;
  - текст → поставщики и позиции по названию, пользователи по имени.
- Ответ — группами с переходом в карточку; клавиатура — как в `SearchSelect` (стрелки, Enter, Esc). Пусто — «Ничего не нашлось».
- Новый маршрут — с ограничением частоты на администратора.

### 5. Журнал читается человеком

Для общего журнала (`/audit`) и всех вкладок «История» (`JournalHistory`):
- **объект — по имени**: компания — названием, сотрудник и пользователь — именем, заявка — «№ 1028», позиция — названием, категория — названием и т. п.; идентификатор — только в «Подробнее»;
- **поля — словами**: «Статус», «Город», «Удалён», «Заметка», «Повторно» и т. п.; технические поля (`accountId`, `noteId`, `memberId`, служебные метки) в строку «было → стало» не выводить — только в «Подробнее»;
- **значения — словами**: этапы воронки («Новая → Связались»), состояния поставщика («Блокировка → Активен»), статусы сотрудника и заявки, да/нет; даты — в формате админки по Алматы; город — названием;
- названия берутся сервером или одним словарём админки — решение агента; одно место для всех экранов, тест словаря;
- числа-коды (годы, БИН, номера, версии) — по-прежнему без разделителя тысяч.

### 6. Связи

- Главная: «Сбой канала уведомлений → Продлить сроки» → A-ORD-03.
- Сигналы «Двойная заявка при позднем закрытии» и «Частые закрытия администратором» → «Открыть объект» ведёт в заявку или в поставщика.
- Меню: «Заявки» и «Пользователи» — живые пункты.

## Бизнес-правила

- Все проверки — на сервере: переходы заявки только через `orderTransition`, причина обязательна (пустую не принимают ни клиент, ни сервер), версии и конфликты.
- Номер не уходит в ответ, журнал, лог, мониторинг или адрес страницы целиком — кроме ответа на явный запрос «Показать номер».
- Код и QR заявки не показываются нигде.
- Выгрузок списков с персональными данными нет.
- Клубный доступ — только через существующие `ClubAccess` и `ClubAccessGrants`.
- Реальных сообщений не отправлять: в dev канал тестовый (`/dev/messages`). Никаких настоящих номеров в тестах.

## Edge cases

- Два администратора одновременно: один отменяет заявку, другой закрывает без кода — у второго конфликт с тем, кто и что сделал.
- Отмена заявки, срок которой как раз истёк, — понятный ответ.
- Продление срока заявки, которая уже в другом статусе, — в итоге массового продления «пропущено» с причиной.
- Пользователь без имени (регистрация не завершена) — в списке и поиске без поломки.
- Выдать клубный доступ при действующем — понятно, что прежняя выдача заменяется.
- Отозвать, когда нечего отзывать, — понятный отказ.
- Поиск «1028» — и номер заявки, и часть телефона: обе группы.
- Журнал: объект удалён или переименован — показывается текущее имя или, если объекта нет, понятная подпись без падения.

## Не входит

- Подписки и платежи (TASK-040 и этап C), жалобы и отзывы (этап C), удаление аккаунта и обезличивание.
- Выгрузки.
- Новые шаблоны WhatsApp.

## Acceptance Criteria

1. A-ORD-01…03: список с поиском и отборами, карточка с журналом и актором, все ручные действия с причиной и подтверждением, новая отмена через `orderTransition` с интеграционным тестом (в том числе гонка с закрытием), массовое продление из сигнала.
2. A-USR-01…03: список, карточка со всеми блоками, выдача и отзыв клубного доступа, завершение сессий, неявки; новые маршруты сервера с интеграционными тестами и матрицей доступа (мобильная сессия и сессия кабинета — 403).
3. Номера: в админских ответах скрыты (тест: ни один админский ответ, кроме раскрытия, не содержит полного номера), «Показать номер» с записью в журнал без самого номера; экраны TASK-036 переведены.
4. A-SEARCH: телефон, номер заявки, БИН, артикул, текст — тест разбора запроса и интеграционный тест маршрута с лимитом.
5. Журнал: объекты по имени, поля и значения словами, технические поля — только в «Подробнее»; тест словаря; проверено на записях поставщика, сотрудника, заявки на подключение, заявки, позиции справочника.
6. Проход в браузере:
   1. оформить заявку тестовым пользователем → найти её общим поиском по номеру → продлить срок ответа → отменить с причиной (поставщик видит отмену в кабинете);
   2. вторая заявка → принять в кабинете → «Закрыть без кода» с причиной;
   3. найти пользователя по части номера → «Показать номер» (запись в журнале без номера) → выдать клубный доступ → отозвать → «Завершить все сессии» (приложение или API этого пользователя получает `SESSION_ENDED`);
   4. журнал: записи TASK-036 читаются словами (сотрудник по имени, «Блокировка → Активен», «Новая → Связались»).
7. Контракт — аддитивно (`openapi:compat` без трейлера) или осознанный breaking change с трейлером и обоснованием; `openapi:check` PASS.
8. `ARCHITECTURE.md` — раздел решений; `CLAUDE.md` блок 0 — «Заявки и пользователи в админке», поправить «Поставщики в админке» про номера.
9. `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` — PASS; CI на main — success.
10. Отчёт `tasks/TASK-036.B-REPORT.md`.

## Что должно реально работать

Product Owner вводит в шапке «1028» и сразу попадает в заявку. Продлевает срок, отменяет её с причиной, а поставщик видит отмену в кабинете. Находит пользователя по последним цифрам номера, открывает номер по нажатию — в журнале видно, кто его смотрел. Выдаёт пользователю клубный доступ до конца года и завершает его сессии.

Журнал читается словами: «Айдана Проверка восстановлена: Удалён → Активен, причина „Удалена по ошибке“».
