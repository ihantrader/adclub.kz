# TASK-037 — Автомат заявки «под заказ» (сервер)

Модель: Opus 5.5, High

## Цель

Начало этапа C. Сейчас оформить заявку можно только на товар в наличии. Предложение «Под заказ» показывается в каталоге, но вместо «Оформить» там «Заявки под заказ появятся позже». Сервер отвечает 409 `ORDER_KIND_NOT_SUPPORTED`.

Нужен второй автомат заявки (PRODUCT 10.3, ARCHITECTURE 6.2):
- поставщик подтверждает срок из предложения или предлагает другой;
- пользователь соглашается или отказывается, без ответа заявка истекает;
- товар пришёл — «Готово к выдаче» с более долгим резервом;
- просрочка поставки фиксируется.

Эта задача — **только сервер, домен и контракт**. Экраны приложения, кабинета и админки для новых статусов — TASK-039, вместе с услугами. Уже работающие клиенты не должны ломаться на новых статусах.

## Контекст

- **PRODUCT 10.3:**
  - создавая заявку, пользователь соглашается со сроком из предложения; подтверждение без изменения срока не требует отдельного согласия;
  - другой срок — только с явного согласия пользователя, без него заявка истекает;
  - предоплата — вне платформы.
  
  PRODUCT 10.4 — сроки и резерв. PRODUCT 10.6 — обязательства при отключении поставщика.
- **ARCHITECTURE 6.2** — таблица переходов `on_order`: `create`, `accept` (срок без изменений), `propose_term`, `agree_term`, `reject_term`, истечения, `mark_ready` с отдельным резервом, `overdue` без смены статуса, `close`, `cancel`, `decline_after_accept`. Общие правила — раздел 6.
- **Что уже есть** (TASK-021…025, TASK-036.B; ARCHITECTURE 4.31–4.36, 4.57):
  - **единственная таблица переходов** `orderTransition` (`packages/domain/src/order/order-machine.ts`), применяет её только `OrderTransitions`: условное обновление, версия, гонки, `late_action_ignored`;
  - снимок предложения — `OfferSnapshots`;
  - дата получения — `receiptDate`;
  - резерв — `order-reserve.ts`;
  - свипер сроков `orders.apply-deadlines`;
  - что видит каждая сторона — `order-views.ts`;
  - активные заявки и «ждут получения» — `activeOrderStatuses` / `awaitingReceiptOrderStatuses`;

- **Уже заведено заранее:**

- **SCREENS:** S-ORD-02 (действия по типу и статусу), S-ORD-04 (другой срок: дата в рабочих днях компании, «Клиент должен ответить до …»), M-ORD-02 и M-ORD-03 («Нужен ваш ответ»), P-ORD-05, поток F5.

## Требования

### 1. Домен и автомат

- **Заявка «под заказ» — тот же `customer_order`** с видом заявки и сроком:
  - ожидаемый срок из предложения (`lead_days` снимка) и его дата;
  - предложенный срок и дата, крайний срок ответа пользователя;
  - подтверждённый срок.
  
  Миграция с откатом.
- **Переходы `on_order` — в той же таблице `orderTransition`**, по ARCHITECTURE 6.2:
  - `accept` с подтверждением срока;
  - `propose_term` (сотрудник; новый срок — в рабочих днях компании, не меньше 1 и не больше `offer_lead_days_max`, не равен текущему);
  - `agree_term` и `reject_term` (только сам пользователь заявки);
  - истечение предложенного срока по `term_agreement_hours`;
  - `mark_ready` с резервом `on_order_pickup_reserve_hours` для самовывоза;
  - `close` из «срок подтверждён» и «готова»;
  - `cancel` пользователем;
  - `decline` и отказ после принятия;
  - `admin_cancel`, `admin_close`, `close_late`, продление сроков — как у товара в наличии, где применимо.
  
  Имена статусов — решение агента: например `term_proposed`; «срок подтверждён» — тот же `accepted` с видом заявки или свой статус.
- **Дата получения «под заказ»** — от подтверждения по рабочим дням точки через `receiptDate`, без второго расчёта.
- **Просрочка поставки:** подтверждённая дата прошла, а заявка всё ещё не «готова» → событие в журнале заявки, сигнал администратору (новый вид сигнала) — один раз на заявку. Статус не меняется.
- **«Активная заявка» и «ждёт получения»** дополняются новыми статусами в одном месте: копия без сети, «Нужен ваш ответ» — `needsAnswer`, главная дата. Статистика — только через `countsInStatistics`.
- **Таблица переходов — юнит-тест по всем парам** «статус × действие × вид заявки», как сейчас.

### 2. Сервер и контракт

- **`POST /orders` принимает предложение «под заказ».** Снимок фиксирует ожидаемый срок. `ORDER_KIND_NOT_SUPPORTED` остаётся только для вида, которого ещё нет (услуги — TASK-038).
- **Новые маршруты:**
  - поставщику — «Предложить другой срок»;
  - пользователю — «Согласиться» / «Отказаться»;
  - с версией и понятными отказами: чужая заявка, не тот статус, срок прошёл, гонка — с тем, кто успел.
  
  «Подтвердить срок» — существующее «Принять», для заявки «под заказ» означает «срок подтверждён».
- **Что видит каждая сторона — только `order-views.ts`:**
  - пользователь — ожидаемый, предложенный и подтверждённый срок, «нужен ваш ответ до …»;
  - поставщик — то же плюс журнал с именами;
  - телефон покупателя поставщику — только после подтверждения срока, в том числе после согласия пользователя.
- **Уведомления:**
  - новая заявка «под заказ» — W-01a получателям компании с кнопками «Подтвердить срок» / «Отказать». Нажатие «Подтвердить срок» — тот же путь `order-button-presses.ts` → `OrderTransitions`;
  - после согласия пользователя с новым сроком — W-02 тому, кто предложил срок;
  - отмена пользователем — W-04;
  - новых шаблонов не заводить.
- **Продление сроков администратором** (`extend`) — и для срока ответа пользователя на предложенный срок, если это укладывается в существующий механизм. Решение агента; записать.
- **Контракт.** Аддитивно, где возможно. Новые статусы попадут в `oneOf` ответов сканера кабинета, как в TASK-036.B. Это осознанное изменение — с трейлером `Contract-Breaking-Change` и обоснованием.

### 3. Совместимость клиентов до TASK-039

- **Приложение:**
  - у предложения «Под заказ» по-прежнему «Заявки под заказ появятся позже» — кнопку включит TASK-039;
  - заявку «под заказ», созданную через API, список и карточка показывают без падения, со словами статуса.
- **Кабинет и админка:** заявку «под заказ» видно в списках и карточке со словами статуса и сроком; действия, которых ещё нет на экране, не предлагаются.
- **Сканер кабинета:** «под заказ» в статусе «срок подтверждён» или «готова» выдаётся по коду, как сейчас.
- **Тексты** kk/ru/en для новых статусов.

## Бизнес-правила

- Все правила — на сервере, через одну таблицу переходов. На клиентах нет своей логики переходов.
- Согласиться или отказаться может только сам пользователь заявки. Предложить срок — только сотрудник её компании. При блокировке компании — как другие действия по заявке, `SUPPLIER_BLOCKED`.
- Предложенный срок отображается датой, посчитанной по рабочим дням точки.
- Реальных сообщений не отправлять — тестовый канал.

## Edge cases

- Два сотрудника: один подтверждает срок кнопкой WhatsApp, другой предлагает другой срок в кабинете — один исход, второму — кто и когда.
- Пользователь согласился в тот момент, когда истёк срок ответа — понятный ответ, заявка истекла.
- Пользователь отменяет заявку, пока ждёт предложенный срок, — `cancelled_by_user`, W-04.
- Поставщик предлагает срок, равный текущему, или 0 дней — 400 у поля.
- Подтверждённая дата пришлась на нерабочий день точки — дата по `receiptDate` переносится на рабочий.
- Компанию поставили на паузу после создания заявки — заявка остаётся в силе (PRODUCT 10.6).
- Истечение и свипер при двух worker'ах — один переход.
- Цена предложения изменилась, пока ждали срок, — цена заявки по снимку.

## Что должно реально работать

Пользователь оформляет запросом заявку на масло «под заказ» со сроком 3 дня. Сотрудник «Автомаркета» видит её в кабинете и получает W-01a в тестовом канале. Он предлагает другой срок — 5 дней. Пользователь видит «Нужен ваш ответ до …» и соглашается. Поставщик получает W-02 с телефоном клиента, отмечает «Готово к выдаче» и выдаёт заявку по коду.

Если бы пользователь промолчал — заявка истекла бы сама.
