# TASK-039.B — Запись на услугу на экранах: приложение, кабинет, админка

Модель: Opus 5.5, High

## Цель

Последняя из трёх задач по услугам (EPIC-13). Сервер ведёт запись полностью (TASK-038), но:
- в приложении у услуги «Запись на услуги появится позже»;
- в кабинете нельзя предложить другое время и отметить неявку;
- клиент не может ответить на предложенное время.

После задачи все три вида заявок — в наличии, под заказ, услуга — работают на всех экранах.

## Контекст

- **Сервер** (TASK-038; ARCHITECTURE 4.62, таблица 6.3 «Реализовано в TASK-038»; `CLAUDE.md` — «Записи на услуги в dev»):
  - `POST /orders` с `carId` и `desiredAt` (+ `expectedPrice`);
  - варианты времени пользователю — `GET /order-visit-options?offerId=`, сотруднику — `GET /supplier/orders/{id}/time-options`;
  - «Подтвердить время» — `accept`; «Предложить другое время» — `POST …/propose-time {expectedVersion, visitAt}`; неявка — `POST …/no-show` (раньше времени — 409 `ORDER_NO_SHOW_TOO_EARLY`);
  - ответ пользователя — `/orders/{id}/term/agree|reject`;
  - `serviceVisit` во всех видах: автомобиль, желаемое, предложенное и подтверждённое время;
  - статусы `no_show` и `visit_unresolved`;
  - сигнал «Запись не разобрана».
  
  Клиенты уже показывают запись словами, но действий не предлагают.
- **Как сделан «под заказ» на экранах** (TASK-039; ARCHITECTURE 4.60) — образец:
  - блок ответа M-ORD-03;
  - диалог S-ORD-04 с вариантами сервера;
  - продление ответа в админке;
  - отказы сервера словами.
- **Экраны — SCREENS.md 1.9:**
  - **приложение:** M-CAT-08 («Записаться»), M-ORD-01 «Услуга» (автомобиль обязателен; желаемая дата — только рабочие дни поставщика, время — в пределах часов работы; «Поставщик подтвердит время или предложит другое»; количества нет), M-ORD-02 (главная дата «Ждём вас 14 марта в 10:00», «Нужен ваш ответ» первым), M-ORD-03 (состояния «Услуга» по таблице: «Предложено другое время — Нужен ваш ответ», «Подтверждена — Ждём вас {дата} в {время}», «Время записи прошло» и общие);
  - **кабинет:** S-ORD-01 (группа «Записи на услуги» по дате), S-ORD-02 (Услуга · Новая — «Подтвердить {дата} в {время}» · «Предложить другое время» · «Отказать»; Подтверждена — «Отметить выполнение по QR / коду» · «Отказать» · **после времени визита — «Клиент не пришёл»**, добавлено в 1.9), S-ORD-04 (для услуги — дата и время), S-SCAN-03 («Отметить выполненной»);
  - **админка:** A-ORD-02;
  - тексты T-ORD-*, P-ORD-05; поток F6.
- **Push пользователю ещё нет** (TASK-051).

## Требования

### 1. Приложение

- **Карточка услуги (M-CAT-08):** вместо «Запись на услуги появится позже» — «Записаться» у предложения, по тем же правилам состояния человека, что «Оформить»: гость → вход, без клубного доступа → шторка, с ним → запись.
- **Запись (M-ORD-01 «Услуга»):**
  - автомобиль — текущий из шапки (цена для его модели), смена — выбором из гаража; без цены для модели — понятный отказ;
  - **дата** — только рабочие дни точки из `order-visit-options`;
  - **время** — в пределах часов выбранного дня (шаг — решение агента, например 15 или 30 минут; сервер принимает целую минуту);
  - «Поставщик подтвердит время или предложит другое»;
  - количества нет;
  - состояния при отправке — как у товара: цена изменилась, предложение недоступно, уже есть активная запись.
- **Мои заявки (M-ORD-02):** главная дата записи — «Ждём вас {дата} в {время}» или «Ответьте до …»; «Нужен ваш ответ» первым.
- **Заявка (M-ORD-03):**
  - блок ответа «Поставщик предлагает другое время: {дата} в {время} (было {дата} в {время}). Ответьте до …» с «Согласиться» / «Отказаться» (подтверждение «Заявка будет отменена»), как у «под заказ»;
  - состояния «Услуга» по таблице SCREENS, включая «Время записи прошло» и «неявку» — словами из таблицы, без упоминания дисциплины (SCREENS M-ORD-03 «Правила»);
  - «Куда приехать», автомобиль, время.
- **Без сети:** ответ неактивен с «Нужна сеть».
- **«Повторить»** запись — открывает запись этой услуги у того же поставщика с текущей ценой. Если сервер это пока не отдаёт — решение агента: включить на сервере или оставить «Повторить» скрытым для услуг; записать.

### 2. Кабинет

- **Список (S-ORD-01):** «Новые» — метка «Услуга», автомобиль, «Клиент просит: {дата}, {время}», быстрые «Подтвердить время» / «Отказать»; «В работе» — «Записи на услуги» по дате визита.
- **Карточка (S-ORD-02):**
  - действия по таблице SCREENS 1.9;
  - «Подтвердить {дата} в {время}»;
  - «Предложить другое время» — диалог S-ORD-04 для услуги: дата из `time-options`, время в часах дня, «Клиент должен ответить до …», ошибки у поля, конфликты словами;
  - «Клиент не пришёл» — только после наступления времени визита, с подтверждением; ответ 409 раньше времени — словами;
  - «Отказать», в том числе пока клиент думает.
- **Сканер:** «Отметить выполненной» — уже есть, проверить на записи.

### 3. Админка

- **Карточка заявки:** автомобиль, желаемое, предложенное и подтверждённое время; «Продлить ответ клиента…» и «Продлить срок ответа…» для записи; отмена и закрытие без кода — как сейчас.
- **Сигнал «Запись не разобрана»** — «Открыть объект» → заявка (если ещё не сделано).

### 4. Документы

`ARCHITECTURE.md` — версия 0.64, раздел решений этой задачи, пометка, что 4.61 и 4.62 вошли в 0.64.

## Бизнес-правила

- Логики переходов и проверки времени на клиентах нет: варианты и отказы — от сервера.
- Телефон клиента в кабинете — только после подтверждения времени или согласия клиента. Код и QR — только пользователю.
- Пользователю дисциплина не видна нигде.
- Тексты kk/ru/en; казахский — рабочий черновик.
- Реальных сообщений не отправлять.

## Edge cases

- Пользователь выбрал время, а точка тем временем закрылась на этот день — отказ сервера у поля, выбор заново.
- Предложение снято, пока открыта запись, — «Поставщик снял это предложение».
- Клиент открыл ответ, а срок истёк — «Вы не ответили на предложение поставщика».
- Сотрудник нажал «Клиент не пришёл», а клиент тем временем пришёл и код уже введён коллегой — конфликт словами.
- Сегодня осталось мало времени до закрытия — в выборе только оставшиеся часы.
- Длинное казахское название услуги и автомобиля — без поломки на узком экране.

## Не входит

- Push пользователю — TASK-051.
- Слоты и календарь сервиса — не в MVP.
- Дисциплина за позднюю отмену — EPIC-19.

## Acceptance Criteria

1. Приложение: «Записаться» в M-CAT-08, M-ORD-01 «Услуга» с выбором даты и времени из вариантов сервера, M-ORD-02 и M-ORD-03 со всеми состояниями «Услуга» и блоком ответа. Юнит-тесты чистой логики.
2. Кабинет: S-ORD-01 «Записи на услуги», S-ORD-02 по таблице SCREENS 1.9 (с «Клиент не пришёл»), S-ORD-04 для услуги, сканер «Отметить выполненной».
3. Админка: время и автомобиль в карточке, продление ответа клиента для записи, сигнал → заявка.
4. Контракт: `openapi:check` PASS; изменения — аддитивные или признанные с трейлером.
5. Проход в браузере (тестовые номера, не номер Product Owner):
   1. приложение: «Замена масла» у «Шин Юг» (Астана) → «Записаться» → дата и время из вариантов → кабинет «Подтвердить время» → «Ждём вас …» → «Отметить выполненной» по коду;
   2. кабинет «Предложить другое время» → приложение «Нужен ваш ответ» → «Согласиться» → «Ждём вас {новое время}»;
   3. то же → «Отказаться» → «Вы отменили заявку»;
   4. подтверждённая запись → после времени визита (сдвиг запросом в базу для проверки) «Клиент не пришёл» → у клиента состояние без упоминания дисциплины;
   5. админка — «Продлить ответ клиента» по записи.
6. `ARCHITECTURE.md` 0.64 — раздел решений; `CLAUDE.md` блок 0 — «Записи на услуги в dev» переписать на экраны.
7. `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` и интеграционные тесты изменённых модулей — PASS локально. CI проверяет архитектор при приёмке.
8. Отчёт `tasks/TASK-039.B-REPORT.md` с идентификатором прогона CI.

## Что должно реально работать

Владелец Coolray в Астане открывает «Замена масла», нажимает «Записаться» и выбирает понедельник, 11:00 из свободных рабочих часов сервиса. Сотрудник «Шин Юг» в кабинете предлагает 15:00. Клиент в приложении видит «Нужен ваш ответ» и соглашается — «Ждём вас в понедельник в 15:00». В понедельник сервис отмечает запись выполненной по коду.
