# TASK-041 — Подписка пользователя через сторы: сервер

Модель: Opus 5.5, High

## Цель

Сервер подписок без внешних провайдеров готов (TASK-040, ARCHITECTURE 4.72, 9.4.1): автомат статусов, `billing_event`, `ClubAccess`, `GET /me/subscription`. События вводит только тестовая команда.

Задача добавляет настоящие реализации порта `SubscriptionProvider` для App Store и Google Play: проверка покупки, приём уведомлений сторов, ежедневная сверка, сигнал и push о проблеме оплаты.

**Учётных записей App Store Connect и Google Play Console нет** (решение Product Owner 20.11.2026: делать сейчас на подменённых ответах сторов). Поэтому:

- ни одного настоящего вызова сторов в задаче нет; реализации проверяются на подменённом `fetch` и локально подписанных данных — как `WhatsappCloudChannel`, `FcmPushProvider`, `ApnsPushProvider`;
- живая проверка на песочницах — отдельная задача после появления учётных записей;
- экраны приложения M-SUB-01 и M-SUB-02 — TASK-041.B, после приёмки этой задачи.

## Решения архитектора

- **Без агрегатора.** RevenueCat не используется: прямые реализации на стандартных `fetch` и `node:crypto`, без SDK сторов (как остальные провайдеры проекта).
- **Провайдеры:** `apple` и `google` — две реализации порта; выбор по платформе покупки. В development и тестах по умолчанию остаётся `TestSubscriptionProvider`. Production без настроенных сторов стартует, но маршруты сторов отвечают «недоступно» (как `card_kz` у эквайера), а сигнал администратору говорит, чего не хватает.
- **Источник истины** — уведомления сторов и наша таблица `subscription`. Клиент никогда не сообщает «подписка активна».

## Требования

### 1. Проверка покупки

`POST /billing/store/sync` (мобильная сессия; гость — 401, кабинет и админка — 403), лимит частоты на учётную запись.

- Тело: платформа и то, что отдал стор приложению (Apple — подписанная транзакция JWS; Google — `purchaseToken` и идентификатор продукта). Точная форма — на усмотрение исполнителя, по документации сторов.
- Сервер проверяет покупку сам: Apple — подпись JWS и цепочку сертификатов до корня Apple, затем состояние через App Store Server API; Google — Play Developer API (`purchases.subscriptionsv2.get`), подтверждение покупки (`acknowledge`), если она не подтверждена.
- Покупка принадлежит учётной записи сессии: `appAccountToken` / `obfuscatedExternalAccountId` равен её id. Решение «чья покупка» — существующая `purchaseLinkVerdict`. Покупка другого аккаунта — 409 `SUBSCRIPTION_LINKED_TO_ANOTHER_ACCOUNT`, подписка остаётся у первого.
- Результат проходит тот же путь, что событие: `billing_event` → существующее применение → журнал. Повтор того же `sync` ничего не меняет.
- Продукт стора не из `plan.store_product_ids` действующего тарифа — отказ, подписка не создаётся.
- Стор недоступен или не ответил за предел времени — 503 с `retryable: true`, существующий доступ не меняется.
- Ответ — текущая подписка в форме `GET /me/subscription`.

### 2. Уведомления сторов

Два маршрута вне клиентского контракта, по образцу `/webhooks/whatsapp` (сырое тело — `raw-body-routes.ts`; проверка подлинности первой, до разбора; предел размера и частоты; приём — 200 сразу, применение — worker):

- **Apple** — App Store Server Notifications V2: `signedPayload` (JWS). Проверяются подпись, цепочка до корня Apple, `bundleId` и окружение.
- **Google** — Real-time Developer Notifications через push-подписку Pub/Sub: проверяется OIDC-токен запроса (подпись ключами Google, `aud`, адрес сервисной учётной записи из настройки окружения). Уведомление несёт только токен покупки — состояние сервер запрашивает в Play Developer API.

Общее:

- Идемпотентность — по идентификатору уведомления стора (`billing_event`, как у TASK-040). Порядок — по времени события стора.
- **Таблица «имя события стора → наше событие» — в одном месте на провайдера**, с юнит-тестом на каждую строку. Имена и подтипы — по действующей документации сторов (в ARCHITECTURE 9.4.1 они помечены как предположение — проверить и исправить). Неизвестное событие сохраняется и ничего не меняет.
- `grace_until` берётся из события стора, не вычисляется.
- Уведомление о чужом приложении, чужом окружении или с негодной подписью — отказ, следа в `billing_event` нет.
- Тела уведомлений, токены покупок и JWS целиком не попадают в журнал приложения, мониторинг и журнал действий.

### 3. Ежедневная сверка и сигнал

- Задача (расписание — на усмотрение исполнителя; порядка раза в час допустимо): подписки сторов, у которых срок или льготный период прошёл, а события нет, — состояние запрашивается у стора и применяется тем же путём. Пакетами, с пределом на запуск; один недоступный стор не останавливает сверку другого.
- Существующее правило `expired_unconfirmed` → `expired` (`store_lag_tolerance_hours`) не меняется: сверка только приносит слово стора раньше.
- Сигнал администратору `store_sync_stale`: нет ни одного успешного обращения к API стора дольше `store_outage_signal_hours` при наличии подписок этого стора. Один открытый сигнал на стор, закрывается сам при первом успехе. На главной админки и в «Сигналах» — словами, с «Открыть объект» → «Биллинг → Подписки пользователей» с отбором платформы.

### 4. Push о проблеме оплаты

- Переход в `grace` — один push P-SUB-01 (шаблон уже есть) через `Notifications.enqueue` в транзакции события; открывает M-SUB-02 (цель экрана — в контракте, сам экран — TASK-041.B).
- Напоминание за `user_billing_reminder_days` до конца льготного периода — один раз на льготный период. Оплата до напоминания его отменяет.
- Резерв WhatsApp — по существующему правилу `fallbackDecision` (шаблон `user_…` для P-SUB-01 уже есть — проверить, не дублировать).

### 5. Конфигурация и dev

- Переменные окружения сторов (идентификатор приложения и ключ App Store Server API, окружение; сервисная учётная запись Google, имя пакета, ожидаемые `aud` и адрес отправителя Pub/Sub) — в `.env.example` с пояснениями. Секреты — только в `.env`. Production отказывается стартовать с частично заданным набором одного стора.
- Корневой сертификат Apple — файл в репозитории (публичный), с тестом на отпечаток.
- Dev-команда, имитирующая уведомление стора по HTTP на свой API (по образцу `dev:messages:webhook`, только development/test): подписывает локальным тестовым ключом, который сервер принимает только вне production. `dev:subscription:event` остаётся.
- `subscription:status` показывает стор, окружение стора и время последней сверки.
- Админка: в блоке «Подписка» карточки пользователя — стор и последнее слово стора (когда и что). Перенос покупки на другой аккаунт администратором — **не входит** (BACKLOG).

### 6. Проверки

Интеграционные тесты с настоящим worker'ом; сторы — локальный HTTP-сервер или подменённый `fetch`, подписи — локально созданной цепочкой сертификатов:

- сценарий ARCHITECTURE 18.10 целиком, шаги 1–8, для Apple; шаги 1, 4–7 — для Google;
- `sync`: своя покупка, чужая покупка, повтор, чужой продукт, недоступный стор, поддельная и просроченная подпись, чужой `bundleId`, чужое окружение;
- уведомления: негодная подпись и негодный OIDC-токен — отказ без следа; повтор и одновременная доставка — одно применение; события не по порядку; неизвестное событие;
- возврат и отзыв покупки закрывают доступ сразу; ранее созданная заявка и её код остаются;
- сверка: потерянное уведомление о продлении — доступ не закрывается; стор недоступен — `expired_unconfirmed`, затем `expired`, продление задним числом;
- сигнал `store_sync_stale` открывается и закрывается сам;
- push: один P-SUB-01 на льготный период, напоминание, отмена напоминания оплатой;
- что покидает процесс: ни JWS, ни токена покупки в журнале, мониторинге и выводе команд.

## Не входит

- Экраны приложения M-SUB-01, M-SUB-02 и библиотека покупок в приложении (TASK-041.B).
- Настоящие вызовы сторов, продукты в консолях, проверка на песочницах (после появления учётных записей).
- Перенос покупки между аккаунтами администратором; промо-предложения, пробный период, семейный доступ.
- Подписка поставщика (TASK-042, не трогать).

## Acceptance Criteria

1. **Проверка покупки.** `POST /billing/store/sync` для обоих сторов на подменённых ответах: своя покупка даёт клубный доступ (`ClubAccess`, `POST /orders` проходит), чужая — 409 без изменений, повтор — без изменений. Тесты — в отчёте.
2. **Уведомления.** Оба маршрута: проверка подлинности до разбора тела, идемпотентность, порядок, отказ без следа. Таблица соответствия событий каждого стора — в одном месте, с тестом на каждую строку и ссылкой на страницу документации в комментарии.
3. **Сценарий 18.10** проходит интеграционным тестом для Apple целиком и для Google в указанных шагах.
4. **Сверка и сигнал.** Тесты требования 3; сигнал виден в админке (браузер, тестовый ИИ и тестовые сторы) — снимок или текст страницы в отчёте.
5. **Push.** Тесты требования 4; P-SUB-01 виден на `/dev/pushes` после имитации уведомления стора dev-командой.
6. **Без секретов и без внешних вызовов.** В тестах и CI нет ни одного обращения к сторам; тест «что покидает процесс» зелёный.
7. **Локальные проверки:** `pnpm format:check`, `lint`, `typecheck`, `test`, `build`. Интеграционные: `billing`, новый файл сторов, `admin-panel`, `notifications`/push-резерв — если задеты; при новой миграции — `database.integration.test.ts` и запись в `apps/api/src/testing/expected/migrations.ts`; новая фоновая задача — в `expected/background-jobs.ts`; новый маршрут `/admin` — в `expected/admin-routes.ts` и счётчики маршрутов тестов доступа. Контракт: `openapi:generate`, `openapi:check`, `openapi:compat --snapshots`. CI не ждать.
8. **Документы.** ARCHITECTURE — новый раздел 4.98, строки I1221–I1245; в 9.4.1 исправить имена событий сторов по документации и абзац «Не реализовано до TASK-041». Версию и историю ARCHITECTURE не менять. CLAUDE.md — «Подписки в dev». В отчёте `tasks/TASK-041-REPORT.md` — идентификатор прогона CI, список того, что проверит только песочница, и что нужно от Product Owner в консолях сторов (продукты, льготный период, адреса уведомлений, ключи).
