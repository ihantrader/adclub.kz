# TASK-043 — Биллинг в админке: сводка, подписки пользователей, платежи поставщиков, тарифы

Модель: Opus 5.5, High

## Цель

Подписка поставщика картой (TASK-042, доводки 042.A и 042.B) и подписки пользователей на сервере (TASK-040) работают. Администратор пока видит биллинг только по одному объекту:
- блок «Подписка» в карточке пользователя;
- вкладка «Подписка» в карточке поставщика;
- сигналы `payment_failed`, `payment_system_down`, `billing_plan_missing`.

Тарифы заводит только оператор командой `billing:plan:add`.

Задача делает раздел «Биллинг» админки по SCREENS 7.8 (A-BILL-01…04) и PRODUCT 11 («статистика по подпискам, список неуспешных платежей, история списаний»). После неё администратор:
- видит, сколько подписок и у кого платёж не прошёл;
- находит любое списание;
- сам назначает повышение тарифа поставщиков с анонсом.

## Требования

### 1. Одно место счёта

Каждое число сводки — **ровно число строк списка**, куда ведёт её карточка, с теми же отборами. Это то же правило, что у главной админки и качества справочника (TASK-034, TASK-035): сводка и список берут одну и ту же SQL-функцию (или одни выражения), а не два похожих запроса.

Определения записать в ARCHITECTURE (новый I-номер):
- **Подписка пользователя «активна».** Даёт доступ по `subscriptionAccess`: `active`, `grace`, `cancelled` до конца срока, `expired_unconfirmed` в пределах допуска. Каждое состояние показывается словами отдельно.
- **«Новая за период».** Первое `started` подписки (по `billing_event`, `applied`) попало в период.
- **«Прекращена за период».** Переход в конечное состояние — `expired`, `refunded`, `revoked` — попал в период.
- **Поставщик:**
  - **«оплачено»** — `active`;
  - **«проблема»** — `past_due`, а также неразрешённая попытка `unavailable` / `unknown`;
  - **«пауза по оплате»** — `suspended` / `billing_paused_at`;
  - **«нет карты»** — нет подписки и карты.

  Каждый поставщик — ровно в одной группе.

Период — дни по Алматы, как в «Заявках». Ручная выдача клубного доступа в подписки **не входит**. Её можно показать отдельной строкой «Доступ выдан вручную: N», если это не путает счёт.

### 2. A-BILL-01 «Сводка» (`/billing`)

- **Подписки пользователей:** активные по платформам (iOS / Android / прочие — как `subscription.platform`, без выдумывания), новые и прекращённые за период. Выбор периода — как в «Заявках», по умолчанию последние 30 дней.
- **Поставщики:** оплачено / проблема / пауза по оплате / без карты.
- **Списания поставщиков за период:** успешных — число и сумма ₸; неуспешных — число.
- Каждая карточка открывает список с тем же отбором.
- **Тариф поставщиков:** в силе сейчас и объявленное изменение («С {дата} — {цена} в месяц»), ссылка на «Тарифы». Если тарифа нет — предупреждение со ссылкой (сигнал `billing_plan_missing` уже есть).

### 3. A-BILL-02 «Подписки пользователей» (`/billing/users`)

- **Вкладки:** «Действующие» и «Прекращённые» (счётчики — по правилу п. 1).
- **Отборы в адресе:** статус, платформа, провайдер, «истекает в ближайшие N дней», период (для «новых» / «прекращённых» из сводки), поиск по части номера и имени.
- **Строка:**
  - пользователь — имя или скрытый номер, ссылка в карточку на «Клубный доступ»;
  - статус словами;
  - платформа;
  - оплачено до;
  - доступ до;
  - дата начала;
  - для прекращённых — когда и почему (вид события).
- «Всего N», «Показать ещё» (курсор).

### 4. A-BILL-03 «Платежи поставщиков» (`/billing/payments`)

- **Вкладка «Неуспешные»** — поставщики с незавершённым неуспехом.
  - Строка: поставщик (в карточку на «Подписку»), сумма, причина отказа словами, номер попытки за период, когда была последняя, следующая попытка (или «Автоматических попыток больше не будет»), **дней до паузы** (из `bankRetryWindowEnd` / `grace_until` — те же функции, что у W-05, без второго расчёта).
  - Отдельно — попытки, ждущие ответа платёжной системы («Платёжная система недоступна» / «исход неизвестен»). Они не неуспех плательщика (I819…).
- **Вкладка «История списаний»** — все попытки.
  - Отборы: период, поставщик (выбор с поиском), статус (успешно / отказ / недоступно / неизвестно), вид (первое / плановое / «Оплатить сейчас» / повтор).
  - Строка: дата, поставщик, сумма, период подписки, карта (маска), статус и причина, кто нажал (сотрудник — для ручной оплаты).
  - «Всего N», «Показать ещё».
- Токен карты не попадает ни в ответ, ни в журнал, ни в лог. Маска — как в кабинете.

### 5. A-BILL-04 «Тарифы» (`/billing/plans`)

- **Поставщики:**
  - тариф в силе;
  - объявленное и запланированное изменения;
  - история записей `plan` (цена, с какой даты, анонс за N дней, причина, кто завёл — оператор или администратор).
- **«Запланировать изменение…»** — цена ₸, дата начала (день по Алматы), «Предупредить за N дней», причина.
  - Перед сохранением — «было → стало»: «С {дата} тариф — {цена} в месяц; поставщики увидят это с {дата анонса}».
  - Сервер проверяет правила (решить и записать в ARCHITECTURE):
    - дата начала — не сегодня и не в прошлом;
    - **повышение** нельзя начать раньше, чем через «Предупредить за N дней» от сейчас: иначе обещание PRODUCT 14.1 «предупреждается заранее» не выполняется. Сервер отвечает ошибкой у поля даты с ближайшей допустимой датой;
    - понижение — по тем же правилам или проще, решить самому;
    - пределы цены и N — из настроек, если есть, иначе разумные с записью в ARCHITECTURE;
    - дубль даты — ошибка у поля (`UNIQUE (audience, valid_from)`).
  - Журнал — `plan.added` с актором-администратором.
- **«Отменить запланированное…»** — только запись, которая ещё не вступила в силу.
  - С причиной; журнал `plan.cancelled`.
  - Решить, удаляется запись или помечается, и записать в ARCHITECTURE. История должна показывать отменённое.
  - Анонс, который поставщики уже видели, после отмены пропадает из кабинета. Это осознанное поведение: проверить и описать.
- Действующий тариф не правится: только новая запись с датой (I783).
- **Одновременная правка двумя администраторами:** второй получает понятный отказ (версия или ожидаемое состояние), а не дубль.
- **Пользователи:** цены не редактируются (они в сторах).
  - Показать, что заведено в `plan` для аудитории `user` (только просмотр).
  - Показать текст `price_increase_notice_text` (kk/ru/en) с правкой — тем же механизмом, что настройки (с версией и причиной), или ссылкой на «Настройки». Выбрать то, что не создаёт второй путь записи настройки.
- Команда `billing:plan:add` / `billing:plan:list` оператора остаётся и проходит тем же сервисом, что экран.

### 6. Меню, главная, сигналы

- В меню — раздел «Биллинг» (между «Поставщиками» и «Настройками»), подстраницы — вкладками раздела.
- На главной — карточка «Платежи поставщиков не прошли · N», если её ещё нет. Число — по правилу п. 1. Сигналы не дублировать: если карточка сигнала уже есть, она ведёт в A-BILL-03.
- «Открыть объект» у сигналов `payment_failed` / `payment_system_down` — в A-BILL-03 или в «Подписку» поставщика. Выбрать полезнее и единообразно.
- Карточки пользователя и поставщика — ссылка «Все платежи» / «Все подписки» в раздел с отбором по объекту.

### 7. Сервер и контракт

- Новые админские маршруты (`/admin/billing/…`) — `auth: "session"`, контекст `admin`, постранично (курсор), отборы в адресе под именами API. Внести в `apps/api/src/testing/expected/admin-routes.ts`.
- Контракт — аддитивно (`openapi:compat` без трейлера), `openapi:generate` и `openapi:check`.
- Номера людей — скрыты сервером во всех новых ответах.
- Большие таблицы: списки и сводка не читают всё в память. Замерить сводку и первую страницу истории на объёме: ~2 000 поставщиков × 12 периодов попыток и ~20 000 подписок пользователей. Результат — в отчёт. Нужные индексы — миграцией (внести в `expected/migrations.ts`).

## Не входит

- Настоящий эквайер и сторы (TASK-041); экраны оплаты M-SUB-01/02.
- Возвраты, ручные списания и правка подписки администратором. Администратор ничего не списывает и не меняет статусы. Единственное действие с деньгами в задаче — тариф.
- Выгрузка в файл, графики.
- D-041 (`supplier_card_required`) — переключатель не трогать.
- Тексты SCREENS. Где текста нет — писать в духе соседних экранов и перечислить новые строки в отчёте на утверждение Product Owner.

## Acceptance Criteria

1. **Сводка = список.** Интеграционный тест: на данных со всеми состояниями (пользователи — каждый статус, две платформы, начала и прекращения на границах периода по Алматы; поставщики — во всех четырёх группах, включая `unknown` и `unavailable`) каждое число сводки равно `total` и постраничному обходу списка с её отбором.
2. **Каждый поставщик — ровно в одной группе.** Тест, в том числе с административной и биллинговой паузами одновременно.
3. **«Дней до паузы» и «следующая попытка»** совпадают с тем, что W-05 / W-05a обещали этому поставщику. Тест берёт одни доменные функции.
4. **Тарифы:**
   - администратор планирует повышение — кабинет поставщика (`GET /supplier/subscription`) показывает анонс с даты анонса, а списание после даты начала идёт по новой цене (тест с ходом времени);
   - повышение раньше срока предупреждения, прошлая дата и дубль даты — отказ у поля;
   - отмена — только будущей записи, анонс пропадает;
   - два администратора одновременно — одна запись;
   - журнал `plan.added` / `plan.cancelled` с причиной;
   - команда оператора — тем же сервисом.
5. **Доступ.** Матрица доступа новых маршрутов (гость, мобильная, кабинет — отказ). Ни полного номера, ни токена карты в ответах, журнале и логе (проверка вывода, как в других интеграционных файлах).
6. **Админка в браузере** (1440, светлая), на dev-данных, заведённых командами (`billing:plan:add`, `dev:subscription:event`, тестовые карты и `jobs:run billing.charge-due` — как «Подписка поставщика в dev»):
   - все четыре экрана;
   - карточки сводки открывают списки с тем же числом;
   - «Неуспешные» с поставщиком на втором дне повторов и с поставщиком на паузе;
   - «История» с отборами;
   - планирование и отмена тарифа, после которых кабинет «Автомаркета» показывает и убирает «С {дата} тариф — {цена} в месяц»;
   - конфликт двух вкладок.

   Описать в отчёте фактами.
7. **Замер** п. 7 — в отчёте (время сводки и первой страницы, план запроса при необходимости).
8. **`ARCHITECTURE.md`** — версия по порядку:
   - решения (определения групп, правила тарифа, отмена);
   - I783 и I833 — обновить ссылки;
   - `CLAUDE.md` блок 0 — «Биллинг в админке в dev».
9. **Локально** `pnpm format:check`, `lint`, `typecheck`, `test`, `build`; интеграционные тесты изменённых модулей (`billing`, `supplier-billing`, `admin-panel`, `admin-users`, `database`). Push в `main` без ожидания CI. Отчёт — `tasks/TASK-043-REPORT.md` с id прогона.
