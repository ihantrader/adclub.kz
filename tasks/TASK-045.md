# TASK-045 — Поиск: индекс Meilisearch, опечатки, фасеты, качество

Модель: Opus 5.5, High

## Цель

TASK-044 дала поиск на PostgreSQL: артикул, раскладка, транслитерация, синонимы и исправление слова — только когда ничего не нашлось. Чего не хватает:
- **устойчивости к опечаткам**, когда запрос частично что-то находит;
- **ранжирования** по релевантности и популярности;
- **фасетов** — отбора результатов по категориям и характеристикам;
- **измеренного качества** поиска.

ARCHITECTURE 10 выбрала для этого Meilisearch (уже в стеке и в dev-compose) как производный индекс при PostgreSQL — источнике истины.

## Контекст

- **ARCHITECTURE 10:**
  - **10.1** — документ позиции и синхронизация: `search_outbox` в той же транзакции, что изменение; worker применяет пакетами; полная переиндексация — команда и ночная сверка;
  - **10.2** — обработка запроса (с TASK-044 «как реализовано»): варианты запроса одним `multi-search`, объединение по позиции; синонимы в Meilisearch; город;
  - **10.3** — фильтр по автомобилю составными токенами совместимости.
- **TASK-044** (ARCHITECTURE 4.64):
  - предобработка в домене (текст и ключ, варианты, `searchRankKey`);
  - `item_search_synonym`;
  - `GET /catalog/search` — ветка артикула и текстовая ветка на PostgreSQL;
  - показ — только функциями каталога: `shownOffers` / `offersInReach`, `CompatibilityEvaluator` + правило D-029, `describeListItems`;
  - экран M-CAT-04 в приложении.
- **Окружение:** Meilisearch в `infra/docker/compose.dev.yml`, переменные `MEILISEARCH_URL` и `MEILI_MASTER_KEY`. `/ready` его не проверяет (4.x I17) — поиск не должен валить готовность API.
- **SCREENS M-CAT-04** — «отбор по категориям» в результатах. Фильтры характеристик — как M-CAT-03 у подкатегории.

## Требования

### 1. Индекс — производный, правила показа не переезжают

- **Индекс только находит и ранжирует кандидатов.** Что показать, решают те же функции каталога на PostgreSQL, что сейчас (`shownOffers`, `CompatibilityEvaluator`, D-029, город для услуг, видимость поставщика). Индекс, отставший от базы, не может показать лишнего — только не найти. Записать в ARCHITECTURE.
- **Документ позиции** — по 10.1, с поправками на то, что есть:
  - названия kk/ru/en, бренд и написания, синонимы позиции и категории, названия категорий, ключи предобработки;
  - артикул и варианты;
  - вид, категории двух уровней;
  - значения фильтруемых характеристик для фасетов;
  - токены совместимости (10.3) — **решение агента**: использовать ли фильтр совместимости в Meilisearch или фильтровать кандидатов `CompatibilityEvaluator` после поиска. Записать с замером;
  - города предложений;
  - популярность — заявки за 90 дней, только через `countsInStatistics` / `inSupplierStatistics`.
  
  В индекс попадают только активные позиции, у которых есть хотя бы одно активное предложение.
- **Синонимы** из `item_search_synonym` — в настройки индекса группами kk/ru/en.
- **Синхронизация:**
  - `search_outbox` пишется в транзакции каждого изменения, влияющего на документ: позиция, переводы, характеристики, синонимы, совместимость, предложение (выставление, правка, снятие, возврат), поставщик (пауза, блокировка, тип, город точки, часы);
  - worker применяет пакетами с задержкой в секунды, идемпотентно;
  - **«Правило одно место»** — регистрация изменения через одну функцию, а не разбросанные вставки. Решение агента, записать;
  - **ночная сверка** — фоновая задача по расписанию сравнивает индекс с базой и чинит расхождения; число расхождений — в метрике и лог.
- **Команды оператора:** `search:reindex` (полная переиндексация без простоя — через новый индекс и переключение), `search:status` (документов, очередь outbox, последняя сверка).

### 2. Запрос

- **Текстовая ветка `GET /catalog/search` — через Meilisearch:**
  - варианты запроса из домена одним `multi-search`;
  - встроенная устойчивость к опечаткам;
  - объединение по позиции;
  - ветка артикула остаётся в PostgreSQL первым блоком (10.2).
- **Ранжирование:** артикул → релевантность Meilisearch → популярность; товары с предложениями в выбранном городе выше; «Весь Казахстан» снимает приоритет. Внутри — одна функция порядка (развить `searchRankKey`).
- **T-CAT-08** «Показаны результаты по …» — когда сработал вариант, отличный от исходного, или Meilisearch исправил опечатку (если это можно определить; решение агента).
- **Meilisearch недоступен** — поиск отвечает текстовой веткой PostgreSQL из TASK-044, а не ошибкой. Метрика и предупреждение в лог. Тест с остановленным контейнером.
- **Контракт** — аддитивно: фасеты в ответе и параметры отбора.

### 3. Фасеты и отбор в приложении

- **Ответ поиска несёт фасеты:**
  - категории второго уровня с числом позиций;
  - если выбрана одна категория — её фильтруемые характеристики с вариантами и числами.
  
  Числа — по тем позициям, которые реально будут показаны (после правил показа), либо приблизительные с пометкой. Решение агента, записать.
- **Приложение (M-CAT-04):**
  - чипы категорий с числами — нажатие отбирает результаты по категории;
  - в выбранной категории — «Фильтры» с характеристиками (тот же компонент, что в M-CAT-03), «Показать N позиций», «Сбросить».

### 4. Качество поиска — измеряемое

- **Набор фраз** `search-eval/phrases.json`, данные в репозитории:
  - 60–100 запросов по dev-справочнику с ожидаемыми позициями;
  - артикулы в разных написаниях;
  - раскладка, транслитерация;
  - опечатки в 1–2 буквы;
  - синонимы kk/ru/en;
  - смешанные языки;
  - запросы, которые ничего не должны находить.
- **Интеграционный тест на настоящем Meilisearch** (Testcontainers):
  - для каждой фразы ожидаемая позиция в первых трёх;
  - порог — не ниже 95 % фраз;
  - «ничего не должно находить» — пусто.
  
  В отчёте — доля и список провалов.
- Тот же набор — командой оператора на dev-базе, для будущих правок синонимов.

## Бизнес-правила

- PostgreSQL — источник истины. Индекс перестраивается из базы в любой момент.
- Поиск не показывает того, чего не показал бы каталог. При любом расхождении индекса — «не найдено», а не «показано лишнее».
- В индекс не попадают персональные данные, телефоны и тексты гарантии с контактами.
- Реальных внешних вызовов нет: Meilisearch — свой контейнер.

## Edge cases

- Предложение сняли — позиция пропадает из выдачи сразу (правила показа), из индекса — после outbox.
- Поставщика поставили на паузу — то же.
- Позицию перевели (kk) — находится по-казахски после outbox.
- Синоним добавили — работает после обновления настроек индекса.
- Переиндексация во время поиска — поиск отвечает без ошибок.
- Meilisearch упал посреди работы — поиск переключается на PostgreSQL. Outbox копится и применяется после восстановления.
- Очень общий запрос («масло») — страницы без пропусков и повторов.

## Не входит

- Голос и фото как вход в поиск, ИИ-помощник — этап D.
- Поиск в кабинете и админке по индексу — остаются на PostgreSQL.

## Acceptance Criteria

1. Индекс: документ, синонимы, outbox в транзакциях изменений через одну функцию регистрации, worker, ночная сверка, `search:reindex` без простоя, `search:status`. Интеграционные тесты на настоящем Meilisearch: изменение каждого вида попадает в индекс; откат транзакции не оставляет записи outbox; переиндексация без простоя; сверка чинит расхождение.
2. Запрос через Meilisearch с вариантами и опечатками; артикул первым; город; T-CAT-08; падение Meilisearch → PostgreSQL (тест).
3. Правила показа не изменились: тесты TASK-044 на D-029, город услуг, видимость поставщика, паузу — зелёные. Добавлен тест «индекс отстал — лишнего не показано».
4. Фасеты в ответе и в приложении: чипы категорий с числами, фильтры характеристик в выбранной категории.
5. Качество: `search-eval/phrases.json`, интеграционный тест ≥ 95 % в первых трёх, команда оператора; в отчёте — доля и провалы.
6. Проход в браузере (приложение под react-native-web): «колодкм», «тормозные колодкм», «масло 5w30», «моторное масло shell», «brake pads»; чип категории; фильтр характеристики.
7. Контракт аддитивно (`openapi:compat` без трейлера), `openapi:check` PASS.
8. `ARCHITECTURE.md` — версия 0.66, раздел решений, 10.1–10.3 «как реализовано»; `CLAUDE.md` блок 0 — «Поиск в dev» (индекс, команды, сверка, набор фраз).
9. `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` и интеграционные тесты изменённых модулей — PASS локально. CI проверяет архитектор при приёмке.
10. Отчёт `tasks/TASK-045-REPORT.md` с идентификатором прогона CI.

## Что должно реально работать

Владелец Atlas набирает «тормозные колодкм» и сразу видит колодки — опечатка не мешает, исправления «на ноль» больше не нужно. По запросу «масло» видит чипы «Моторные масла · 3», «Замена масла · 1». Выбирает «Моторные масла», открывает «Фильтры» и отбирает вязкость 5W-30.

Администратор снимает предложение — оно сразу пропадает из выдачи, а индекс догоняет за секунды.
