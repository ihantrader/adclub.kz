# TASK REPORT — TASK-046.A

## Status
COMPLETED

## Result
Файл прайса больше не может остановить API и worker.

- **API при загрузке не распаковывает и не читает файл целиком.** Он смотрит только на первые байты, на каталог ZIP у `.xlsx` и не больше первых 64 КиБ у CSV. Всё остальное делает worker, и загрузка становится `failed` с той же причиной и теми же словами в кабинете.
- **Каталог ZIP проверяется на правдоподобие.** Запись, у которой сжатых байтов больше, чем она объявляет несжатыми, лжёт о размере (deflate так не умеет). Поэтому файл архитектора («100 байт» в 20 МБ) отказывается сразу: 400 «Файл повреждён» за 82 мс.
- **Worker распаковывает каждую запись потоком.** Распаковка обрывается на первом байте сверх объявленного размера или общего бюджета файла (200 × размер, от 32 до 512 МБ). Из бюджета тратят все записи и оба прохода по листу.
- **Ограничено и то, что копится в памяти:** записи ZIP, объединённые ячейки, общие строки, текст ячейки, колонки CSV. Объединённые ячейки применяются без квадратичного прохода.
- **Долгое чтение отдаёт ход циклу событий и слушает сигнал задачи.** Поэтому тайм-аут задачи и остановка worker'а работают.
- **Отказанные загрузки тратят попытку** в пределе компании.
- **Доделано найденное при приёмке:**
  - фаза отсчитывается от начала работы worker'а;
  - повтор продолжает разбор значений;
  - загрузка, помеченная `failed`, не получает строк от опоздавшего запуска;
  - запомненный формат ищется по хэшу заголовка;
  - подтверждение колонок из устаревшей вкладки — 409 со словами «Колонки уже подтвердил {кто}»;
  - испорченные курсоры — 400.
- **Прайс одной компании не задерживает прайсы других:** `prices.parse` и `prices.read-values` идут по два на worker.

## Technical Decisions
Всё внесено в `ARCHITECTURE.md` 4.66, I702–I708.

- **Бюджет распаковки.** 200 × размер файла, не меньше 32 МБ и не больше 512 МБ, общий на все записи и оба прохода.
  - 200× — с запасом к реальному сжатию XML (у выгрузки 1С на 50 000 строк — около 10–20× на проход).
  - Нижний порог 32 МБ — для маленьких файлов, где теги сжимаются слабо.
  - Потолок 512 МБ — время разбора остаётся в секундах.
- **Проверка по каталогу (`entryProblem`).** Deflate не увеличивает данные больше чем примерно на 1/256. Поэтому «сжатых байтов больше, чем несжатых» — надёжный признак лжи о размере, и он виден без распаковки. XML-часть, объявленная больше бюджета, тоже отказывается сразу.
- **CSV при загрузке — не больше первых 64 КиБ.** Файл такого размера проверяется целиком: это доли миллисекунды, и прежние мгновенные отказы маленьких файлов остались. У большего файла по началу видны кодировка и «не таблица», а остальное находит worker.
- **Предел отказов — общий с пределом загрузок компании** (`price_import_refusal` и тот же запрос). Отдельный предел на сотрудника не вводил: предел нужен на компанию, а один механизм проще двух.
- **Конфликт подтверждения колонок — через версию загрузки.** Поле `expectedVersion` необязательное, поэтому клиент без него работает как прежде.
- **`concurrency` у фоновых задач.** Без этого один worker брал по одному `prices.parse`, и прайс на 50 000 строк задерживал чужой (сосед ждал 10 с; с двумя запусками — 0,5 с).

### Замеры (AC-2)

**`/health` и ответ на загрузку бомбы 20 МБ.**

До изменений:
- Старый код в процессе — это то, что API выполнял синхронно внутри запроса:
  - файл 1 МБ, внутри общих строк 1 ГБ нулей при объявленных 100 байтах — запрос держится **3,3 с** (у архитектора 2 ГБ — 6 с; 20 ГБ в 20 МБ — порядка минуты);
  - честные 60 МБ общих строк в файле 64 КБ — **0,9 с**.
- Бомба в листе в worker'е: **7,8 с** полной остановки цикла событий, пик памяти **1,4 ГБ**.

После изменений, интеграционный тест (Testcontainers, API и worker в одном процессе):
- файл приёмки 20 МБ («100 байт» внутри) — **400 за 82 мс**, `/health` не дольше **8 мс**;
- бомба 20 МБ с правдоподобным объявленным размером — **201 за 494 мс** (приём 20 МБ и запись в MinIO), worker отказал «broken» через **0,7 с**, `/health` не дольше **10 мс**.

После изменений, dev (API и worker — отдельные процессы):
- файл приёмки из кабинета — 400 за 143 мс, `/health` — до 27 мс;
- бомба с правдоподобным размером — 201, затем `failed`/`broken`, `/health` — до 27 мс;
- время приёма — от 0,65 до 1,7 с: это запись 20 МБ в MinIO на Windows. Обычный файл того же размера стоит столько же.

**Память и время worker'а на бомбах** (в процессе, после изменений):

| Файл | Отказ через | Рост памяти |
|---|---|---|
| 19 ГБ в общих строках | 21–65 мс | ≤ 18 МБ |
| 19 ГБ в листе | 48 мс | ≤ 1 МБ |
| 3,5 ГБ, объявленные честно | 20 мс | ≤ 6 МБ |

**Объединения:** 100 000 диапазонов над 50 000 строк читаются за 2,1 с, остановка цикла событий — не дольше 72 мс. В интеграционном тесте небольшой прайс другой компании разобран за 0,5 с, пока читался этот файл.

**Обычный файл 1С на 50 000 строк** (интеграционный): загрузка 133 мс, чтение в строки 11,1 с, разбор значений 5,4 с. В TASK-046 было 0,97 с, 14,4 с и 10,2 с. В процессе чтение замедлилось с 2,4 до 3,4 с — это цена мелких кусков распаковки.

## Errors & Fixes
- **Интеграционный файл сначала упал целиком.** `TRUNCATE_ALL` не знал новую таблицу, которая ссылается на `supplier`. Таблица добавлена в `testing/database.ts` и в `schema-drift.test.ts`.
- **Загрузка бомбы по пути 201 заняла 579 мс** при требовании меньше 500 мс. Причина — ввод-вывод (приём 20 МБ и запись в MinIO), а не разбор. Решение — дешёвая проверка правдоподобия размеров по каталогу (`entryProblem`): файл приёмки теперь отказывается сразу за 82 мс. Бомбе с правдоподобным размером, которая неизбежно сохраняется, тест разрешает до 2 с и отдельно проверяет `/health`.
- **Соседняя загрузка ждала 10 с:** worker брал по одному `prices.parse`. Добавлен `concurrency` (I708), теперь 0,5 с.
- **Остановки цикла событий 146–237 мс на сильно сжимаемых объединениях.** Кусок входа уменьшен до 1 КиБ, ход отдаётся каждые 256 КиБ выхода. Стало не больше 72 мс.

## Deviations
- **CSV при загрузке проверяется целиком, если файл не больше 64 КиБ.** Требование 1 относит число строк и кривой CSV к worker'у. Для маленьких файлов это доли миллисекунды, и прежний мгновенный отказ сохранился. Для файлов больше 64 КиБ эти проверки делает worker, как требует задача.
- **Требование «загрузка отвечает 201 или 400 быстрее 500 мс».** Для бомбы приёмки выполнено: 400 за 82 мс. Бомба с правдоподобным размером (201) — 494 мс в интеграционном тесте, но в dev на Windows до 1,7 с. Это запись 20 МБ в хранилище, одинаковая для любого файла такого размера; цикл событий при этом свободен (`/health` до 27 мс).
- **Добавлено вне буквы задачи:** `concurrency` у фоновых задач. Без него не выполнялось «worker продолжает разбирать прайсы других компаний».

## Known Issues / Risks
- **Ответ на загрузку файла около 20 МБ** в dev на Windows — от 0,65 до 1,7 с. Это ввод-вывод в MinIO, ускорить его можно только потоковой записью в хранилище; см. Future Improvements.
- **`prices.parse` по два запуска на worker** — каждый держит свой файл в памяти, до 20 МБ.
- **Записи отказов старше суток удаляет `prices.expire-stalled`.** Отдельной задачи для этого не заводил.
