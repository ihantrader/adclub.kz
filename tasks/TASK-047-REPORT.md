## Technical Decisions
Все решения внесены в `ARCHITECTURE.md` 4.67:
- **Состояния** `parsed → matching → review → applying → applied`, `failed`, `expired` (I709).
- **Четыре шага сопоставления** (I711):
  - память «пропустить / нет в справочнике» проверяется после точного артикула, чтобы позиция, заведённая позже, находилась;
  - поиск по названию — по индексу названий в памяти (один запрос за запуск) с тем же ключом слова, что поиск поставщика (`searchKey`, `searchVariants`).
- **«Сильный» кандидат — правило домена** (I712): все слова названия позиции есть в строке; каждое слово строки покрыто названием, брендом или категорией; числа совпадают; бренд не противоречит; не меньше двух слов; другой артикул — не сильный.
- **ИИ** (I714):
  - выбор ИИ всегда идёт в «нужно проверить» с пометкой «предложено ИИ», на витрину он попадает только после «Верно»;
  - уверенность не ниже `price_match_confidence_threshold` — выбор ИИ стоит предложенной позицией;
  - уверенность ниже порога — позиции нет, выбор ИИ первым кандидатом;
  - недоступный ИИ и исчерпанный бюджет — загрузка ждёт в `matching`, задача ставит себя через `price_match_retry_seconds`.
- **Пропавшие — одно SQL-определение** (I716).
- **Память компании `supplier_sku_mapping`** с решением «позиция / пропустить / нет в справочнике» (I717):
  - «Не отправлять» у ненайденной строки запоминается как «пропустить»: следующий прайс не предлагает отправить её снова;
  - отклонённый администратором ключ не отправляется повторно по умолчанию.
- **План строки — одна функция** для предпросмотра и применения (I719). Правила предложения — `offerTermsProblem` домена.
- **Применение — фоновая задача** `prices.apply` одной транзакцией с пакетной записью (I720). Обоснование: 50 000 строк — десятки секунд, запрос столько не держится.
- **Журнал** (I722): запись у каждого созданного, изменённого и снятого предложения (автор — сотрудник, `source: price_import`) и одна запись `price_import.applied` с числами.
- **Предложение по одобренному запросу само не создаётся** (I721): цена в старом файле могла устареть, поставщик получает предложение следующей загрузкой.

## Deviations
- **Порог резкой цены.** Задача называет его `price_import_sharp_change_percent`, но в реестре с TASK-007 есть `price_change_threshold_percent` (30 %, группа «Прайс»). Использован он; новой настройки нет.
- **Порог уверенности ИИ.** Это существующая `price_match_confidence_threshold`. Выбор ИИ при любой уверенности остаётся «нужно проверить» (бизнес-правило: совпадения ИИ — только после «Верно»). Порог решает лишь, стоит ли выбор ИИ предложенной позицией.
- **Шаг 3 «тот же поиск, что у поставщика».** Понимание слова то же: ключ `searchKey`, раскладки и транслитерация `searchVariants`, начало слова. Но поиск идёт по индексу в памяти, а не SQL-запросом `itemNameMatches` на каждую строку (производительность). Записано в I711.
- **Компания «только услуги».** Каждая строка товара — ошибка `supplier_type`, применение ничего не создаёт (как в edge case). Строка, сопоставленная с услугой, — ошибка `service_item`.
- **Бренд в форме «Создать позицию».** Подставляется по написанию, только если в строке был бренд. В выгрузке 1С колонки бренда нет — администратор выбирает бренд сам.

## Known Issues / Risks
- **Модели ИИ.** `ai_model_price_match_primary/_fallback` выбраны по образцу перевода (`google/gemini-2.5-flash-lite`, `deepseek/deepseek-v4-flash`). Замера качества сопоставления нет — по задаче это Future (D-058). Настоящая модель в этой задаче не вызывалась ни разу.
- **Память индекса названий.** Индекс держится в памяти worker'а на время одного запуска сопоставления. На справочнике в сотни тысяч позиций его размер стоит измерить.
- **Dev-данные.** В dev остались:
  - 11 позиций справочника, заведённых для сценария;
  - изменённые цены и предложения «Автомаркета»;
  - записи `supplier_sku_mapping` и `catalog_request` моих загрузок.

  Свои промежуточные сопоставления и запросы между прогонами сценария я удалял сам, две цены предложений возвращал через кабинет. Настройки входа (`login_code_resend_interval_seconds`, `login_code_requests_per_phone`) не трогались. Номер и второй фактор администратора Product Owner не использовались.
