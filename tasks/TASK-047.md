# TASK-047 — Импорт прайса: сопоставление со справочником и применение (сервер) + запросы на позиции в админке

Модель: Opus 5.5, High

## Цель

После TASK-046 и TASK-046.A прайс поставщика разобран в строки: цена, наличие, срок, ошибки строк. Эта задача доводит импорт до результата на витрине:
- каждая строка сопоставляется с позицией справочника;
- строки делятся на группы сверки;
- решения поставщика сохраняются;
- одной транзакцией создаются и обновляются его предложения.

Ненайденные позиции уходят администратору запросом на добавление, а в админке появляется экран, где администратор их разбирает.

Экран сверки в кабинете (S-PRICE-03, S-PRICE-04), выгрузка и обратная загрузка — **TASK-048**. Здесь — сервер, контракт и админка. Весь путь проверяется запросами и тестами.

## Требования

### 1. Сопоставление (worker, после `parsed`)

Новый шаг загрузки (состояние `matching`, затем `review`). Строки без ошибок проходят по порядку, первый сработавший шаг решает.

1. **Запомненное сопоставление компании** (`supplier_sku_mapping` по нормализованному артикулу поставщика; без артикула — по нормализованному названию, с предупреждением 12.2) → **уверенно**.
2. **Точный артикул:** `article_norm` + бренд строки (по любому написанию бренда); или единственная позиция с таким артикулом, если бренда нет или он не узнан → **уверенно**. Несколько позиций с этим артикулом и бренд не решает → **нужно проверить** с кандидатами.
3. **Поиск по названию** (тот же поиск, что у поставщика в «Добавить позицию») → кандидаты. Единственный сильный кандидат с совпадающими ключевыми характеристиками → **уверенно** (правило «сильный» — решение агента, в домене, с тестами). Иначе кандидаты передаются ИИ.
4. **ИИ** — новая операция `AiService`:
   - пакеты строк с 1–3 кандидатами каждой, модель выбирает кандидата или «нет в справочнике» с коротким объяснением;
   - модель и запасная — настройки `ai_model_price_match_primary` / `_fallback`; умолчание по образцу перевода, замер — Future;
   - ниже порога уверенности (настройка) → **нужно проверить**, с пометкой «предложено ИИ»;
   - «нет» → **не найдено**;
   - ИИ недоступен или исчерпан дневной бюджет → загрузка ждёт и повторяется сама; запомненное и точный артикул применимы без ИИ (повторный прайс проходит полностью без ИИ).
   - `TestAiGateway` отвечает детерминированно (для dev и тестов); внешних вызовов в тестах нет.
5. **Только допустимое:**
   - кандидаты — активные позиции видимых подкатегорий;
   - тип позиции допустим для типа компании: «только товары» не получает услуги и наоборот;
   - **услуги в импорт прайса не входят** — у них цены по моделям (TASK-019); строка, сопоставленная с услугой, — ошибка строки словами.
6. **Повторы в файле:**
   - один артикул дважды — первая строка решает, остальные — ошибка «повтор строки N»;
   - две разные строки на одну позицию — обе «нужно проверить» с объяснением.
7. **Ход** — в `stats`: сколько сопоставлено и каким шагом, сколько отдано ИИ.

### 2. Группы и пропавшие

- **Группы** — по SCREENS:
  - **уверенно**;
  - **нужно проверить**;
  - **не найдено**;
  - **ошибки в строках**;
  - **пропали из файла** — активные предложения компании (кроме услуг), позиции которых не встретились в файле. По каждой — число активных заявок (нетерминальные статусы); итог «по N позициям есть активные заявки».
- **Строка «уверенно»** показывает «было → стало» (цена, наличие, срок).
- **Резкое изменение цены** — больше порога настройки `price_import_sharp_change_percent` (например, 30 %) относительно текущей цены предложения. Такая строка помечена и **без отдельного подтверждения не применяется** (D-039, D-052).

### 3. Решения поставщика (черновик сверки)

Маршруты кабинета (имена — решение агента):
- **список строк по группе** — страницы, текст строки, кандидаты, «предложено ИИ», «было → стало»;
- **решение по строке:**
  - «Верно» (выбранный кандидат);
  - «Другая позиция» (`itemId` из поиска поставщика, с теми же правилами допустимости);
  - «Пропустить»;
  - «Нет в справочнике»;
  - у резкой цены — «Подтвердить цену»;
  - у не найденной — «Отправить администратору» (по умолчанию включено) или «Не отправлять»;
- **«Пропустить все оставшиеся»** — единственное массовое действие в «нужно проверить» (D-039);
- **выбор по пропавшим** — «Снять с продажи» / «Оставить как есть», одним выбором на всю группу. Без выбора применение отклоняется, если в группе что-то есть.

Решения хранятся на сервере (черновик переживает закрытие страницы), с версией загрузки — устаревшая вкладка получает 409, как в TASK-046.A. Каждое решение записывает, кто его принял.

**Предпросмотр применения** — числа для кнопки S-PRICE-03:
- обновить N;
- создать K;
- снять M;
- отправить на добавление R;
- «N строк не проверены и не будут применены».

### 4. Применение

`POST …/apply` с `expectedVersion` — одна транзакция под блокировкой загрузки; повтор (двойной клик, вторая вкладка) не применяет второй раз.

- **Уверенные и подтверждённые строки:**
  - есть предложение компании на эту позицию — обновляются цена, наличие, срок, свой артикул; снятое — возвращается в продажу (PRODUCT 12.3);
  - нет — создаётся новое: самовывоз, если у точки есть адрес; доставка — по «Доставке по умолчанию» компании; гарантии нет;
  - правила `offers.service.ts` (пределы цены и срока, «под заказ» требует срока > 0, тип компании) — **одна проверка** с выставлением вручную; нарушение — строка в итоге как «не применено» с причиной, остальные применяются;
  - **«нет в наличии» в файле** → предложение снимается с продажи (своя причина снятия), вернётся при следующем прайсе с наличием;
  - **наличия нет в файле** — у существующего предложения не меняется; у нового — «в наличии»;
  - **срока нет** — у существующего не меняется; у нового «под заказ» без срока — строка «не применено».
- **Подтверждённые и уверенные по артикулу** сопоставления → `supplier_sku_mapping` (кто подтвердил, когда); запомненное — `last_used_at`.
- **Пропавшие:** при выборе «снять» — снятие с причиной «нет в новом прайсе». Заявки не трогаются: их снимки не меняются. При «оставить» — ничего.
- **Не найденные с «Отправить администратору»** → `catalog_request` (тип `new_item`): данные строки, компания, строка импорта. Повторный прайс не создаёт второй открытый запрос на тот же артикул компании.
- **Цена «под заказ» и срок** — те же правила, что у ручного выставления. Дата получения у клиента считается как обычно (`receiptDate`).
- **Блокировка компании** (I697) — применение запрещено (403 `SUPPLIER_BLOCKED`, как прочие действия кабинета). Пауза — разрешено (на витрине и так не видно).
- **Журнал действий:**
  - одна запись `price_import.applied` с числами;
  - у предложений — записи изменения с автором-сотрудником, как при правке вручную, и пометкой «из прайса»; можно одной записью на импорт со списком — решение агента, записать;
- **Позиции, ставшие недоступными между сверкой и применением** (архив позиции, скрытая категория), — «не применено» с причиной.
- **Итог** (для S-PRICE-04): обновлено, создано, снято, вернулось в продажу, на добавление отправлено, не применено с причинами. Состояние `applied`.

### 5. Запросы на позиции — админка (A-MOD-01)

**Сервер:**
- список запросов (новые сверху; отборы — состояние, поставщик), карточка — данные строки, поставщик, импорт, похожие позиции (поиск);
- **«Создать позицию»** — создаёт позицию тем же путём, что «Новая позиция» справочника, и связывает запрос: запрос `approved` со ссылкой на позицию, у компании — сопоставление `supplier_sku_mapping`, и следующий прайс применяет строку сам;
- **«Это существующая позиция»** — выбор позиции; сопоставление компании запоминается, запрос `approved`;
- **«Отклонить»** с обязательной причиной — она видна поставщику (S-MOD-01 — TASK-048);
- всё — в журнале.

Предложение по одобренному запросу само не создаётся: цена в старом файле могла устареть. Поставщик получает его следующей загрузкой. Записать в ARCHITECTURE.

Поставщику — маршрут списка своих запросов со статусами и причиной отказа (экран S-MOD-01 — TASK-048).

## Бизнес-правила

- На витрину попадает только то, что поставщик подтвердил или что сопоставлено детерминированно (запомненное, точный артикул и бренд). Совпадения ИИ — только после «Верно» построчно.
- Ошибочный файл не обнуляет витрину: пропавшие снимаются только явным выбором.
- Снятие пропавших и «нет в наличии» не трогает заявки и их снимки.
- Поставщик видит только свои загрузки, строки, предложения и запросы; администратор видит всё.

## Edge cases

- Повторный тот же прайс — всё «уверенно» по запомненному, ИИ не вызывается, сверка — ноль строк «нужно проверить».
- Прайс, где у половины строк сменился бренд на написание другого регистра или на кириллицу («Джили») — точный артикул по любому написанию бренда.
- Артикул существует у двух брендов, бренда в файле нет — «нужно проверить» с двумя кандидатами, ИИ не нужен.
- Коллега поменял цену предложения вручную после сверки — применение берёт текущую цену для проверки резкого изменения. Строка, ставшая резкой, не применяется без подтверждения (в итоге — «требует подтверждения цены»).
- Два сотрудника одновременно применяют одну загрузку — ровно одно применение, второй получает 409 с тем, кто применил.
- Применение 50 000 строк — укладывается в разумное время, без зависания API (замер в отчёте). При необходимости — пакетами внутри одной транзакции или фоновой задачей со статусом `applying`. Решение агента, записать.
- ИИ недоступен — загрузка в `matching` ждёт, известное уже разложено; после восстановления продолжает сама.
- Позиция архивирована администратором во время сверки — строка «не применено».
- У компании «только услуги» прайс товаров — каждая строка с товаром — ошибка строки «тип компании», применение ничего не создаёт.
- Пропавших много (поставщик загрузил половину прайса) — выбор обязателен, «Оставить как есть» ничего не снимает.
