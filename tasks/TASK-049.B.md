# TASK-049.B — Отзывы и жалобы: экраны приложения

Модель: Opus 5.5, High

## Цель

TASK-049 сделала отзывы и жалобы на сервере и в админке: проверка до публикации, очереди, решения администратора. В приложении их пока нет — заявка возвращает `canReview`, `review`, `complaint`, `complaintReasons`, но кнопок «Оценить» и «Пожаловаться» не видно.

После этой задачи пользователь в приложении:
- оценивает поставщика по выданной заявке;
- видит судьбу отзыва;
- если текст отклонён — исправляет его один раз или публикует только оценку;
- жалуется и видит, что жалоба рассмотрена.

Только экраны. Сервер и контракт меняются, если найдётся дыра; любое изменение — аддитивно.

## Контекст

**Экраны и тексты (SCREENS):**
- **M-ORD-02** — в истории «у закрытых без отзыва — «Оценить»».
- **M-ORD-03:**
  - действия завершённой заявки — «Оценить поставщика», «Пожаловаться», «Повторить заказ»;
  - у закрытой (выданной) — заметная строка T-ORD-08 «Не получали товар? Сообщите нам» → M-ORD-06;
  - без сети — действия неактивны с «Нужна сеть».
- **M-ORD-05 «Оценка поставщика»:**
  - звёзды 1–5 обязательно, текст по желанию, T-ORD-09, «Отправить»;
  - после — T-REV-01 «Спасибо! Отзыв появится после проверки»;
  - на заявке «Отзыв на проверке» / «Отзыв опубликован»;
  - не прошёл — T-REV-02 «Отзыв не опубликован: {причина}. Исправьте текст или опубликуйте только оценку» с действиями «Исправить текст» (один раз) / «Опубликовать только оценку»;
  - тестовый заказ — вместо кнопки «Отзыв недоступен: это тестовый заказ»;
  - один отзыв на заявку, после публикации не редактируется.
- **M-ORD-06 «Жалоба»:**
  - причины «Не получил товар или услугу» / «Товар не соответствует» / «Цена выше клубной» / «Поставщик не выходил на связь» / «Другое»; текст; «Отправить»;
  - после — «Спасибо. Администратор клуба рассмотрит обращение»;
  - на заявке «Жалоба на рассмотрении» / «Жалоба рассмотрена».

**Сервер TASK-049** (ARCHITECTURE 4.69, I737–I752):
- `POST /reviews`, исправление и «только оценка», `POST /complaints`;
- в `UserOrder` — `canReview`, `review` (`status`, `rejection`, `canEditText`, `canPublishScoreOnly`), `complaint`, `complaintReasons` (пусто — жаловаться нельзя);
- тестовая заявка — `REVIEW_NOT_ALLOWED {reason: test_order}`;
- коды `REVIEW_*` / `COMPLAINT_*`, пределы, длины — настройки (`review_text_max_length`, `complaint_text_max_length`).
- **Что видит автор:** `checking` и `held` — «на проверке»; `hidden` — «опубликован» (I742).

**Приложение:**
- `apps/mobile/src/screens/orders/OrderScreen.tsx` — комментарий: «Оценить» и «Пожаловаться» — этап C;
- история заявок;
- `useRequest` / `DataState`, загрузка без мигания (D-069);
- шторки и диалоги дизайн-системы, движение (`motionPlan`), копия активных заявок без сети;
- образцы — экран оформления и ответ на другой срок (TASK-039).

## Требования

### 1. Оценка (M-ORD-05)

- **Вход:**
  - «Оценить поставщика» в действиях выданной заявки (M-ORD-03);
  - «Оценить» в строке истории (M-ORD-02) у тех, где `canReview`.
  
  Экран — свой экран стека заявки: поверх, системный «назад».
- **Содержимое:**
  - **звёзды 1–5** — крупные, доступные пальцем и читалке экрана: «Оценка 4 из 5»;
  - **текст** — по желанию, многострочный, счётчик длины по настройке сервера;
  - T-ORD-09 под полем;
  - «Отправить» неактивна без оценки.
- **Отправка:**
  - ключ повтора — один на экран (как при оформлении): повтор после потерянного ответа не создаёт второй отзыв;
  - отказ сервера — словами: уже есть, тестовый заказ, не выдана, предел, длина, нет сети.
- **После:** T-REV-01, возврат на заявку.
- **На заявке — блок отзыва по `review.status` (видимому автору):**
  - «Отзыв на проверке» со звёздами и текстом;
  - «Отзыв опубликован»;
  - T-REV-02 с причиной словами (четыре причины SCREENS) и кнопками «Исправить текст» (если `canEditText`) и «Опубликовать только оценку» (если `canPublishScoreOnly`).
- **«Исправить текст»:**
  - тот же экран: оценка только для чтения, текст заполнен прежним, подсказка «Исправить можно один раз»;
  - отправка → снова «на проверке».
- **«Опубликовать только оценку»** — подтверждение «Текст не будет опубликован» → «Отзыв опубликован».
- **Тестовый заказ** — вместо кнопки строка «Отзыв недоступен: это тестовый заказ». Признак — от сервера: поле или отказ `test_order`. Своего расчёта на клиенте нет. Если поля в `UserOrder` нет — добавить аддитивно (решение агента, записать).

### 2. Жалоба (M-ORD-06)

- **Вход:**
  - «Пожаловаться» в действиях (если `complaintReasons` не пуст);
  - заметная строка T-ORD-08 у выданной заявки → тот же экран сразу с причиной «Не получил товар или услугу».
- **Содержимое:**
  - причина — список из `complaintReasons` (только разрешённые сервером сейчас), подписи словами;
  - текст — обязателен для «Другое», для прочих по желанию, счётчик длины;
  - «Отправить».
- **После:** «Спасибо. Администратор клуба рассмотрит обращение», возврат на заявку.
- **На заявке:** «Жалоба на рассмотрении» / «Жалоба рассмотрена» с причиной. Пока жалоба открыта, «Пожаловаться» не показывается (сервер вернёт пустой `complaintReasons`).
- **Отказы словами:** уже есть открытая, заявка ещё не принята, предел, длина, сеть.

### 3. Состояния и согласованность

- **Без сети** (копия активных заявок) — «Оценить», «Пожаловаться», «Исправить» неактивны с «Нужна сеть»; блоки отзыва и жалобы — из последнего ответа, если есть.
- **Режим «только просмотр»** (M-START-03 «нужно обновить») — без действий.
- **Обновление при возврате на заявку и из фона** — как у остальных экранов заявки: администратор решил, и при следующем открытии видно.
- **Гость и пользователь без клубного доступа** свою выданную заявку видят и оценивают так же: доступ к отзыву не зависит от подписки. Если сервер решает иначе — следовать серверу, записать.
- **Тексты** — kk/ru/en; SCREENS — дословно.
- **Логика экранов** («что показать на заявке» по `review` и `complaint`, доступность кнопок, причины словами) — чистые функции с тестами в `apps/mobile` (как `orders/*-rules`).

### 4. Попутно: плавающий тест фоновых задач

`apps/api/src/jobs/jobs.integration.test.ts` «never runs a singleton job twice at a time, whichever worker takes it» дважды подряд падал в CI (приёмки TASK-047 и TASK-049): за 40 с singleton-задачу брал только один из двух worker'ов (`expected Set{'second'} to deeply equal Set{'first','second'}`); перезапуск — зелёный, локально — зелёный.

Суть теста — singleton не выполняется дважды одновременно. Проверка «взяли оба» подтверждает, что гонка двух worker'ов вообще была. Сделать её детерминированной, **не ослабляя**: например, на время остановить опрос одного worker'а, чтобы задачу обязательно взял второй, затем вернуть. Решение агента — записать в отчёт.

Сначала проверить, не связано ли это с `localConcurrency` у задач (TASK-046.A, `job-runner.service.ts`). Если связано — чинить причину, а не тест.

## Не входит

- push P-REV-01 и P-ORD-06 — TASK-051;
- рейтинг, «Новый поставщик», страница поставщика с отзывами (M-CAT-09) — TASK-050;
- ответ поставщика на отзыв — вне MVP.

## Edge cases

- Отправил отзыв, ответ потерян, нажал ещё раз — один отзыв (ключ повтора).
- Отзыв отклонён, пользователь исправил, новый текст снова отклонён — на заявке только «Опубликовать только оценку».
- Жалоба решена — снова можно пожаловаться (сервер вернул причины).
- Заявка услуги (выполненная запись) — «Оценить» так же. «Не получил товар или услугу» подходит по тексту.
- Очень длинный текст на казахском — поле и счётчик не ломают раскладку на маленьком экране.
- Системный размер шрифта «крупный» — звёзды и кнопки не перекрываются (проверяется на телефоне; в браузере — масштабом).

## Что должно реально работать

Тестовый пользователь с клубным доступом получает товар у «Автомаркета». В приложении на заявке он нажимает «Оценить поставщика», ставит 2 звезды, пишет критику — «Спасибо! Отзыв появится после проверки», а через пару секунд на заявке — «Отзыв опубликован».

Второй раз он пишет отзыв с названием поставщика. Администратор отклоняет текст — на заявке появляется «Отзыв не опубликован: название поставщика…». Пользователь исправляет текст, но администратор отклоняет и его, и пользователь публикует только оценку.

По третьей заявке он нажимает «Не получали товар? Сообщите нам». Жалоба «на рассмотрении», а после решения администратора — «рассмотрена».
