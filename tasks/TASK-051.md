# TASK-051 — Push-уведомления пользователю: токены устройств, отправка, подтверждение, разрешение в приложении

Модель: Opus 5.5, High

## Цель

Пользователь узнаёт о событиях своей заявки, только открывая приложение: заявки обновляются при старте, возврате из фона и вытягиванием (4.46 I443), опроса по таймеру нет, а строка M-ORD-03 «Сообщим, когда можно забирать» заменена на «статус заявки изменится», потому что присылать нечем (D-066, I455). Поставщик при этом получает WhatsApp о каждом шаге.

Задача делает push пользователю по PRODUCT 15 и SCREENS 8.4 (P-ORD-01…09, P-REV-01, P-SUB-01), шторку разрешения M-PUSH-01 после первой заявки (D-066) и строку push в M-PRO-04. После неё:
- каждое событие заявки, отзыва и оплаты, перечисленное в SCREENS 8.4, уходит push на язык пользователя, и нажатие открывает заявку;
- сервер знает, какие push подтверждены приложением (ack) — на этом TASK-052 построит резерв WhatsApp;
- внешних вызовов в dev, тестах и CI нет: провайдер за портом, как у сообщений поставщикам и платежей.

## Требования

### 1. Порт провайдера и тестовая реализация

- Порт `PushProvider` в новом модуле `apps/api/src/modules/notifications` (имя — на усмотрение): отправить одно уведомление на один токен и вернуть исход — `sent` с идентификатором провайдера, `invalid_token` (токен мёртв: `UNREGISTERED`/`INVALID_ARGUMENT`), `unavailable` (повторить позже), `rejected` (не повторять), `unknown` (запрос мог дойти, ответа нет).
- **`TestPushProvider`** — для dev, тестов и CI: ничего никуда не отправляет, запоминает отправленное, режимы отказов через `PUSH_TEST_MODE` (как `MESSAGE_TEST_MODE`), страница `http://localhost:3000/dev/pushes` только при тестовом провайдере (последние уведомления: вид, язык, заголовок и текст, данные, токен маской, статус, ack).
- **Настоящий провайдер** — по ARCHITECTURE 9.3: FCM HTTP v1 (Android и iOS через APNs) на стандартном `fetch` без SDK, OAuth2-токен сервисного аккаунта подписывается `node:crypto`. Переменные — `PUSH_PROVIDER=test|fcm`, учётные данные FCM — только в `.env` (в `.env.example` — имена и формат); production с тестовым провайдером не стартует (как у сообщений). Класс проверяется на подменённом `fetch` (форма запроса, разбор исходов, истечение OAuth-токена); **вживую не вызывается** — у проекта нет проекта Firebase, это честно пишется в отчёт. Если есть веская причина выбрать Expo Push Service вместо FCM напрямую — решить и записать в ARCHITECTURE с причиной; порт от этого не зависит.

### 2. Токены устройств

- Маршрут мобильной сессии: зарегистрировать или обновить токен устройства (`platform` ios/android, сам токен, при желании — модель устройства без персональных данных). Токен привязан к **сессии** и учётной записи: конец сессии (выход, «Завершить на всех других», завершение администратором, истечение) снимает токен с рассылки сразу — на устройство, где человек вышел, push не приходит. Вход другим номером на том же устройстве переносит токен к новой учётной записи.
- Мёртвый токен (`invalid_token` от провайдера) деактивируется; активные токены других устройств того же человека продолжают получать.
- Токен нигде не показывается целиком (логи, журнал, админка, отчёт) — только маска; в санитайзер наблюдаемости добавить поле.
- Уборка неактивных токенов — периодической задачей по сроку из настройки.

### 3. Единственный вход и журнал

- **`Notifications.enqueue(tx, …)`** — единственный способ поставить push из модулей: вид (из `notificationKinds` реестра настроек, вынести в одно место — контракт или домен; добавить `review_text_rejected` и, если решите слать, `supply_overdue`), получатель (`accountId`), субъект (заявка, отзыв, подписка), подстановки, `dedupeKey`. Ставится **в транзакции породившего события**: откат события уносит уведомление; одно событие — одному получателю — одно уведомление (уникальность ключа в базе), в том числе при повторе действия и при двух worker'ах.
- Таблица `notification` по ARCHITECTURE 5 (поля `fallback_of_id`, `acked_at` — заводятся сейчас, резерв их заполнит в TASK-052). Решить и записать: одна строка на получателя-событие, а доставки по устройствам — в отдельной таблице или в полях; ack любым устройством подтверждает уведомление.
- **Отправка** — задача worker'а в три шага, как у сообщений: занять строку на срок, вызвать провайдера **без открытой транзакции и без блокировки строки**, записать исход. `unavailable` — повторы по настройкам (число и пауза, нарастающая), затем мёртвая очередь; `rejected` — один раз; `unknown` — статус `unknown`, второй копии нет, решает человек (`push:retry`); прерванная попытка (процесс убит) — свипер восстанавливает по сроку захвата, как `messaging.recover-interrupted`. Статус только вперёд.
- **Тексты** — данные кода (`push-templates.ts`): kk/ru/en по SCREENS 8.4, заголовок и текст, подстановки проверяются при старте и в `pnpm test` (полнота языков, совпадение подстановок, длина). Язык — язык учётной записи (`account.language`), без него — русский. **Без клубного доступа на момент отправки вместо названия поставщика — «Поставщик»**: правило берётся у `order-views.ts` (что пользователь видит о поставщике своей заявки), второго правила не заводить.
- **Содержимое push** — только то, что в SCREENS: ни кода заявки, ни QR, ни телефона, ни адреса, ни имён сотрудников. Данные для открытия — тип экрана и идентификатор (`PushTarget`: `{ screen: "order", params: { orderId } }`; подписка — экран подписки). Ни в логах, ни в мониторинге содержимого нет (санитайзер).
- **Метрики** — по видам и статусам, доля неподтверждённых за окно; команды оператора `push:list`, `push:retry <id>`, `push:status`.

### 4. События, которые шлют push

Через `Notifications.enqueue` в той же транзакции, что и переход (`OrderTransitions.apply`, свипер сроков, сервис отзывов, события подписки):

| Событие | Шаблон | Вид |
|---|---|---|
| Принята (товар в наличии) | P-ORD-01 | `order_accepted` |
| Готова к выдаче (в наличии и под заказ — резерв до …) | P-ORD-02 | `order_ready` |
| Резерв истекает (заметка `reserve_expiring` свипера) | P-ORD-03 | `reserve_expiring` |
| Отказ поставщика (до и после принятия) | P-ORD-04 | `order_declined` |
| Предложен другой срок (под заказ) или время (услуга) | P-ORD-05 | `term_proposed` / `time_proposed` |
| Закрыта: по коду, поздно, администратором без кода | P-ORD-06 | `order_closed` |
| Поставщик не ответил вовремя — отменена | P-ORD-07 | `order_expired_no_response` |
| Срок подтверждён (под заказ) | P-ORD-08 | `order_confirmed` |
| Время подтверждено (услуга) | P-ORD-09 | `order_confirmed` |
| Отзыв не опубликован — текст отклонён | P-REV-01 | `review_text_rejected` |
| Подписка пользователя: проблема с оплатой (`grace_started`, аудитория `user`) | P-SUB-01 | `payment_failed` |

- Действия самого пользователя (отмена, согласие с новым сроком) push не дают. Истечение резерва (`reserve_expired`), истечение времени ответа клиента, отмена администратором и «срок поставки прошёл» в SCREENS 8.4 текстов не имеют: **не присылать** и перечислить в отчёте с предлагаемыми текстами на утверждение Product Owner — кроме «срок поставки прошёл», который ARCHITECTURE 4.59 обещал этой задаче: прислать с текстом в духе соседей (в приложении уже есть «Срок поставки прошёл — свяжитесь с поставщиком») и тоже вынести на утверждение.
- Поставщику ничего не меняется (его канал — WhatsApp). Тестовая заявка сотрудника у своей компании push получает как обычная — это заявка пользователя.
- Один и тот же переход двумя сотрудниками (гонка, `late_action_ignored`) — один push.

### 5. Подтверждение (ack)

- `POST /notifications/{id}/ack` — мобильная сессия, только своё уведомление (чужое и несуществующее — одинаковый 404), повтор — не ошибка. Открытие экрана заявки подтверждает все неподтверждённые уведомления этой заявки (отдельный маршрут или параметр — решить; клиент не перечисляет идентификаторы, которых не получал).
- Приложение подтверждает: при получении push в фоне (background handler, где платформа будит), при нажатии и при показе экрана заявки. Без сети — при следующем открытии.
- Резерв по таймауту **не делается** (TASK-052), но `acked_at` и доля неподтверждённых в метриках — уже здесь.

### 6. Приложение

- **Модуль push** (`services/push.ts` или подобное) за своим портом: разрешение, получение токена, подписка на получение и нажатие, передача на сервер. Нативный модуль `expo-notifications` изолирован: под `react-native-web` и в тестах приложение работает без него (порт с заглушкой), а в Expo Go на телефоне отсутствие токена (Expo Go не даёт токен FCM на Android; на iOS — проверить) — не ошибка: приложение работает, сервер ничего не получает. Разрешение не запрашивается нигде, кроме шторки M-PUSH-01 и «Открыть настройки» в M-PRO-04.
- **M-PUSH-01** — после успеха M-ORD-01 (товар, под заказ, услуга): первая заявка этой учётной записи на этом устройстве **и** push не разрешены → шторка с T-ORD-10, «Включить» → системный запрос, «Не сейчас» → повтор после следующей заявки, **не больше двух раз** (счёт — на устройстве, на учётную запись). Уже разрешено или отказано системой насовсем — шторки нет. Текст — kk/ru/en (казахский — рабочий, на проверку носителем).
- **Регистрация токена** — после разрешения, при старте с разрешением, при входе и при смене токена платформой; выход — снятие (сервер делает это и сам по концу сессии).
- **Нажатие на push** — M-ORD-03 этой заявки (холодный старт — через `decideStart` правило 6 → `rootStart`: заменить заглушку «каталог» на экран заявки; если человек не вошёл или заявка не его — обычный старт); P-SUB-01 — экран подписки профиля (M-SUB-02 нет до TASK-041 — записать отклонение). В «только просмотре» (M-START-03) — открыть заявку из копии.
- **Получение в открытом приложении** — обновить копию заявок (`OrdersCopyProvider.refresh`) и открытый экран заявки; показывать ли системный баннер поверх открытого экрана той же заявки — решить, записать. Получение в фоне — обновить копию, если платформа дала выполнить (R18: QR отменённой заявки не должен жить в копии дольше, чем нужно).
- **M-PRO-04** — пункт «Уведомления» в профиле вошедшего: push «Включены» / «Выключены — статус заявок смотрите в приложении», «Открыть настройки» (системные настройки приложения). Строка резервного канала и «Напоминания о замене» — не сейчас.
- Строки M-ORD-03 «статус заявки изменится» (I455) вернуть к SCREENS («Сообщим, когда можно забирать» и подобные) **только там, где push теперь действительно уходит** и только для человека с разрешёнными push; иначе прежний честный текст.

### 7. Сервер, контракт, списки

- Маршруты — мобильная сессия (`auth: "session"`, контекст `user`); кабинет и админка — 403. Контракт — аддитивно. Новые фоновые задачи — в `apps/api/src/testing/expected/background-jobs.ts`, миграции — в `expected/migrations.ts`, таблицы — в `orm-tables.ts`.
- `.env.example` — новые переменные с описанием; `AI_PROVIDER`-подобный разбор в `env.schema.ts` с проверкой production.
- Админки в задаче нет (A-SET-03 «Шаблоны уведомлений» — не сейчас: шаблоны — данные кода, как у WhatsApp). В карточке пользователя во вкладке «Сессии» можно показать «push: есть» у устройства — по желанию, если это одна строка.

## Не входит

- Резерв WhatsApp для пользователя, `push_unreliable`, отметка «нет WhatsApp» (TASK-052) — но таблица и ack готовы к нему.
- Напоминания о ТО (P-REM-01/02), экраны оплаты (M-SUB-01/02, TASK-041), сборки для сторов и живая проверка на устройстве с настоящим FCM (TASK-056).
- Переключатель видов уведомлений (M-PRO-04: по заявкам и оплате не отключаются).
- Тексты SCREENS. Где текста нет — писать в духе соседних и перечислить в отчёте на утверждение Product Owner.

## Acceptance Criteria

1. **Каждое событие — ровно одно push.** Интеграционный тест (настоящие API и два worker'а, тестовый провайдер): для каждого события таблицы п. 4 — один push получателю на его языке с текстом по SCREENS 8.4 (kk, ru, en — по одному примеру каждого языка), с `PushTarget` на заявку; действия самого пользователя — ни одного; гонка двух сотрудников (как в `order-notices`) — один push; откат транзакции события — уведомления нет; повтор задачи — второй копии нет.
2. **Содержимое.** Ни в одном push, журнале, логе и мониторинге — кода заявки, QR, телефона, адреса, имени сотрудника, полного токена (`captureOutput` и проверка `payload`); без клубного доступа — «Поставщик» вместо названия тем же правилом, что в `order-views`.
