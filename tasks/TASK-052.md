# TASK-052 — Резерв WhatsApp для пользователя: критичные события без подтверждения push, ненадёжный push, пользователь без WhatsApp

Модель: Opus 5.5, High

## Цель

После TASK-051 пользователь получает push о событиях заявки, отзыва и оплаты, а сервер знает, подтвердило ли приложение получение (ack). Но push — канал без гарантии: телефон выключен, приложение удалено, разрешение не дано или система не разбудила приложение. Для критичных событий (поставщик принял, отказал, предложил другой срок, резерв заканчивается, заявка закрыта, проблема с оплатой) это означает, что человек узнаёт о них, только открыв приложение, — хотя у него есть WhatsApp, которым он входил.

Задача делает уровень 3 схемы ARCHITECTURE 9.3: критичное уведомление, которое приложение не подтвердило за `push_ack_timeout_minutes`, или которое некуда было отправить, дублируется одним WhatsApp-сообщением через уже существующий шлюз сообщений; пользователь, у которого push раз за разом не подтверждается, получает критичное сразу в WhatsApp; пользователь без WhatsApp резерва не получает и видит об этом строку в профиле. После неё:
- ни одно критичное событие не остаётся незамеченным дольше таймаута, если у человека есть WhatsApp;
- каждое событие даёт не больше одного резервного сообщения — при любых гонках, повторах задач и двух worker'ах;
- резерв стоит денег (PRODUCT 15), поэтому он идёт только по списку критичных видов, только по не подтверждённым push и только пока событие ещё актуально; администратор и оператор видят, сколько резерва уходит и кому.

## Требования

### 1. Когда уходит резерв

Единое правило в одном месте (чистая функция, таблица случаев в юнит-тесте), которое применяет свипер `notifications.fallback` (раз в минуту, как остальные свиперы):

| Состояние push критичного вида | Резерв |
|---|---|
| `sent`, ack нет, прошло `push_ack_timeout_minutes` от `sent_at` | уходит |
| `sent`, ack есть | не уходит никогда |
| `no_device` (нет активного токена: разрешения нет, вышел, приложение удалено) | уходит сразу, без ожидания |
| `failed` (все устройства отказали окончательно) | уходит сразу |
| `unknown` | как `sent` — после таймаута |
| `queued` (ещё отправляется, повторы `unavailable`) | ждёт исхода; если и через таймаут от создания исхода нет — уходит |
| `cancelled` (сессия кончилась до отправки) | как `no_device` |
| получатель `push_unreliable` | критичное уходит сразу при постановке push, не дожидаясь таймаута |
| получатель без WhatsApp | не уходит; уведомление помечается, что резерв невозможен |
| вид не из `critical_notification_kinds` | не уходит никогда |
| **событие уже не актуально** — у того же субъекта есть более позднее уведомление (заявка принята, а потом уже готова или закрыта) | уходит только последнее актуальное; устаревшее помечается, что резерв не нужен |

- Один push — не больше одного резерва: ключ резервной строки — от исходного уведомления (`fallback_of_id` уникален), сообщение шлюза — с `dedupeKey` от него же; два worker'а и повтор свипера второй копии не дают.
- Изменение `push_ack_timeout_minutes` и списка видов действует со следующего прохода свипера; ack, пришедший после отправки резерва, ничего не отменяет (дубль — известное ограничение 9.3).
- Резерв не зависит от клубного доступа: заявка есть — человек должен о ней знать (как копия заявок, 4.33).

### 2. Как уходит резерв

- Резерв — строка `notification` с `channel = whatsapp`, `fallback_of_id` → исходное push-уведомление, тем же видом, субъектом и подстановками; отправляется **только через `Messaging.enqueue(tx, …)`** существующего шлюза (новых каналов, провайдеров и переменных окружения нет; production с тестовым каналом по-прежнему не стартует). Статусы доставки шлюза (`sent`, `delivered`, `read`, `failed`, `unknown`) отражаются на резервной строке через `MessageSubjects` (субъект `notification`: `stillSend` — ещё актуально и у получателя есть WhatsApp; `onResult` — записать исход).
- **Шаблоны пользователю** — новые записи реестра `message-templates.ts` на kk и ru (en получателю — ru, Meta-шаблоны по языкам; записать), категория utility, без кнопок, по одному на критичный вид: заявка принята, отказ, другой срок / время, резерв заканчивается, заявка закрыта, проблема с оплатой подписки (и `order_ready`, `order_confirmed`, `order_expired_no_response`, `supply_overdue`, `review_text_rejected` — шаблоны завести, чтобы администратор мог включить вид в список; в умолчании их нет). Тексты — в духе P-ORD-*, с подписью клуба и фразой «Подробнее — в приложении»; **содержимое то же, что у push**: ни кода, ни QR, ни телефона, ни адреса, ни имён сотрудников; без клубного доступа — «Поставщик» тем же правилом `order-views`. Идентификаторы — `U-ORD-01…`, `U-SUB-01` по образцу 8.5; все тексты — в отчёт на утверждение Product Owner (одобрение Meta — позже, с первой живой отправкой).
- Номер получателя — номер учётной записи; в журнале, логах и `/dev/messages`-подобных страницах — маска, как у сообщений поставщикам.
- Ограничение частоты резерва на одного получателя — настройка (например, не больше N резервных сообщений в сутки на учётную запись, сверх — только push и отметка в журнале); значение по умолчанию — щедрое, цель — защита от сбоя, а не экономия.

### 3. Ненадёжный push и пользователь без WhatsApp

- **`push_unreliable`**: получатель, у которого **три критичных push подряд** ушли в резерв по таймауту (ack не пришёл), помечается ненадёжным — следующие критичные уведомления получают резерв сразу при постановке (push при этом тоже отправляется). Любой ack снимает отметку. Число — настройка. Состояние хранится у учётной записи в одном месте (поле или маленькая таблица состояния уведомлений — решить, записать), меняется только модулем уведомлений.
- **Нет WhatsApp**: отметка ставится, когда (а) код входа подтверждён через SMS (`phone_verification.channel = sms` — читать уже записанное, не заводить второй путь), (б) шлюз ответил `no_whatsapp` на любое сообщение этому номеру. Снимается при успешной доставке в WhatsApp этому номеру — кодом входа или сообщением. Для такого пользователя резерв не ставится, SMS не отправляется, push идёт как обычно.
- Оба состояния видны: приложению — через профиль (строка M-PRO-04), администратору — в карточке пользователя («WhatsApp: нет с {дата}», «push не подтверждается с {дата}») и отбором списка «нет WhatsApp» (`A-USR-01`), оператору — в `push:status`.

### 4. Приложение (M-PRO-04)

- Вторая строка пункта «Уведомления»: «Если push не дойдёт, важное продублируем в WhatsApp» — когда у человека есть WhatsApp; T-PRO-03 «WhatsApp не подключён — важные события смотрите в приложении» — когда нет. Состояние — от сервера (аддитивное поле профиля или ответа состояния уведомлений), без сети — последнее известное. Тексты kk/ru/en (казахский — рабочий, на проверку).
- Ничего другого в приложении не меняется; экраны оплаты и настройки видов — не сейчас.

### 5. Наблюдаемость и оператор

- Метрики: число резервных сообщений по видам и исходам, доля критичных push, ушедших в резерв, за окно `push_unacked_window_hours`; число пользователей `push_unreliable` и «без WhatsApp».
- `push:status` — те же числа словами; `push:list` — у уведомления видно, ушёл ли резерв и чем кончился; `/dev/pushes` — резервная строка рядом с исходной.
- Сигнал администратору (`AdminSignals`) — если доля резерва за окно выше порога-настройки: один открытый сигнал, закрывается сам, когда доля вернулась ниже (как `whatsapp_outage`); «Открыть объект» — пока некуда, достаточно текста.

### 6. Сервер, контракт, списки

- Новые маршруты, если понадобятся, — мобильная сессия; админские — в `apps/api/src/testing/expected/admin-routes.ts`; контракт аддитивно, `openapi:generate`.
- Новая задача — в `expected/background-jobs.ts`, миграция — в `expected/migrations.ts`, таблицы — в `orm-tables.ts`; `TRUNCATE_ALL` в `testing/database.ts`.
- Постановка резерва — в транзакции прохода свипера (откат — ничего не ушло); сообщение шлюза — там же, `dedupeKey` от резервной строки. Если постановка задачи шлюза в той же транзакции даёт ту же гонку, что I865, — применить то же решение и записать.

## Acceptance Criteria

1. **Правило резерва.** Юнит-таблица на все строки таблицы п. 1; интеграционный тест (настоящие API и два worker'а, тестовый провайдер push и тестовый канал сообщений): критичный push без ack через таймаут (настройка 1 минута, время — сдвигом `sent_at`, а не ожиданием) — ровно одно WhatsApp-сообщение на `/dev/messages`-эквиваленте с `fallback_of_id`; ack до таймаута — ни одного; `no_device` — сразу; некритичный вид — никогда; событие, которое успело устареть (принята → готова), — резерв только по последнему; два worker'а и повтор свипера — одна копия; откат прохода — ничего.
2. **Содержимое.** В резервном сообщении, его подстановках, журнале и выводе процесса (`captureOutput`) — ни кода, ни QR, ни телефона, ни адреса, ни имён сотрудников, ни полного номера получателя; без клубного доступа — «Поставщик».
3. **Ненадёжный push.** Три критичных подряд без ack → отметка, четвёртое — резерв сразу при постановке; ack снимает отметку; настройка числа действует.
4. **Без WhatsApp.** Вход по SMS → отметка, резерв не ставится, уведомление помечено «резерв невозможен», push идёт; `no_whatsapp` от шлюза → то же; успешная доставка в WhatsApp (код входа или сообщение) снимает; админка — карточка и отбор «нет WhatsApp»; `GET /account/profile` (или ответ состояния) — поле для M-PRO-04; кабинет и админка на мобильных маршрутах — 403.
5. **Шлюз.** `stillSend` отказывает устаревшему резерву (заявка закрыта, пока сообщение ждало повторов `unavailable`); исходы `failed`/`unknown` записаны на резервной строке; `messages:retry` работает как для сообщений поставщикам; ограничение частоты на получателя — 429-подобный отказ в журнале, не ошибка события.
6. **Приложение в браузере** (`mobile-web`, `api-test-ai`, `worker-test-ai`, кабинет): вошедший с WhatsApp видит в M-PRO-04 «Если push не дойдёт, важное продублируем в WhatsApp»; вход тестовым номером по SMS (`LOGIN_CODE_TEST_FAILING_CHANNELS=whatsapp`) → T-PRO-03; сценарий «принял в кабинете → ack не пришёл → через таймаут (1 минута) резервное сообщение на `/dev/messages` с текстом U-ORD-01» — описать фактами, с идентификаторами.
7. **Наблюдаемость.** `/metrics` — новые метрики; `push:status` — доля резерва и число помеченных; сигнал при доле выше порога открывается и закрывается сам.
8. **`ARCHITECTURE.md`** — версия по порядку: новый раздел 4.x (правило, таблица, шаблоны пользователю, состояния получателя, частота, сигнал), обновить 9.3 («реализовано»), 5 (`notification` — что из задуманного сделано иначе), 14 (новые настройки), I866 — что закрыто; `CLAUDE.md` блок 0 — «Резерв WhatsApp для пользователя в dev» (как увидеть резерв за минуту, как пометить «нет WhatsApp», команды).
