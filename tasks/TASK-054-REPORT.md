## Result
- Очередь автоперевода идёт по важности для покупателя: сначала структура (категории, характеристики, варианты списков и элементы регламентов ТО), затем позиции с предложением на витрине, затем остальные позиции. ## Technical Decisions
В ARCHITECTURE добавлен раздел 4.97, строки I1205–I1220; версия и история не менялись. Главное:
- **Приоритет хранится в задаче и поддерживается минутной задачей.** Выбор пакета идёт по одному индексу и предложений не касается.
  - Каталог не может зависеть от предложений, поэтому правило витрины передаётся через существующий реестр `CatalogItemListRules`, как это уже сделано для «есть предложения» (I556).
  - Обработчик минутной задачи живёт в модуле предложений.
- **Порядок групп строгий, без «старения».** Нижняя группа берётся, когда верхние пусты (I1208).
- **Массовый повтор идёт путём оператора, порциями.** Каждая порция записывается в журнал в своей транзакции (I1216).
- **Ответ очереди расширен аддитивно.** `openapi:compat` — совместимо.
- **Маршрут `/admin/translations/retry-failed` не начинается с `/admin/catalog`**, поэтому счётчики маршрутов справочника в `catalog.integration.test.ts` и `catalog-items.integration.test.ts` не изменились. Маршрут добавлен в `expected/admin-routes.ts` и в тест доступа переводов.

### Замер выбора пакета и минутного обхода (AC-2)
- **База:** своя `adclub_t054` в `adclub-dev-postgres-1` (PostgreSQL 16). Мигрирована, заполнена `dev:compatibility:seed` и `dev:suppliers:seed`.
- **Данные:** 25 000 активных позиций; 50 000 задач позиций (kk и en); 400 задач структуры; у 5 000 позиций есть предложение «Автомаркета» с часами работы.
- **Запрос выбора** — как в `claim`: `UPDATE … WHERE id IN (SELECT id … ORDER BY priority, updated_at, id LIMIT 20 FOR UPDATE SKIP LOCKED)`. Снимался `EXPLAIN (ANALYZE, BUFFERS)` в транзакции, которая потом откатывалась.
- **План:** `Limit → LockRows → Index Scan using translation_task_claim_idx` (20 строк, `shared hit=22`), затем `Index Scan using translation_task_pkey` для обновления.

| Случай | Время исполнения | 5 прогонов без EXPLAIN |
|---|---|---|
| До обхода | 1,18 мс | 1,2–4,6 мс |
| После обхода (10 000 задач в группе 1, структура убрана) | 0,67 мс | 0,9–1,1 мс |
| Худший: первые 45 000 строк индекса арендованы другими запусками (`Rows Removed by Filter: 45000`) | 45,4 мс | 32–45 мс |

Минутный обход:
- первый проход поднял 10 000 задач за 4,75 с;
- повторные проходы ничего не меняли и заняли 3,95 и 4,24 с (25 страниц);
- страница позиций — `Index Only Scan using translation_task_pending_item_idx → Unique`, 1,06 мс;
- запрос страницы с правилом витрины и обновлением — порядка 160–190 мс;
- ни один запрос не близок к пределу 2 с.

## Known Issues / Risks
- Минутный обход каждый раз проходит все позиции с ждущим переводом: при 50 000 задачах это около 4 с работы базы в минуту. Если ждущих позиций станут сотни тысяч, обход стоит ограничить изменившимися позициями (I1219).
- Позиция, поставленная серверной командой (`translations:queue-missing`), до минуты стоит в нижней группе.
- `retryFailed` пропускает строки, заблокированные в тот же момент (`SKIP LOCKED`). Такие строки останутся отказанными до следующего нажатия.
- **Что осталось в общей dev-базе:**
  - категории «Проба перевода», «Проба: свечи» с характеристикой «Зазор» и «Проба: фильтры салона» — их можно убрать в архив в админке;
  - тестовый администратор `+77010000954`;
  - настройку `login_code_resend_interval_seconds` временно менял, вернул через `settings:reset`.
- **База замера `adclub_t054`** оставлена в контейнере. Удалить:
