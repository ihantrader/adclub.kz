# TASK-055 — Окружение staging и деплой: образы, стек staging в РК, миграции до деплоя, секреты, резервное копирование, обратный прокси и TLS, адреса staging для веба и приложения

Модель: Opus 5.5, High

## Цель

У проекта до сих пор одно окружение — машина разработки: API и worker запускаются из исходников, PostgreSQL, Redis, Meilisearch и MinIO — в `compose.dev.yml`, кабинет и админка — dev-серверы Vite, приложение — Expo Go, браузер и с TASK-056 первая сборка APK, которая смотрит на `localhost`. Без сервера нельзя ни поставить сборку на телефон и пройти путь с настоящим API, ни отдать приложение на проверку сторам (им нужны работающее приложение и страница политики конфиденциальности на домене), ни проверить то, что видно только снаружи: TLS, адрес клиента за прокси, лимиты по IP при CGNAT операторов, поведение при перезапусках, резервные копии.

Задача делает проект **разворачиваемым**: Docker-образы, стек staging на стандартных компонентах по решению D1/D-010 (ARCHITECTURE 15.1), миграции до деплоя, секреты в зашифрованном файле (sops + age), резервное копирование и проверка восстановления, обратный прокси с TLS и заголовками безопасности, деплой одним шагом из CI, адреса staging для кабинета, админки и приложения. После неё:
- весь стек поднимается из репозитория одной командой — и на машине разработки как репетиция, и на сервере staging;
- каждый push в `main` с зелёным CI сам доезжает до staging: образы по SHA, миграции, перезапуск, проверка `/ready`;
- сборка приложения `preview`/`preview-apk` смотрит на staging, и Product Owner проходит путь на телефоне против настоящего сервера;
- секреты, резервные копии и процедура переезда к другому провайдеру в РК описаны и проверены, а не подразумеваются.

## Требования

### 1. Образы

- Один образ `api` для API-процесса, worker'а и серверной команды (разные команды запуска), многоступенчатая сборка из монорепозитория pnpm (установка только нужных workspace-пакетов, `pnpm deploy` или аналог; сборка `packages/*` и `apps/api`; в итоговом слое — только `dist` и production-зависимости), не root, закреплённые базовые образы (D-016; Node 24 LTS), `HEALTHCHECK` по `/health`, метки с SHA коммита и версией.
- Образы веб-клиентов: `supplier-web` и `admin-web` собираются с `VITE_API_URL` и `ADMIN_WEB_RELEASE_VERSION` аргументами сборки и отдаются статикой из образа прокси или отдельным статическим сервером — выбрать и записать; на одном образе не должно быть двух адресов API.
- Реестр — GitHub Container Registry (`ghcr.io/ihantrader/…`; код без данных, 8.5 не нарушается): задача CI `images` на push в `main` собирает и публикует образы с тегами `sha-<короткий SHA>` и `main`; сборка воспроизводима, `latest` не используется.
- Локальная репетиция: `docker compose -f infra/docker/compose.staging.yml …` поднимает весь стек на машине разработки (прокси с самоподписанным сертификатом для `localhost`), и путь «вход сотрудником → заявка → выдача по коду» проходит против контейнеров, а не исходников.

### 2. Стек staging

- `infra/docker/compose.staging.yml`: `postgres` (16, том, `shm_size`, параметры под 8 ГБ), `redis` (7, AOF), `meilisearch` (v1.11, мастер-ключ из секретов), `api`, `worker` (один образ, `restart: unless-stopped`, лимиты памяти, `depends_on` с healthcheck'ами), `proxy` (обратный прокси с автоматическим TLS Let's Encrypt — Caddy предпочтителен, решение записать; HTTP → HTTPS; HSTS; `X-Forwarded-For`/`X-Forwarded-Proto`; gzip/brotli; статика кабинета и админки; заголовки безопасности и **CSP** — встроенный скрипт темы веб-клиентов получает nonce или hash, `unsafe-inline` для скриптов не допускается; размеры тела запроса под загрузку фото и прайса — `photo_max_size_mb`, `import_max_file_mb`), ротация логов контейнеров (`json-file`, `max-size`/`max-file`), часовой пояс процессов — UTC, время продукта — Алматы (13.3).
- Файлы — S3 провайдера по S3 API (`S3_*`); MinIO в staging нет. Без выданного бакета репетиция локально идёт на MinIO из `compose.dev.yml`.
- `TRUST_PROXY` — ровно один доверенный hop (прокси на той же машине); интеграционная проверка: адрес клиента для лимитов берётся из `X-Forwarded-For` только от прокси, а поддельный заголовок напрямую к API не меняет адрес.
- **`/dev/*` на staging закрыт** (`/dev/login-codes`, `/dev/messages`, `/dev/pushes`, `/dev/payment/*`): прокси не пропускает эти пути наружу, `LOGIN_CODE_DEV_OUTBOX` не включается; тестировщики входят номерами служебного входа (`review-login:enable`, TASK-077), администраторы — своими номерами с TOTP; коды для них в staging выдаются тем же служебным входом (решение: отдельный список тестовых номеров с постоянными кодами, не больше 10, срок — месяц). Swagger `/docs` и `/openapi.json` на staging — за тем же запретом или за basic auth прокси (решить, записать).
- Origin веб-клиентов — только адреса staging (`SUPPLIER_WEB_ORIGINS`, `ADMIN_WEB_ORIGINS`); приложение — не браузер и в origin не нуждается.

### 3. Миграции до деплоя

- Деплой выполняет миграции отдельным одноразовым контейнером того же образа (`node-pg-migrate up` без `--envPath`, из переменных окружения), **до** замены API и worker'а; при ошибке миграции деплой останавливается, прежние контейнеры продолжают работать. `jobs:schema-migration check` и `migrate:status` — часть шага.
- Обратимость уже проверяет CI (`database.integration.test.ts`); деплой её не повторяет.

### 4. Секреты

- `infra/secrets/staging.env.sops` — зашифрованный sops + age файл переменных окружения staging в репозитории; `.sops.yaml` с открытыми ключами (Product Owner, CI); расшифровка — при деплое в память/временный файл с правами `600`, удаляется после запуска compose (или передаётся через `docker compose --env-file` из `tmpfs`).
- Скрипт `infra/scripts/secrets-init.mjs`: генерирует `SESSION_TOKEN_SECRET`, `LOGIN_CODE_HASH_SECRET`, `ADMIN_TOTP_ENCRYPTION_KEY`, `PAYMENT_TOKEN_ENCRYPTION_KEY`, `PAYMENT_WEBHOOK_SECRET`, `METRICS_TOKEN`, `MEILI_MASTER_KEY`, `POSTGRES_PASSWORD` криптографически случайными значениями нужной длины и сразу шифрует файл — значения не печатаются никогда.
- **Запрет dev-значений**: вне development/test процесс не стартует, если секрет равен значению из `.env.example` или умолчанию dev (`adclub-dev-secret`, `adclub-dev-master-key`, пароль `adclub` и т. п.) — проверка в `env.schema.ts` с тестом.
- Ротация: описать, что происходит при смене каждого секрета (`SESSION_TOKEN_SECRET` завершает все сессии; `LOGIN_CODE_HASH_SECRET` обесценивает действующие коды; `ADMIN_TOTP_ENCRYPTION_KEY` требует сброса второго фактора; `PAYMENT_TOKEN_ENCRYPTION_KEY` — перепривязки карт) — в ARCHITECTURE, не отдельным файлом.

### 5. Резервное копирование и восстановление (15.4)

- Ежедневный `pg_dump` (custom format, сжатие) в бакет резервных копий с префиксом даты и хранением 14 дней (жизненный цикл — наша задача очистки или правило бакета по S3 API, без фирменных функций); WAL-архив для контейнерного PostgreSQL — через `archive_command` в тот же бакет (окно 7 дней) или честно отложить до managed PostgreSQL с обоснованием в ARCHITECTURE.
- Еженедельная **проверка восстановления**: скрипт поднимает временный контейнер PostgreSQL, восстанавливает последний дамп, запускает `migrate:status` (все миграции применены) и сверяет число строк ключевых таблиц с источником; результат — в лог и метрику; ручной запуск — одной командой.
- Версионирование бакета файлов — если провайдер поддерживает по S3 API; иначе — ежедневная копия `rclone sync` в бакет резервных копий. Meilisearch — `search:reindex` после восстановления.
- `infra/MIGRATION.md` (15.1) — регламент переезда к другому провайдеру в РК по пяти шагам, с командами из этой задачи; прогон регламента на staging раз в квартал — заметка в ARCHITECTURE (задачи-напоминания не нужно).

### 6. Деплой

- `infra/scripts/deploy.sh` на VM: `docker compose pull` образов по SHA, расшифровка секретов, миграции (п. 3), `up -d`, ожидание `/ready` 200 и `/health` через прокси, вывод версии (`GET /meta/client-policy` отвечает, `X-Client` админки принят), откат — повторный деплой предыдущего SHA одной командой.
- Задача CI `deploy-staging`: после зелёного `ci` на push в `main` — по SSH на VM (секреты GitHub: хост, пользователь, ключ, `SOPS_AGE_KEY`), environment GitHub `staging`; сбой деплоя — красный прогон; параллельные деплои сериализуются (`concurrency`). Ручного подтверждения для staging нет (15.5); для prod — будет в своей задаче.
- Первичная настройка VM — `infra/scripts/bootstrap-vm.sh` (Docker Engine из официального репозитория, пользователь `deploy`, брандмауэр: 22, 80, 443; автообновления безопасности; `fail2ban` для SSH; часовой пояс UTC; каталоги данных) — идемпотентный, запускается один раз с sudo.

### 7. Лимиты по IP и CGNAT (долг TASK-004)

- Таблица всех лимитов «по адресу» (`login_code_*_per_ip`, `session_refresh_per_ip` 600/час, `catalog_read_per_ip` 300/мин, `supplier_lead_per_ip`, `compatibility_check_per_ip`, `vehicle_document_per_ip`, `whatsapp_webhook_per_ip` и остальные из реестра настроек) с оценкой: сколько человек за одним адресом CGNAT оператора РК (Kcell, Beeline, Tele2/Altel — порядок сотен–тысяч абонентов на адрес) выдерживает каждый лимит при обычном использовании, и предложение новых умолчаний там, где лимит сработал бы на группе клуба из 50–100 человек в одной сети. **Умолчания в коде не менять** без решения Product Owner — предложение в отчёте и в ARCHITECTURE; на staging значения ставятся настройками. Срабатывания лимитов видны в метриках (TASK-009) — на них и смотреть после запуска группы.

### 8. Веб-клиенты в staging

- Сборка кабинета и админки с адресом API staging; service worker кабинета и установка PWA проверяются по HTTPS на телефонах Product Owner (как TASK-031, но уже без `dev:lan`); `ADMIN_WEB_RELEASE_VERSION` в окружении API совпадает с версией собранной админки, иначе API не стартует — шаг деплоя берёт её из образа.
- CSP не ломает тему (встроенный скрипт), шрифты (Onest из пакета `ui`), фото по подписанным ссылкам S3 (`img-src` с адресом хранилища), QR и сканер (камера — `Permissions-Policy`), карты и WhatsApp — внешние переходы, не встраивание. Размер бандлов — измерить и записать (~830 КБ по плану; оптимизация — не эта задача).
- Статический каталог для документов (`/docs/…` на домене кабинета или отдельный `www`): пустые заглушки с текстом «страница готовится», чтобы `club_terms_url`/`club_privacy_url` можно было задать, когда появятся тексты; Product Owner и юрист заменяют содержимое без релиза.

### 9. Настройки и данные staging

- После первого деплоя серверной командой в контейнере: `admin:grant` для администраторов Product Owner, `default_city`, группа «Документы и поддержка» (`club_partner_form_url` → `/join` кабинета), `review-login:enable` для тестовых номеров, `settings:set` лимитов по п. 7; dev-заполнение (`dev:*:seed`) на staging **не выполняется** — `NODE_ENV=staging` его запрещает так же, как production (проверить, что серверная команда это делает; если нет — добавить). Справочник, автомобили и поставщики заводятся через админку и импорт (TASK-035, TASK-035.B, TASK-036) или переносом дампа dev-данных без персональных данных — решить, записать.
- Тестовые провайдеры на staging (`LOGIN_CODE_CHANNELS=test`, `MESSAGE_PROVIDER=test`, `PUSH_PROVIDER=test`, `PAYMENT_PROVIDER=test`, `AI_PROVIDER` — OpenRouter с ключом staging, потому что перевод и прайсы без ИИ не проверяются; бюджет `ai_daily_budget_usd` маленький): записать, что именно staging не проверяет (ничего не уходит людям) и как это сменится с TASK-026/041/042. Для push на телефонах Product Owner на staging допустим `PUSH_PROVIDER=live` с `APNS_ENVIRONMENT=sandbox` и FCM — когда появятся ключи (TASK-056 часть B).

### 10. Мониторинг и журнал

- Логи API и worker'а — JSON в stdout контейнеров, ротация Docker, хранятся на VM (РК); `MONITORING_DSN` и `MONITORING_ENVIRONMENT=staging` — если Product Owner даст приёмник; `/metrics` доступен только с `METRICS_TOKEN` (внешний сборщик — позже); внешняя проверка живости `/health` раз в минуту (любой бесплатный пингер) — по желанию, в отчёт.

## Acceptance Criteria

1. **AC-1 — образы.** `docker build` образов `api`, `supplier-web`, `admin-web` проходит локально и в CI (`images` на push в `main` публикует в GHCR с тегом по SHA); образ `api` не root, с `HEALTHCHECK`; в нём нет исходников, dev-зависимостей и `.env`. Evidence: вывод сборки, `docker image inspect`, список слоёв/размер, ссылка на пакеты GHCR.
2. **AC-2 — стек локально.** `compose.staging.yml` поднимается на машине разработки с самоподписанным TLS; `curl -k https://localhost/ready` → 200; кабинет и админка открываются по HTTPS; путь «вход сотрудником → заявка от пользователя → выдача по коду» пройден против контейнеров. Evidence: команды и ответы, скриншоты или текст страниц.
3. **AC-3 — прокси.** HTTP → HTTPS, HSTS, CSP без `unsafe-inline` для скриптов, тема и шрифты работают; `/dev/*`, `/docs`, `/openapi.json` снаружи — 404/401 (решение записано); `TRUST_PROXY`: интеграционный тест — адрес из `X-Forwarded-For` только от прокси, подделка напрямую не меняет адрес. Evidence: заголовки ответов (`curl -I`), тест.
4. **AC-4 — миграции до деплоя.** Деплой с намеренно сломанной миграцией останавливается до замены контейнеров, прежние API и worker продолжают отвечать; с исправленной — применяется и запускает новые. Evidence: вывод двух прогонов `deploy.sh` локально (или на VM).
5. **AC-5 — секреты.** `staging.env.sops` расшифровывается только ключами из `.sops.yaml`; `secrets-init.mjs` генерирует и шифрует, ничего не печатая; процесс с dev-значением секрета вне development/test не стартует (тест); в git ни одного секрета (поиск по истории задачи). Evidence: тесты, `git log -p` по `infra/secrets`, вывод скрипта.
6. **AC-6 — резервные копии.** Ежедневный дамп в бакет и проверка восстановления работают: восстановление в временный контейнер, `migrate:status` «всё применено», числа строк совпадают; документ `infra/MIGRATION.md` со всеми командами. Evidence: вывод проверки восстановления (локально на MinIO — для части A; на бакете провайдера — часть B).
7. **AC-7 — деплой из CI.** `deploy-staging` после зелёного `ci` деплоит по SSH, ждёт `/ready`, падает при сбое; `concurrency` сериализует; откат одной командой. Evidence: идентификаторы прогонов, вывод деплоя (часть B; для части A — прогон скрипта локально против локального стека).
8. **AC-8 — лимиты и CGNAT.** Таблица лимитов по IP с оценкой и предложением умолчаний — в отчёте и ARCHITECTURE; умолчания в коде не изменены. Evidence: таблица.
9. **AC-9 — staging живой (часть B).** `https://api.staging.adclub.kz/ready` → 200 с TLS Let's Encrypt; кабинет и админка по своим адресам; администратор Product Owner вошёл с TOTP; тестовый номер служебного входа входит в приложение (`preview-apk`, пересобранное с `EXPO_PUBLIC_API_URL` staging) на телефоне Android и доходит до каталога. Evidence: ответы `curl`, вывод `eas env:list`, ссылка на сборку, описание прохода на телефоне.
