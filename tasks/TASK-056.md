# TASK-056 — Сборки для сторов: нативная сборка и внутреннее тестирование, OTA-обновления, версия сборки в политике клиента, снимки контракта, push на iOS и фоновый ack

Модель: Opus 5.5, High

## Цель

Приложение до сих пор жило только в Expo Go и в браузере разработки: нативной сборки, которую можно поставить на телефон из TestFlight или внутреннего тестирования Google Play, нет. Из-за этого не проверено всё, что живёт только в собственной сборке: разрешение на уведомления, токен push, фоновая доставка, открытие заявки из push при холодном старте, различение установленных приложений (WhatsApp, карты), камера техпаспорта на телефоне. Одновременно накопились решения, которые нельзя откладывать до публикации: какой версией приложение представляется серверу, когда JS обновляется поверх нативной оболочки (OTA), как сервер остаётся совместимым с уже опубликованными версиями (снимки контракта, ARCHITECTURE 7.2), и как push доходит до iPhone (токен APNs, который FCM HTTP v1 не принимает — I866).

Задача делает приложение **выпускаемым**: конфигурация нативной сборки и профилей выпуска, OTA-обновления в рамках одной версии стора, версия сборки как единственная версия для политики клиента, снимки контракта по опубликованным версиям с проверкой в CI, push на iOS через APNs напрямую, подтверждение push в фоне, ссылки на страницы приложения в сторах, долги I866 — и, когда Product Owner даст учётные записи, первые сборки во внутреннее тестирование обеих платформ. После неё:
- сборку можно собрать и отправить во внутреннее тестирование одной командой по описанной процедуре, а JS-правку доставить OTA без похода в стор;
- сервер знает настоящую версию установленного приложения и не ломает контракт ни одной поддерживаемой версии — это проверяет CI;
- push доходит и до Android (FCM), и до iPhone (APNs), а дошедший push подтверждается и при закрытом приложении, где платформа это позволяет, — резерв WhatsApp (TASK-052) перестаёт срабатывать на уже доставленных уведомлениях.

## Внешние зависимости и решения Product Owner

Задача делится на **часть A** (всё в репозитории, проверяется без учётных записей) и **часть B** (первые сборки и публикация во внутреннее тестирование — только с учётными записями). Без них часть B — `BLOCKED` с точным списком, часть A всё равно выполняется целиком.

Нужно от Product Owner (агент не заводит и не оплачивает ничего сам, не запускает `eas login`/`eas build` без выданных учётных данных):
1. **Учётная запись Expo (EAS)** и доступ к проекту (`eas init` даёт `extra.eas.projectId`) — для EAS Build, EAS Submit и EAS Update.
2. **Apple Developer Program** (организация), запись приложения в App Store Connect, ключ API App Store Connect для `eas submit`, **ключ APNs `.p8`** (Key ID, Team ID) — для push на iOS.
3. **Google Play Console**, приложение создано, сервисный аккаунт для `eas submit`; **проект Firebase** только для Android: `google-services.json` для сборки и сервисный аккаунт FCM (уже предусмотренные `FCM_*`).
4. **Идентификаторы**: bundle identifier iOS и package Android. Предложение по умолчанию — `kz.adclub.app` на обеих платформах (домен `adclub.kz`; имя в сторах — «Asia Drive Club»). Другое решение — в `app.json` меняется одна строка на платформу.
5. **Адрес API для сборки внутреннего тестирования** — staging (TASK-055). До staging первая сборка `preview` может смотреть только на адрес, который Product Owner укажет сам; в репозитории адресов нет — только переменная профиля.
6. Материалы страниц в сторах (описания kk/ru, скриншоты, возрастной рейтинг, формы о данных, адрес политики конфиденциальности — `club_privacy_url`, TASK-055) — к публикации, не к внутреннему тестированию; список — в отчёте.

Секреты (ключи `.p8`, `google-services.json`, сервисные аккаунты) в репозиторий не попадают никогда: EAS хранит их как secrets/file-переменные окружения проекта, сервер — `.env`.

## Требования

### 1. Версия приложения и OTA-обновления (7.4)

- **Версия сборки — единственная версия для сервера.** `X-Client`, сравнение с `minSupportedVersion` и всё, что сегодня читает `appInfo.version`, берут версию **установленной нативной сборки** (`expo-application`: `nativeApplicationVersion`, сборочный номер — `nativeBuildVersion`), а не `Constants.expoConfig.version` из манифеста обновления. В браузере и Expo Go, где нативной версии нет, — прежний источник. Одна функция решения (чистая, с тестом): «что приложение называет своей версией».
- **OTA только внутри своей версии стора:** `expo-updates`, `runtimeVersion: { policy: "appVersion" }` — обновление JS никогда не попадает в сборку другой версии; каналы EAS Update по профилям (`preview`, `production`). Проверка обновления — при старте и при возврате из фона, применение — при следующем запуске (без перезагрузки посреди работы); заставка M-START-01 обновления не ждёт (её бюджет — 2,5 с на политику клиента, 4.37). Без сети и в Expo Go `expo-updates` молчит.
- **Что видно человеку:** в M-PRO-06 «Версия приложения» — версия сборки и, если применено OTA, короткий идентификатор обновления («1.0.0 · обновление a1b2c3d»); так поддержка понимает, какой код у человека. Текст — на утверждение.
- **Семантика для администратора:** описания настроек `client_min_version_ios|android` говорят, что это версия сборки из стора (минимум, ниже которого приложение не обслуживается), и что OTA её не меняет. Правило выпуска: нативное изменение — новая версия стора; поднятие `client_min_version_*` — через несколько недель после выхода версии (7.4); JS-правка в рамках версии — OTA.
- **Номера сборок**: `ios.buildNumber` и `android.versionCode` ведёт EAS (`cli.appVersionSource: "remote"`, автоинкремент на сборке); в `app.json` только `version` — версия стора. Выпуск версии — коммит с поднятием `version` и тег `mobile-v<version>` (процедура — п. 8).

- `eas.json`: профили `development` (dev-client, внутреннее распространение, API — `EXPO_PUBLIC_API_URL` из окружения профиля, по умолчанию пусто → как сейчас, машина dev-сервера), `preview` (внутреннее тестирование: TestFlight и внутренний трек Google Play, канал `preview`, `EXPO_PUBLIC_API_URL` — адрес staging из переменной окружения EAS), `production` (стор, канал `production`); `submit`-профили с ссылками на учётные данные через переменные EAS, не значения. Никаких адресов и ключей в файле.

Сгенерированные `ios/` и `android/` в репозиторий не попадают (`.gitignore`, managed workflow).
- Expo Go продолжает работать для разработки (`pnpm --filter mobile start`): всё нативное за портами с ответом «недоступно» (как `native-push-port.ts`).

### 3. Push на iOS — APNs напрямую (решение I866)

- **Выбор:** отправка в APNs напрямую, второй класс порта `ApnsPushProvider` — по образцу I854 (без SDK, минимум звеньев, Firebase на iOS не нужен): `node:http2` к `api.push.apple.com` (`api.sandbox.push.apple.com` для `development`-сборок), токен провайдера JWT ES256 из ключа `.p8` (`node:crypto`), кэш до 50 минут, один выпуск на одновременные отправки; заголовки `apns-topic` (bundle identifier), `apns-push-type: alert`, `apns-priority: 10`, `apns-collapse-id` = `collapseKey`, `apns-expiration`; тело — `aps.alert.body`, `aps.sound`, `aps.content-available: 1` (п. 4) и `data` как у FCM. Соединение http2 переиспользуется и закрывается по простою; `signal` отменяет запрос.
- **Исходы по документированным `reason`:** `410` и `BadDeviceToken`, `Unregistered`, `DeviceTokenNotForTopic` → `invalid_token`; `429`, `5xx`, `TooManyRequests`, `ServiceUnavailable`, `Shutdown`, обрыв до отправки → `unavailable`; `403` (`InvalidProviderToken`, `ExpiredProviderToken` — после одного обновления токена), `400` о запросе (`BadTopic`, `PayloadTooLarge`, `MissingTopic`) → `rejected`; таймаут после отправки заголовков, обрыв после соединения, `200` без `apns-id` → `unknown`. Юнит-тесты — на локальном http2-сервере с самоподписанным сертификатом (генерируется в тесте), как `fcm-push-provider.test.ts` на подменённом `fetch`.
- **Маршрутизация по платформе устройства:** `device_token.platform = ios` → APNs, `android` → FCM; это решает один компонент (`PushSender`/фабрика провайдера), а не обработчики. Конфигурация: `PUSH_PROVIDER=test` — как было; `PUSH_PROVIDER=live` — требует **и** `FCM_*`, **и** `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_PRIVATE_KEY`, `APNS_BUNDLE_ID`, `APNS_ENVIRONMENT=sandbox|production` (production-окружение сервера принимает только `production`); прежнее значение `fcm`, если оно есть, — переименовать или оставить синонимом с записью. Без `.env.example` и `env.schema.test.ts` не обходится. Токен в логи и журнал не попадает (`maskToken`).
- Приложение: на iOS `getDevicePushTokenAsync` даёт токен APNs — он и отправляется в `PUT /notifications/device-token` как сейчас; на Android — токен FCM (нужен `google-services.json` в сборке). В Expo Go — по-прежнему `null`.

### 4. Подтверждение push в фоне (I862)

- `expo-task-manager` и фоновая задача `expo-notifications` (`registerTaskAsync`): push, пришедший при закрытом или свёрнутом приложении, подтверждается `POST /notifications/{id}/ack` **из фоновой задачи**: сессия читается из защищённого хранилища, истёкший access-токен обменивается тем же правилом `session-fetch-core` (один обмен), нет сессии или `SESSION_ENDED` — ничего; любая неудача молчит и добирается при следующем открытии (существующий путь). Логика задачи — чистая функция с тестом (данные push → что подтвердить и когда).
- Что требуется от сервера и сборки: на iOS — `UIBackgroundModes: remote-notification` и `content-available: 1` в push (п. 3); на Android — сообщение FCM в форме, при которой `expo-notifications` вызывает задачу и показывает уведомление сам (решить по документации SDK 57 и записать: `notification` + `data` или только `data`), канал `default` остаётся.
- **Ограничения честно:** iOS может не разбудить приложение (низкий заряд, режим энергосбережения, пользователь «смахнул» приложение) — тогда ack придёт при открытии, и резерв WhatsApp уйдёт по таймауту (9.3 — принятое ограничение). Проверка на устройстве — только в собственной сборке (часть B); до неё — тесты логики и `expo prebuild`.

### 5. Снимки контракта по опубликованным версиям (7.2)

- Папка снимков (например `packages/contracts/snapshots/mobile/<version>.openapi.json` — решить место, записать): снимок — `apps/api/openapi.json` на момент выпуска версии приложения; список поддерживаемых версий — файл рядом (`supported.json`: версия, дата выпуска, платформы), новая запись добавляется командой выпуска `pnpm release:mobile:snapshot <version>` (создаёт снимок из текущего `openapi.json`, дописывает список; версия должна совпадать с `app.json`).
- **CI:** `openapi:compat` получает режим `--base-file <снимок>` и в `checks` прогоняется против **каждого** снимка из списка (один шаг, цикл по списку; трейлер `Contract-Breaking-Change` действует и здесь, с теми же оговорками). Снимок снимается из списка только после того, как `client_min_version_*` обеих платформ перешагнул эту версию — процедура в 4.81; юнит-тест следит, что каждый снимок из списка существует, каждый файл в папке — в списке, и версии не убывают.
- **Первый снимок — `1.0.0`:** та версия, что уйдёт во внутреннее тестирование в части B; создаётся в этой задаче командой выпуска. Сравнение с `main` (`openapi:compat --base`) остаётся — оно ловит ломающее изменение внутри одной версии.

### 6. Ссылки на приложение в сторах (M-START-03, TASK-078)

- Настройки `client_store_url_ios` и `client_store_url_android` (группа политики клиента, по умолчанию пусто; значение — `https://apps.apple.com/…` / `https://play.google.com/store/apps/details?id=…`), отдаются в `GET /meta/client-policy` аддитивно (`platforms.<p>.storeUrl: string | null`); приложение открывает их на M-START-03, а при `null` — прежний поиск по названию. Администратор меняет через «Настройки → Политика клиента» (существующий экран, новые ключи появляются сами, если реестр их описывает, — проверить).

### 7. Долги TASK-051 (I866)

- Холодный старт из push: открытие заявки ждёт чтения сессии столько, сколько нужно (не 1 с), с одним общим пределом заставки; тест логики.
- Выход без сети: запрос выхода (и снятие устройства — сервер снимает его концом сессии) ставится в очередь и выполняется при появлении сети; до этого приложение уже в гостевом режиме (как сейчас). Тест логики.
- Неудачный ack: 4xx не повторяется (удаляется из очереди), 5xx и нет сети — повтор при следующем возврате; тест.
- Две одновременные регистрации разных токенов одной сессии — не 500: один запрос побеждает, второй получает согласованный ответ (например, последний записанный токен — `upsert` по сессии под блокировкой), без ошибки в мониторинге; интеграционный тест на одновременные запросы.

## Acceptance Criteria

1. **Версия сборки.** Юнит-тест: в собственной сборке `X-Client` и сравнение с политикой берут нативную версию, а отличающаяся версия манифеста обновления на них не влияет; в Expo Go и браузере — прежний источник. `runtimeVersion` — `appVersion` (тест читает `app.json`). Строка M-PRO-06 показывает версию и идентификатор обновления (в браузере — без него).
2. **Конфигурация сборки.** В `app.json` — идентификаторы обеих платформ, `UIBackgroundModes`, `runtimeVersion`, `updates`; `eas.json` — профили `development`, `preview`, `production` без адресов и секретов; шаг CI `expo config` + `expo prebuild --no-install` для обеих платформ + `expo-doctor` зелёный (вывод в отчёте); в репозитории нет `google-services.json`, `.p8`, `ios/`, `android/`.
3. **APNs.** Юнит-тесты `ApnsPushProvider` на локальном http2-сервере: успех с `apns-id`, `410 Unregistered` → `invalid_token`, `429`/`503` → `unavailable`, `403 InvalidProviderToken` → `rejected` (после одного обновления токена), таймаут после отправки → `unknown`, обрыв до отправки → `unavailable`; заголовки `apns-topic`, `apns-collapse-id`, `content-available`; токен провайдера кэшируется и обновляется. Маршрутизация: iOS → APNs, Android → FCM (тест `PushSender`). Конфигурация: `live` без `APNS_*` или без `FCM_*` не стартует; production с `APNS_ENVIRONMENT=sandbox` не стартует; тесты `env.schema.test.ts`. Токен ни в одном логе (тест вывода).
4. **Фоновый ack.** Задача зарегистрирована в собственной сборке и не трогается в Expo Go/браузере; чистая функция «данные push → ack» с тестами (нет сессии, истёкший токен — один обмен, `SESSION_ENDED`, 4xx, нет сети); на сервере ack принимается как прежде. Проверка на устройстве — часть B (иначе `NOT RUN`, так и написать).
5. **Снимки контракта.** Снимок `1.0.0` и список поддерживаемых версий в репозитории; команда выпуска создаёт снимок и дописывает список; `openapi:compat --base-file` работает; шаг CI прогоняет все снимки из списка; юнит-тест согласованности папки и списка. Доказательство: локально внесённое ломающее изменение (удалённое поле ответа) — проверка против снимка падает с понятным сообщением (вывод в отчёте), изменение откатывается.
6. **Ссылки сторов.** `settings:set client_store_url_android https://play.google.com/store/apps/details?id=kz.adclub.app --reason "dev"` → в `GET /meta/client-policy` `platforms.android.storeUrl`, в браузере (`mobile-web`, Android) M-START-03 (`client_min_version_android 2.0.0`) открывает эту ссылку; `settings:reset` → прежний поиск. Контракт аддитивен (`openapi:compat`).
7. **Долги I866.** Тесты: холодный старт из push открывает заявку при чтении сессии дольше 1 с; выход без сети завершается при появлении сети; ack с 4xx не повторяется, с 5xx — повторяется один раз при возврате; интеграционный тест — десять одновременных регистраций разных токенов одной сессии: ни одного 500, один токен в `device_token`, отсутствие ошибки в мониторинге.
8. **Документы.** ARCHITECTURE 4.81 с процедурой выпуска, обновлены 7.2, 7.4, 9.3, 4.79, I862, I866, 15.1, 14; CLAUDE.md блок 0; `.env.example`; списки `expected/` и `orm-tables.ts`, если менялись.
9. **Часть B.** Идентификаторы сборок EAS, номера сборок TestFlight и Google Play, результаты проверок на устройствах и OTA — или `BLOCKED` с перечнем недостающих учётных записей и решений.
10. **Локально** `pnpm format:check`, `lint`, `typecheck`, `test`, `build`, `openapi:check`, `openapi:compat`; интеграционные тесты изменённых модулей (`notifications`, `settings`, где менялись).
