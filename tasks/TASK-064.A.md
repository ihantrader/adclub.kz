# TASK-064.A — Фото прайса: доводка по приёмке

Модель: Opus 5.5, High

## Цель

TASK-064 принята с замечаниями (ARCHITECTURE I1101). Независимое ревью при приёмке нашло пять дефектов. Опасных среди них нет, но два бьют по деньгам и устойчивости сервера. Задача их закрывает. Нового поведения для поставщика задача не добавляет.

## Требования

### 1. Страница, которую ИИ не успевает прочитать, не читается бесконечно

**Сейчас.** `price-photo-runner.ts`: истёкший предел времени вызова ИИ приходит как `AiGatewayError("unavailable")` (`ai.service.ts`, `controller.abort`). Он входит в `FALLBACK_WORTHY`, поэтому загрузка уходит в ожидание (`wait(importId, "unavailable")`). Через `price_match_retry_seconds` страница читается заново — с первого чтения, ведь результат первого чтения не сохраняется. Так повторяется до истечения сверки (`price_import_review_days`, 7 дней). Страница мелкой печати, которой не хватает 180 с, тратит общий `ai_daily_budget_usd` каждую минуту — и у помощника, переводов и всего остального.

**Нужно:**
- **Счёт попыток.** У страницы — число попыток распознавания. Попытка, кончившаяся ожиданием из-за ответа ИИ (недоступен, предел времени), считается. Исчерпанный бюджет (`AiBudgetExhaustedError`) не считается: модель не вызывалась.
- **Предел.** После N попыток (настройка, например `price_photo_read_attempts`, по умолчанию 3) страница получает `failed` («Не удалось распознать»). Поставщик видит «Переснять» и «Убрать страницу», как у нечитаемой. Остальные страницы ждать не перестают.
- **Сброс.** Пересъёмка страницы сбрасывает счёт.
- **Первое чтение не пропадает.** Если первое чтение удалось, а второе упало по таймауту, повтор не платит за первое снова: результат первого чтения сохраняется до второго. Как именно — решает исполнитель (колонка страницы или иначе).
- **Различение причин — по желанию.** Можно отличать таймаут от недоступности провайдера: таймаут — свойство страницы, недоступность — свойство провайдера. Если отличаешь, недоступность провайдера счёт не тратит. Решение записать.

### 2. Загрузка фото не съедает память API до проверки пределов

**Сейчас:**
- `upload-body.middleware.ts` буферизует тело маршрута до 60 МБ ещё до сервиса.
- `formPages` разбирает все части `Response.formData()` без предела их числа и копирует каждую (`Promise.all(... arrayBuffer())`). Предел `price_photo_max_pages` проверяется только после этого.
- Проверка часового предела стоит до разбора, но вне блокировки, так что одновременные запросы все её проходят.
- Получается: десятки одновременных тел по 60 МБ или одно тело из сотен тысяч мелких частей `page` занимают гигабайты памяти и держат цикл событий.

**Нужно:**
- **Предел маршрута до чтения тела** — как `photo_requests_per_ip` и `speech_requests_per_ip` (`UploadRateLimitMiddleware`, правило `countedBeforeBody`). Предел — на сотрудника или компанию, отказанные запросы тоже считаются, ответ 429 с `details.limit`. Название и размер настройки выбирает исполнитель.
- **Разбор формы с пределами** — по числу частей (не больше `price_photo_max_pages`) и по размеру каждой (не больше `price_photo_max_size_mb`). Лишняя часть или слишком большая страница — отказ сразу, без копирования остального. Подходит потоковый разбор или своя проверка границ поверх уже прочитанного буфера. Новая зависимость — только если без неё никак, с обоснованием в ARCHITECTURE.
- Ответы и коды отказов для поставщика не меняются: `too_many_pages`, `too_large` с номером страницы, `malformed`.

### 3. Фото не делает «пропавшими» предложения, которые на нём есть

**Сейчас.** `agreePricePhotoPages` оставляет только строки первого чтения, подтверждённые вторым. Строку, которую нашло только второе чтение, правило отбрасывает: это защита от выдуманных строк. Но `missingOffersQuery` строит «есть в файле» только по `price_import_row`. Поэтому предложение, которое модель один раз пропустила, попадает в «Пропали из файла». Если поставщик выберет «Снять с продажи», оно снимется, хотя напечатано на фото.

**Нужно:**
- **Строки любого чтения.** Позиция, чей артикул (или сопоставление по памяти компании) встретился хотя бы в одном чтении страницы, не считается пропавшей. Строки при этом в сверку не добавляются: защита от выдуманных строк остаётся.
- **Пояснение у фото.** Во вкладке «Пропали из файла» загрузки фото — пояснение, что на фото может быть только часть прайса. Текст kk и ru; в SCREENS его нет, добавить в код кабинета и отметить в отчёте для Product Owner. Выбор «Снять с продажи» / «Оставить как есть» по-прежнему обязателен.

### 4. Файлы страниц не остаются в хранилище навсегда

**Сейчас.** Две дыры:
- Страницы кладутся в хранилище до транзакции загрузки. Если процесс упал между записью и фиксацией, строки `price_import` нет. Свипер `prices.delete-files` ходит только по загрузкам, и файлы под префиксом не удаляются никогда.
- Если `price_import_file_retention_days` меньше `price_import_review_days`, свипер удаляет файлы загрузки в `needs_retake`. Пересъёмка после этого пишет новый файл, который уже никто не удалит.

**Нужно:**
- **Сироты.** Файлы без загрузки убирает уборка по сроку, как `catalog.cleanup-photo-files` у фото позиций (`photo_orphan_retention_hours`). Это может быть новая периодическая задача или расширение существующей; задачу внести в `apps/api/src/testing/expected/background-jobs.ts`.
- **Пересъёмка после удаления файлов.** Пересъёмка загрузки, чьи файлы уже удалены (`file_deleted_at`), — отказ 409 с понятной причиной; кабинет предлагает новую загрузку. Либо свипер не трогает загрузку, пока она ждёт пересъёмки. Выбери одно и запиши.

### 5. Экран загрузки не тянет распознанные строки страниц

**Сейчас.** `photoPagesOf` (`price-imports.service.ts`) выбирает все колонки `price_import_photo_page`, включая JSONB `rows` (до тысячи строк на страницу). Он вызывается при каждом опросе экрана (раз в 1,5 с), в сводке сверки и в списках поставщика и администратора. А `rows` после записи в `price_import_row` не очищается.

**Нужно:**
- Выбирать только нужные колонки.
- `rows` очищать после записи строк — либо доказать, что они нужны дальше, и записать почему.

## Acceptance Criteria

1. **Попытки и предел.** Страница, на которой ИИ раз за разом не укладывается в предел времени, после N попыток — `failed` с «Переснять». Бюджет не тратится сверх N попыток. Первое удачное чтение не оплачивается повторно. Пересъёмка сбрасывает счёт. Интеграционный тест с тестовым ИИ (режим или ответ, который упирается в предел времени).
2. **Загрузка.** Предел маршрута до чтения тела (отказанные считаются, 429). Тело из лишних или слишком больших частей отказывается без копирования всех частей. Интеграционный тест и юнит-тест разбора. Коды отказов для кабинета прежние.
3. **«Пропали из файла».** Позиция из второго чтения не попадает в «Пропали из файла»; пояснение у загрузки фото — на ru и kk. Тест.
4. **Хранилище.** Сироты убираются по сроку. Пересъёмка после удаления файлов не оставляет файла без владельца. Тест на настоящем MinIO.
5. **Запросы.** `photoPagesOf` не читает `rows`; решение по очистке `rows` записано и закрыто тестом.
6. **Локальные проверки:** `pnpm format:check`, `lint`, `typecheck`, `test`, `build`; интеграционные `price-photos`, `price-review`, `price-imports`. Контракт: `openapi:generate`, `openapi:check`, `openapi:compat --snapshots`. CI не ждать.
7. **Документы.** ARCHITECTURE — строки 4.93 со следующего свободного номера после I1101; таблица 14, если появились настройки. CLAUDE.md «Фото прайса в dev» — если поменялись команды или поведение. Отчёт `tasks/TASK-064.A-REPORT.md` с идентификатором прогона CI.
