# TASK-068.A — Поиск фото и фото поставщиков: доводка по приёмке

Модель: Opus 5.5, High

## Цель

TASK-068 принята с замечаниями (ARCHITECTURE I1155). Часть замечаний ревью архитектор поправил при приёмке:
- неудачный поиск задачи больше не повторяется каждый час;
- после первого общего сбоя задача останавливается;
- загрузчик не дочитывает чужие тела;
- соединение не берётся из общего пула.

Задача закрывает остальное. Новых экранов нет.

## Требования

### 1. Фото запроса на позицию не теряется и не обходит предел

**Сейчас.** `catalog-photos.service.ts`:
- Статус запроса `new` проверяется вне транзакции. Затем файлы уходят в хранилище, это сетевое время. Потом строка фото вставляется без блокировки и без повторной проверки `catalog_request`.
- Если администратор в этот промежуток одобрил или отклонил запрос, `adoptRequestPhotos` или `dropRequestPhotos` уже отработали.
- Новое фото остаётся с `item_id NULL` и `status = proposed` навсегда. В очередь администратора оно не попадает, а поставщик вечно видит «На рассмотрении».
- По той же причине параллельные загрузки обходят предел 3 фото на запрос: счёт `held` тоже идёт вне транзакции.

**Нужно:** в транзакции вставки снова проверить статус запроса и число его фото под блокировкой строки запроса (`FOR SHARE` или `FOR UPDATE`). Запрос уже решён — отказ 409 с понятным текстом в кабинете, файлы — в уборку сирот.

### 2. Перенос фото запроса учитывает предел позиции

**Сейчас.** `adoptRequestPhotos` не проверяет предел 10 активных фото позиции. Если запрос с 3 фото связать с позицией, у которой уже 10, у неё станет 13.

**Нужно:** переносится столько фото, сколько помещается. Остальные отклоняются с причиной, которую видит поставщик (ru, kk, en). Тест.

### 3. Повторная загрузка того же файла не показывает чужое фото

**Сейчас.** Если загруженный файл побайтово совпадает с фото, которое уже есть у позиции, ответ отдаёт найденную по контрольной сумме строку. Её мог загрузить другой поставщик, поиск ИИ или администратор. Поставщик видит её статус, причину отклонения и подписанную миниатюру.

**Нужно:** поставщику — только его собственные фото. Совпадение с чужим — ответ «Такое фото у позиции уже есть» без сведений о нём. Совпадение со своим — его строка, как сейчас.

### 4. Выбор позиций для фоновой задачи не растёт с каталогом

**Сейчас.** `photo-search-job.ts` (`due`) через `CROSS JOIN LATERAL` считает `shownOffers()` для каждого предложения каждой активной позиции без фото, затем сортирует. При десятках тысяч предложений после импорта прайсов запрос упрётся в 2 с `statement_timeout`.

**Нужно:** запрос с ограниченной ценой. Например, сначала кандидаты по индексу (активные товары без фото, срок повтора прошёл, есть активное предложение), с пределом, и только для них — проверка витрины. Как именно — решает исполнитель. Замер на 50 000 предложений в отчёте.

### 5. Поиск не держит в памяти 20 полноразмерных снимков сразу

**Сейчас.** `photo-search.service.ts` хранит до 20 подготовленных изображений (оригинал и варианты) до ранжирования. При `photo_max_size_mb` около 10 это сотни МБ на один поиск, в том числе в процессе API по кнопке администратора.

**Нужно:** для ранжирования держать только то, что ему нужно (контрольная сумма, перцептивный хэш, домен, размеры). Файлы готовить и сохранять только для выбранных кандидатов. Либо ограничить одновременно подготовленные. Пик памяти — в отчёте.

### 6. Мелочи

- **Курсор «Модерация → Фото».** Курсор кабинета теряет микросекунды `created_at`, поэтому фото с той же миллисекундой может пропасть между страницами. Курсор должен сохранять полное значение, как в других списках.
- **Диапазоны SSRF.** Блокировать IPv4-compatible (`::/96`) и IPv4-translated (`::ffff:0:0:0/96`) адреса. Юнит-тест.

## Не входит

- Живые вызовы SerpAPI. Ключа нет.
- Режим показа `photo_display_mode` (ждёт юриста).
- TASK-065.A, TASK-072.A (идут параллельно).

## Acceptance Criteria

1. **Запрос решён во время загрузки.** Интеграционный тест: запрос одобрен или отклонён между проверкой и вставкой — 409, фото без владельца не остаётся. Параллельные загрузки не превышают 3 фото на запрос.
2. **Предел позиции.** Тест: перенос в позицию с 9 фото добавляет одно, остальные отклонены с причиной.
3. **Чужое фото.** Тест: поставщик, загрузивший копию чужого фото, не получает его статуса, причины и ссылки.
4. **Задача.** Запрос `due` на 50 000 предложений укладывается в предел. Замер в отчёте, тест на выбор позиций не сломан.
5. **Память.** Пик памяти поиска на 20 результатах — в отчёте, до и после.
6. **Мелочи.** Курсор и диапазоны — тесты.
7. **Локальные проверки:** `pnpm format:check`, `lint`, `typecheck`, `test`, `build`. Интеграционные: `photo-search`, `catalog-photos`, `catalog-requests` (какие есть). Контракт: `openapi:generate`, `openapi:check`, `openapi:compat --snapshots`. CI не ждать.
8. **Документы.** ARCHITECTURE — раздел 4.95, строки I1156–I1169. Версию и историю ARCHITECTURE не менять. CLAUDE.md — если поменялось поведение. Отчёт `tasks/TASK-068.A-REPORT.md` с идентификатором прогона CI.
