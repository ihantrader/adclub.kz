# TASK-076 — Быстрый CI: параллельные интеграционные тесты, агент не ждёт CI

Модель: Sonnet 5.5, Medium

## Цель

Product Owner ждёт слишком долго (10.10.2026). Сейчас прогон CI на `main` идёт 9–12 минут, и сессия агента в конце каждой задачи ждёт его зелёного результата. Если прогон падает — ещё столько же.

Нужно:
1. сократить прогон CI до ~4–5 минут, не убирая ни одной проверки;
2. убрать ожидание CI из сессии агента — результат CI смотрит архитектор при приёмке.

## Контекст

- **CI** — `.github/workflows/ci.yml`, одна задача `ci` с шагами по очереди. Замер прогона 37832047256 (TASK-036):
  - интеграционные тесты (`pnpm test:integration`, Testcontainers) — **510 с**;
  - сборка 46 с, проверка типов 33 с, юнит-тесты 25 с, линтер 24 с, формат 13 с, установка и прочее — секунды.
- **Интеграционные тесты** — Vitest на настоящих PostgreSQL и Redis (Testcontainers), файлы `*.integration.test.ts` в `apps/api`. Каждый файл поднимает свои контейнеры. Перехват вывода `src/testing/output-capture.ts` проверяет каждый файл на утечку секретов — это должно остаться.
- **Полный набор интеграционных тестов на машине разработки не гоняется** (около 40 минут). Агенты запускают локально только файлы тех модулей, которые меняли. Поэтому CI — единственное место, где идёт весь набор. Убирать его нельзя.
- `concurrency` с `cancel-in-progress` уже есть — устаревший прогон отменяется.

## Требования

### 1. Параллельный CI

- **Быстрые проверки и интеграционные тесты — в параллельных задачах.**
  - Задача «checks»: установка, формат, линтер, типы, значки, юнит-тесты, сборка, `openapi:check`, `openapi:compat`, проверка мягкой остановки.
  - Интеграционные тесты — матрица из нескольких частей через `vitest --shard` (или равноценный способ). Число частей — решение агента по замеру, ориентир — 4. Части должны быть примерно равны по времени, а не только по числу файлов. Если для этого нужен порядок или распределение по длительности — сделать.
- **Ничего не пропускается.** Каждый интеграционный файл выполняется ровно в одной части. Добавить проверку, что объединение частей = все файлы `*.integration.test.ts`: новый файл не может выпасть, если матрицу забыли поправить.
- **Итог для ветки — один.** Добавить завершающую задачу (например «ci»), зависящую от всех частей. Она зелёная, только если зелёные все части. Итог прогона в `gh run list` остаётся одним `success`/`failure`.
- Кэш pnpm остаётся. Установка в каждой задаче — из кэша. Скачивание образов Docker (PostgreSQL, Redis, MinIO) — с кэшированием, если оно заметно сокращает время. Решение агента по замеру.
- Цель — прогон на `main` **не дольше 5 минут** от старта до итога. Если не получается — честный замер и причина в отчёте.

### 2. Агент не ждёт CI

- В `CLAUDE.md` (§11 и где ещё сказано про CI) записать порядок:
  1. агент проходит локальные проверки: format, lint, typecheck, test, build и интеграционные тесты изменённых модулей;
  2. пушит в `main` и пишет отчёт, **не дожидаясь CI**;
  3. в отчёте указывает идентификатор запущенного прогона (`gh run list`), если он доступен;
  4. CI проверяет архитектор при приёмке; красный CI — повод для доводки.
- Правило «push в main после зелёных проверок» относится к локальным проверкам. Ничего, что ослабляет сами проверки, не менять.

### 3. Списки, которые сверяют тесты, — ловить до пуша

Задача за задачей первый прогон CI падает на одном и том же:
- новые маршруты не внесены в список маршрутов теста прав (`identity/access.integration.test.ts`; TASK-036.B, TASK-036);
- новая фоновая задача не попала в список задач;
- новая миграция не попала в проверку миграций (`database.integration.test.ts`).

Агент запускает локально только интеграционные тесты своего модуля, поэтому такие тесты не видит.

- Найти такие проверки «полный список совпадает с …» в интеграционных тестах.
- Где возможно, вынести сверку списка в быструю проверку `pnpm test` без контейнеров: она сравнивает список в тесте с реестром маршрутов контракта, каталогом задач, файлами миграций. Где невозможно — назвать эти файлы в `CLAUDE.md` как обязательные к локальному запуску при новых маршрутах, задачах и миграциях.
- Что из этого сделано — решение агента. Цель: эта ошибка видна агенту до пуша.

## Бизнес-правила

- Ни одна проверка не удаляется, не ослабляется и не помечается необязательной.
- Секреты в CI не добавляются.

## Edge cases

- Новый интеграционный файл без правки матрицы — попадает в одну из частей автоматически, проверка полноты зелёная.
- Одна часть упала — итог прогона `failure`, остальные части доходят до конца (`fail-fast: false`), чтобы видеть все падения сразу.
- Нестабильный тест (как messaging в TASK-035.B) по-прежнему падает честно, без автоматического перезапуска.

## Не входит

- Ускорение самих тестов и переписывание тестов.
- Перенос CI на другой сервис или собственные раннеры.

## Acceptance Criteria

1. CI разбит на параллельные задачи; интеграционные тесты — несколько частей; итог — одна завершающая задача.
2. Проверка полноты: каждый интеграционный файл ровно в одной части (тест или шаг CI).
3. Замер: три прогона на `main` после изменения — время каждого и по частям; цель — не больше 5 минут.
4. Искусственно сломанный интеграционный тест во временной ветке даёт `failure` итоговой задачи. Ветку удалить; в `main` ничего не попадает.
5. `CLAUDE.md` — новый порядок «пуш без ожидания CI».
6. Сверка списков (требование 3): новый маршрут, задача или миграция, не внесённые в список, ловятся `pnpm test` или названной в `CLAUDE.md` локальной проверкой; проверено искусственным пропуском.
7. `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` — PASS.
8. Отчёт `tasks/TASK-076-REPORT.md` с замерами «было / стало».
